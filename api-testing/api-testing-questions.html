Q1 What is an API?

An API (Application Programming Interface) is a contract that allows two software systems to communicate with each other without knowing each other's internal implementation. It defines the rules: what requests can be sent, what data format is expected, and what response will be returned.

Example: A test automation framework calling GET /users/101 doesn't need to know how the backend stores user data in the database — it just needs to know the endpoint, the expected request format, and the response structure.

Interview angle: Be ready to explain APIs as the "waiter" analogy — the client (customer) doesn't talk to the kitchen (server/database) directly; the API (waiter) carries the request and brings back the response.

Q4 Difference between PUT and PATCH

  • PUT replaces the entire resource. If you omit a field, it may be wiped out or reset to default.
  • PATCH updates only the specified field(s); the rest of the resource remains untouched.
PUT /users/101
{ "name": "Sai", "email": "sai@test.com" }   // entire object sent

PATCH /users/101
{ "email": "sai.new@test.com" }              // only the changed field
Test design tip: A common bug class is a PUT endpoint that's incorrectly implemented as a PATCH (or vice versa) — always test PUT with a partial payload to confirm whether omitted fields get nulled out.

Q5 What are HTTP Status Codes?

Status codes are 3-digit codes returned by the server indicating the result of a request. They fall into 5 classes:

Q6 What is JSON?

JSON (JavaScript Object Notation) is a lightweight, human-readable, text-based data format used to exchange data between client and server. It's built on key-value pairs and supports nested objects/arrays — making it the default format for most REST APIs.

{
  "userId": 101,
  "name": "Sai",
  "roles": ["admin", "tester"],
  "active": true
}

In REST Assured, JSON responses are typically parsed using JsonPath or deserialized into POJOs for assertions.

Q7 Difference between Request Payload and Response Payload

  • Request Payload (Body): The data the client sends to the server — typically used with POST, PUT, PATCH. Example: login credentials, new order details.
  • Response Payload (Body): The data the server sends back to the client after processing the request — e.g., the created resource, an error message, or a token.
// Request Payload
{ "username": "sai", "password": "Pass@123" }

// Response Payload
{ "token": "eyJhbGciOi...", "expiresIn": 3600 }

Q8 What are Headers in an API Request?

Headers carry metadata about the request/response — separate from the actual body data. Common headers include:

  • Content-Type — format of the body (e.g., application/json)
  • Authorization — credentials/tokens (e.g., Bearer <token>)
  • Accept — format the client expects in response
  • Cache-Control — caching directives
  • User-Agent, X-Request-Id, custom correlation IDs for tracing
given()
  .header("Content-Type", "application/json")
  .header("Authorization", "Bearer " + token)
.when()
  .get("/api/orders")
.then()
  .statusCode(200);

Q9 What is Authentication?

Authentication answers "Who are you?" — it verifies the identity of the user/system making the request. Common mechanisms: Basic Auth, API Keys, JWT tokens, OAuth 2.0, mTLS (client certificates).

Given your mTLS/SSL security testing background, you can add: "I've validated authentication at the transport layer too — using JKS/PKCS12 keystores for mutual TLS handshake testing, not just application-layer tokens."

Q10 What is Authorization?

Authorization answers "What are you allowed to do?" — once identity is confirmed, authorization determines what resources/actions that identity can access (roles, scopes, permissions).

Quick distinction: Authentication happens first (login), authorization happens after (access control). A 401 means authentication failed; a 403 means authentication succeeded but authorization failed.

Q11 What is a JWT Token and how does it work?

JWT (JSON Web Token) is a compact, self-contained token used for authentication/authorization. It has 3 base64-encoded parts separated by dots:

HEADER.PAYLOAD.SIGNATURE

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJzYWkiLCJyb2xlIjoiYWRtaW4ifQ.4f8a...
  • Header: algorithm + token type (e.g., HS256)
  • Payload: claims — user id, role, expiry (exp), issued-at (iat)
  • Signature: verifies the token wasn't tampered with

Flow: Client logs in → server issues a signed JWT → client sends it in the Authorization: Bearer <token> header on every subsequent request → server validates the signature and expiry before granting access. JWTs are stateless — the server doesn't need to store session data.

Q12 What is OAuth 2.0?

OAuth 2.0 is an authorization framework that lets a third-party application access a user's resources without exposing their credentials. It uses tokens (often JWT) instead of passwords for API access.

Common grant types:

  • Authorization Code — used in web apps (user redirected to login, app gets a code, exchanges it for a token)
  • Client Credentials — machine-to-machine (no user involved) — most common in API test automation
  • Password Grant — legacy, direct username/password exchange for token (now discouraged)
  • Refresh Token — used to get a new access token without re-authenticating

In test automation, a typical pattern (similar to a TokenManager singleton you may have built) is to fetch a token once via Client Credentials grant and reuse it across the test suite until it expires.

Q13 What is Idempotency in APIs?

An operation is idempotent if calling it multiple times with the same input produces the same result as calling it once — without unintended side effects.

  • GET, PUT, DELETE — idempotent by design
  • POST — generally NOT idempotent (calling it twice creates two resources)

Example: PUT /accounts/101/balance {"balance": 5000} called 5 times always results in balance = 5000. But POST /orders called twice creates two separate orders — a critical test scenario (see duplicate order bonus question below).

Q15 What validations should be performed in API Testing?

  • Status Code Validation — correct code for the scenario (200, 201, 400, 404, etc.)
  • Response Body Validation — field values, data types, nested objects/arrays match expectations
  • Schema Validation — response structure conforms to a JSON Schema/contract (catches breaking changes)
  • Header Validation — Content-Type, caching headers, security headers (e.g., X-Content-Type-Options)
  • Response Time Validation — SLA checks (e.g., response under 2 seconds)
  • Database Validation — confirm the API's side effects are correctly persisted (e.g., after a POST, query the DB via JDBC to confirm the row exists with correct values)
  • Security Validation — auth/authz checks, SQL injection, broken object-level authorization (BOLA), sensitive data exposure
given().header("Authorization", "Bearer " + token)
.when().get("/api/orders/5001")
.then()
  .statusCode(200)
  .time(lessThan(2000L))
  .contentType(ContentType.JSON)
  .body(matchesJsonSchemaInClasspath("order-schema.json"))
  .body("orderId", equalTo(5001))
  .body("status", equalTo("CONFIRMED"));

Q16 What is API Versioning?

Versioning allows APIs to evolve without breaking existing clients. Common strategies:

  • URI Versioning: /api/v1/orders, /api/v2/orders
  • Query Parameter: /api/orders?version=2
  • Header Versioning: Accept: application/vnd.company.v2+json

Test consideration: when a new version rolls out, regression tests must confirm the old version still behaves correctly (backward compatibility) until clients migrate.

Q17 What is Rate Limiting?

Rate limiting restricts how many requests a client can make in a given time window, protecting the API from abuse/overload. When exceeded, the server typically returns 429 Too Many Requests.

Common headers returned: X-RateLimit-Limit, X-RateLimit-Remaining, Retry-After. As a tester, you'd verify the limit is enforced correctly, the correct status code/headers are returned, and the limit resets after the window expires — tools like JMeter are useful here to simulate burst traffic.

Q20 How would you test a Login API?

Positive scenarios:

  • Valid username + valid password → 200 OK, valid token returned
  • Token contains correct claims (role, expiry) — decode and validate JWT
  • Response time within SLA

Negative scenarios:

  • Invalid password → 401, no token leaked in response
  • Non-existent username → 401 (not 404 — to avoid leaking which usernames exist)
  • Empty/missing fields → 400 Bad Request with clear validation message
  • SQL injection attempt in username/password fields → properly sanitized, no 500 error
  • Locked/disabled account → appropriate error code and message
  • Case sensitivity checks on username/email

Security/edge cases:

  • Brute-force protection (account lockout after N failed attempts)
  • Token not exposed in URL or logs
  • Password never returned in any response payload
  • Re-login while an old token is still valid (session handling behavior)

DB-level validation: confirm successful login updates a last_login_timestamp or audit log entry where applicable.

💡 Bonus Scenario-Based Questions

B1 How would you test a Payment API?

  • Functional: successful payment with valid card/account, correct amount deducted, correct currency handling, decimal/rounding precision
  • Negative: insufficient funds, expired card, invalid CVV, invalid currency code, negative/zero amount
  • Idempotency: retrying the same payment request (e.g., due to network timeout) with an idempotency key should NOT charge twice
  • Security: PCI-DSS considerations — card numbers should never appear in logs/responses in plain text (masked, e.g., **** **** **** 1234)
  • Integration: validate webhook/callback handling for async payment confirmation (e.g., payment gateway calling back after processing)
  • DB validation: transaction record created with correct status (PENDING → SUCCESS/FAILED), ledger/balance updated correctly, no orphaned/partial transactions
  • Failure/rollback: if the payment gateway times out mid-transaction, confirm the system doesn't leave the order in an inconsistent state

B2 How would you validate duplicate order creation?

  • Send the same POST /orders request twice in quick succession (simulating double-click or retry) and confirm only one order is created if an idempotency key is used
  • Verify the API supports an Idempotency-Key header — same key + same payload should return the original response (often 200 with the existing resource) rather than creating a duplicate
  • Check DB-level constraints — e.g., a unique constraint on (userId + orderReference) to prevent duplicates at the data layer as a safety net
  • Test concurrent/parallel requests (using JMeter or multi-threaded REST Assured calls) to confirm race conditions don't bypass the duplicate check
  • Confirm appropriate response on duplicate detection — typically 409 Conflict with a clear error message

B3 How would you test token expiration?

  • Generate a token with a short expiry (e.g., exp set to a few seconds) and confirm requests succeed before expiry and fail with 401 after
  • Confirm the error response clearly indicates "token expired" (not a generic 401, ideally — useful for debugging and good API design)
  • Validate refresh token flow — expired access token + valid refresh token should issue a new access token without requiring full re-login
  • Test using an expired refresh token too — should be rejected and force re-authentication
  • Boundary testing: request sent exactly at the expiry timestamp (clock-skew tolerance checks)
  • Confirm token is invalidated server-side on logout (if using a blocklist/revocation strategy) and can't be reused
// Pseudocode pattern using a TokenManager singleton
String expiredToken = tokenManager.getExpiredToken();
given().header("Authorization", "Bearer " + expiredToken)
.when().get("/api/orders")
.then().statusCode(401)
       .body("error", containsString("expired"));

B4 How would you test APIs under high load?

  • Load testing: simulate expected concurrent users (e.g., via JMeter) and measure response time, throughput, and error rate under normal peak conditions
  • Stress testing: push beyond expected load to find the breaking point and confirm graceful degradation (not crashes or data corruption)
  • Spike testing: sudden burst of traffic (e.g., flash sale scenario) to validate auto-scaling and rate-limiting behavior
  • Soak/endurance testing: sustained load over a long duration to catch memory leaks or connection pool exhaustion
  • Monitoring during tests: correlate JMeter results with Grafana dashboards (API latency, error rate) and Kibana logs to pinpoint bottlenecks
  • Validation points: response times stay within SLA, no increase in 5xx errors, DB connection pool doesn't exhaust, no data integrity issues from concurrent writes

B5 How would you validate data consistency between API and Database?

  • After a POST/PUT API call, query the database directly (via JDBC — Oracle/PostgreSQL/MariaDB) to confirm the persisted row matches the request payload exactly
  • Validate data type and format consistency (e.g., API returns a formatted date string; DB stores a timestamp — confirm correct mapping)
  • For async/event-driven flows (e.g., Kafka-based pipelines), validate eventual consistency — poll the DB or downstream system with a timeout/retry mechanism rather than asserting immediately
  • Validate cache-DB consistency where Redis is used — confirm cache is correctly invalidated/refreshed on updates, and reads reflect the latest DB state (cache-first read patterns with TTL)
  • Validate soft-deletes/audit columns (e.g., updated_at, is_deleted) are correctly set after relevant API operations
  • Use a combination of REST Assured response assertions + JDBC queries in the same test to assert both layers in one flow
// Example pattern
Response response = given().body(orderPayload)
  .post("/api/orders");
response.then().statusCode(201);

int orderId = response.jsonPath().getInt("orderId");

// DB-side validation
String query = "SELECT status, amount FROM orders WHERE id = ?";
ResultSet rs = dbUtil.executeQuery(query, orderId);
assertEquals("CONFIRMED", rs.getString("status"));
assertEquals(orderPayload.getAmount(), rs.getBigDecimal("amount"));
