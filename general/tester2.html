Q1 Explain the four pillars of OOP with automation examples.

The four pillars are Encapsulation, Inheritance, Polymorphism, and Abstraction. In an automation framework they map directly onto everyday design decisions:

  • Encapsulation — Page classes keep WebElement locators private and expose only behavior methods like login() or clickSubmit(). Tests never touch locators directly, so a UI change only requires editing the page class.
  • Inheritance — A BasePage class holds common methods (waitForElement, click, getText) and every page object (LoginPage, DashboardPage) extends it. Similarly a BaseTest holds driver setup/teardown that all test classes inherit.
  • Polymorphism — Method overloading, e.g. multiple click(WebElement e) and click(By locator) variants; method overriding, e.g. each page class overrides an abstract isPageLoaded() method from BasePage to define its own load-verification logic.
  • Abstraction — An interface like DriverFactory exposes getDriver() without exposing whether it's Chrome, Firefox, or a remote grid node underneath — tests just call the interface.
public abstract class BasePage {
    protected WebDriver driver;
    public BasePage(WebDriver driver) { this.driver = driver; }
    public abstract boolean isPageLoaded();
    protected void click(WebElement el) { el.click(); }
}

public class LoginPage extends BasePage {
    public LoginPage(WebDriver driver) { super(driver); }
    @Override
    public boolean isPageLoaded() { return driver.findElement(By.id("loginForm")).isDisplayed(); }
}
Interview angle: Don't just define the terms — always tie each one back to a concrete framework decision. Interviewers are checking whether you actually apply OOP or just memorized definitions.

Q3 What is the difference between == and .equals() in Java?

== compares references (memory addresses) for objects, and actual values for primitives. .equals() compares logical/content equality, and its behavior depends on whether the class has overridden it.

String a = new String("QA");
String b = new String("QA");
System.out.println(a == b);       // false - different objects
System.out.println(a.equals(b));  // true  - same content

String c = "QA";
String d = "QA";
System.out.println(c == d);       // true - same reference from String pool
Automation relevance: Always use .equals() for assertions on Strings, e.g. Assert.assertEquals(actualTitle, expectedTitle) — TestNG's assertEquals internally uses .equals(), not ==, which is exactly why it's safe for object comparison.

Q4 String vs StringBuilder vs StringBuffer?

  • String — immutable. Every concatenation creates a new object in the string pool/heap, which is wasteful in loops.
  • StringBuilder — mutable, not thread-safe, faster. Best choice for building strings inside loops (e.g. constructing a dynamic XPath or a log message across many appends).
  • StringBuffer — mutable, thread-safe (synchronized methods), slightly slower than StringBuilder. Rarely needed unless multiple threads write to the same buffer, e.g. shared logging in a parallel TestNG suite.
StringBuilder sb = new StringBuilder();
for (String col : columnNames) {
    sb.append(col).append(", ");
}
String query = "SELECT " + sb.substring(0, sb.length()-2) + " FROM transactions";

Rule of thumb: use String for fixed values, StringBuilder for single-threaded dynamic building (99% of framework code), StringBuffer only for shared mutable state across threads.

Q6 Explain HashMap internal working (hashCode, buckets, equals, collisions, resizing, load factor, Java 8 treeification).

HashMap stores entries in an array of buckets. The process for put(key, value):

  1. Java calls key.hashCode(), then applies an internal spreading function to reduce collisions.
  2. The hash is mapped to a bucket index via index = hash & (capacity - 1).
  3. If the bucket is empty, the entry is placed directly. If not empty (a collision), Java walks the chain and uses .equals() to check if the key already exists — if yes, the value is updated; if no, the new entry is appended to the chain.
  4. Load factor (default 0.75) determines when the map resizes: when size > capacity * loadFactor, capacity doubles and all entries are rehashed.
  5. Java 8 treeification: if a single bucket's chain grows beyond 8 entries (and total capacity ≥ 64), that chain converts from a linked list to a red-black tree, changing lookup from O(n) to O(log n) worst case — a defense against hash-flooding/poor hash functions.
Why equals/hashCode both matter: if you use a custom object as a HashMap key (e.g. a TestDataKey class) and override equals() without overriding hashCode(), two "equal" objects can land in different buckets and the map will behave incorrectly — a classic Java interview trap.

Q7 HashMap vs HashSet? How does HashSet work internally?

HashSet is internally backed by a HashMap. Every element you add to a HashSet is stored as a key in an underlying HashMap, with a constant dummy PRESENT object as the value.

public HashSet() { map = new HashMap<>(); }
public boolean add(E e) { return map.put(e, PRESENT) == null; }
  • HashMap stores key-value pairs, allows one null key.
  • HashSet stores only unique values, no duplicates, allows one null element.

Automation use case: deduplicating scraped table data, or verifying "no duplicate order IDs returned by an API" — Assert.assertEquals(list.size(), new HashSet<>(list).size()) is a quick way to assert uniqueness.

Q8 Reverse a String (loop, StringBuilder, recursion).

// 1. StringBuilder (preferred - cleanest, O(n))
public static String reverseBuilder(String s) {
    return new StringBuilder(s).reverse().toString();
}

// 2. Manual loop (shows you understand the mechanics)
public static String reverseLoop(String s) {
    char[] chars = s.toCharArray();
    int left = 0, right = chars.length - 1;
    while (left < right) {
        char temp = chars[left];
        chars[left] = chars[right];
        chars[right] = temp;
        left++; right--;
    }
    return new String(chars);
}

// 3. Recursion
public static String reverseRecursive(String s) {
    if (s.isEmpty()) return s;
    return reverseRecursive(s.substring(1)) + s.charAt(0);
}
Follow-up to expect: "Which is most efficient?" — StringBuilder's reverse() is O(n) time and typically the best answer; recursion is O(n) time but O(n) additional stack space and risks StackOverflowError on very long strings.

Q9 Check whether a String is a palindrome.

public static boolean isPalindrome(String s) {
    String clean = s.toLowerCase().replaceAll("[^a-z0-9]", "");
    int left = 0, right = clean.length() - 1;
    while (left < right) {
        if (clean.charAt(left) != clean.charAt(right)) return false;
        left++; right--;
    }
    return true;
}

// Quick one-liner alternative
public static boolean isPalindromeQuick(String s) {
    String clean = s.toLowerCase().replaceAll("[^a-z0-9]", "");
    return clean.equals(new StringBuilder(clean).reverse().toString());
}

The two-pointer version is generally preferred in interviews because it's O(n) time, O(1) extra space (no new reversed string built), and demonstrates pointer manipulation.

Q10 Find duplicate characters in a String using HashMap<Character, Integer>.

public static void findDuplicates(String s) {
    Map<Character, Integer> freq = new HashMap<>();
    for (char c : s.toCharArray()) {
        freq.put(c, freq.getOrDefault(c, 0) + 1);
    }
    for (Map.Entry<Character, Integer> entry : freq.entrySet()) {
        if (entry.getValue() > 1) {
            System.out.println(entry.getKey() + " -> " + entry.getValue());
        }
    }
}

getOrDefault() avoids null-check boilerplate. Time complexity O(n), space O(k) where k is the number of distinct characters (bounded, so effectively O(1) for ASCII text).

Q11 Find duplicate elements in an array.

public static Set<Integer> findDuplicates(int[] arr) {
    Set<Integer> seen = new HashSet<>();
    Set<Integer> duplicates = new HashSet<>();
    for (int num : arr) {
        if (!seen.add(num)) {   // add() returns false if already present
            duplicates.add(num);
        }
    }
    return duplicates;
}

Using Set.add()'s boolean return value avoids a separate contains() check, keeping this a single O(n) pass instead of O(n) lookups each also costing time — a small but real optimization interviewers like to see.

Q12 Find the second-largest number in an array (sorting and single-pass approaches).

// Sorting approach - O(n log n)
public static int secondLargestSort(int[] arr) {
    int[] sorted = arr.clone();
    Arrays.sort(sorted);
    return sorted[sorted.length - 2];
}

// Single-pass approach - O(n), preferred in interviews
public static int secondLargestSinglePass(int[] arr) {
    int largest = Integer.MIN_VALUE, second = Integer.MIN_VALUE;
    for (int num : arr) {
        if (num > largest) {
            second = largest;
            largest = num;
        } else if (num > second && num != largest) {
            second = num;
        }
    }
    return second;
}

The single-pass version is the "better" answer because it's O(n) with O(1) space and doesn't mutate/require a full sort just to get one value — call this out explicitly if asked to optimize.

Q13 Find the frequency of each word in a String.

public static Map<String, Integer> wordFrequency(String text) {
    Map<String, Integer> freq = new HashMap<>();
    String[] words = text.toLowerCase().split("\\s+");
    for (String word : words) {
        word = word.replaceAll("[^a-z0-9]", "");
        if (word.isEmpty()) continue;
        freq.merge(word, 1, Integer::sum);
    }
    return freq;
}

Map.merge() is a cleaner Java 8+ alternative to getOrDefault + put — it's a good detail to mention to show familiarity with modern Java APIs, which pairs well with a Streams-based follow-up if asked.

Q14 Remove duplicates from a collection while preserving insertion order.

// Using LinkedHashSet - maintains insertion order, removes duplicates

Q15 Find the first non-repeated character in a String.

public static Character firstNonRepeated(String s) {
    Map<Character, Integer> freq = new LinkedHashMap<>();
    for (char c : s.toCharArray()) {
        freq.put(c, freq.getOrDefault(c, 0) + 1);
    }
    for (Map.Entry<Character, Integer> entry : freq.entrySet()) {
        if (entry.getValue() == 1) return entry.getKey();
    }
    return null;
}

LinkedHashMap is used instead of HashMap specifically to preserve the original character order during the second iteration — this is the subtle detail that separates a correct answer from a functionally-wrong one that returns the wrong character when a plain HashMap reorders entries.

Selenium (15 Questions)

Q16 Explain Selenium WebDriver architecture.

Selenium WebDriver architecture has four layers:

  1. Selenium Client Library (bindings) — the Java/Python/JS API you call (driver.findElement(), driver.get()).
  2. JSON Wire Protocol / W3C WebDriver Protocol — client commands are serialized into HTTP requests carrying JSON payloads, sent to the browser driver over REST.
  3. Browser Drivers — ChromeDriver, GeckoDriver, EdgeDriver etc. Each is a standalone server that receives the HTTP/JSON commands and translates them into native browser automation calls.
  4. Browser — executes the actual native call (click, navigate, type) and the driver returns the result back up the chain as an HTTP response.

This is why Selenium works across browsers and languages: the client library and the wire protocol are standardized (W3C spec since Selenium 4), so any language binding can talk to any compliant browser driver.

Q18 Explain implicit wait, explicit wait, and fluent wait.

  • Implicit wait — a global timeout set once on the driver; for every findElement call, WebDriver polls the DOM up to that timeout before throwing NoSuchElementException. driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
  • Explicit wait — condition-specific, applied to one element at a time using WebDriverWait + ExpectedConditions, e.g. wait until clickable, visible, or an attribute changes.
  • Fluent wait — a configurable explicit wait that lets you set polling interval and which exceptions to ignore during polling (e.g. ignore StaleElementReferenceException while waiting).
Wait<WebDriver> wait = new FluentWait<>(driver)
    .withTimeout(Duration.ofSeconds(20))
    .pollingEvery(Duration.ofMillis(500))
    .ignoring(StaleElementReferenceException.class);

WebElement el = wait.until(d -> d.findElement(By.id("submitBtn")));
Critical rule: never mix implicit and explicit waits in the same test — it causes unpredictable total wait times because the two timers can stack in certain browser/driver combinations. Pick one strategy (explicit is the industry standard) and stay consistent.

Q19 Why should Thread.sleep() not be used everywhere in Selenium automation?

  • Fixed, not conditional — it always waits the full duration regardless of whether the element appeared in 200ms or 5s, making suites unnecessarily slow.
  • Flaky under variable load — if the app is slower than the hardcoded sleep on a given run (CI runner under load, slower network), the test fails even though the app is fine — this is one of the most common causes of flaky pipelines.
  • Not scalable — with hundreds of tests, unnecessary fixed sleeps compound into hours of wasted execution time, directly hurting parallel/CI run time (relevant to Q4 in the bonus scenarios: "100 tests take 2 hours").

The correct approach is condition-based waiting (explicit/fluent waits tied to actual DOM state), reserving Thread.sleep() only for rare, justified cases like intentionally pacing a rate-limited third-party API call — and even then a scheduled retry or backoff is usually better.

Q20 Element present in DOM but Selenium throws ElementNotInteractableException. How to debug and fix?

This exception means the element exists in the DOM but the browser can't currently interact with it. Debugging steps:

  1. Check visibility — element might have display:none, zero height/width, or be off-screen. Use an explicit wait for visibilityOf instead of just presenceOf.
  2. Check overlap — another element (modal, spinner, sticky header) may be covering it. Scroll it into view: ((JavascriptExecutor) driver).executeScript("arguments[0].scrollIntoView(true);", element);
  3. Check disabled state — element may be present but disabled until a prior form field is filled; wait for the enabled attribute/condition.
  4. Check animation/transition — the element might be mid-CSS-transition (e.g. sliding into a drawer); a small explicit wait on a stable attribute usually resolves this.
  5. Last resort — JS click — executeScript("arguments[0].click();", element) bypasses interactability checks, but should be used sparingly since it can mask real UX bugs (a real user also couldn't click it).

Q21 How do you handle StaleElementReferenceException?

This occurs when the DOM has been refreshed/re-rendered (AJAX update, page reload, React re-render) after the element reference was fetched, so the old reference no longer points to a valid node.

  • Re-locate the element right before interacting with it rather than caching it far in advance.
  • Wrap in a retry loop that catches StaleElementReferenceException and re-fetches:
public void safeClick(By locator) {
    int attempts = 0;
    while (attempts < 3) {
        try {
            driver.findElement(locator).click();
            return;
        } catch (StaleElementReferenceException e) {
            attempts++;
        }
    }
    throw new RuntimeException("Element still stale after retries: " + locator);
}

Also consider using FluentWait.ignoring(StaleElementReferenceException.class) so waits automatically re-poll through staleness rather than failing outright (as shown in Q18).

Q22 How do you handle dynamic web elements?

  • Dynamic locators — use partial matches: contains(), starts-with(), CSS attribute-contains selectors ([id^='row-']) instead of full static IDs that change per session/build.
  • Relative/axes-based XPath — anchor to a stable nearby element (a label, a heading) and traverse to the dynamic sibling/child, rather than relying on the dynamic element's own attributes.
  • Explicit waits for the element to reach the expected state before acting.
  • Data-* test attributes — if you can influence the dev team, requesting stable data-testid attributes is the most robust long-term fix.

Q30 How would you make Selenium tests reliable and reduce flaky failures?

  • Replace all Thread.sleep() with explicit/fluent waits tied to real DOM conditions.
  • Use stable, semantic locators (data-testid) over brittle absolute XPath.
  • Isolate test data per test/thread to avoid cross-test collisions in parallel runs (see Builder + Faker pattern).
  • Retry transient failures at the framework level (a bounded IRetryAnalyzer in TestNG) rather than manual re-runs, but cap retries and log them separately from genuine failures.
  • Stabilize environment — pin browser/driver versions, avoid shared mutable test environments, use Docker for consistent execution across local and CI.
  • Add synchronization around known slow operations (loading spinners, async API calls) instead of assuming instantaneous UI updates.
  • Track flakiness over time (e.g. Allure history/trend) and quarantine chronically flaky tests for investigation rather than letting them erode trust in the whole suite.

TestNG & Framework Design (10 Questions)

Q31 Explain your automation framework architecture from test execution to browser interaction.

A good answer walks through the full call chain layer by layer:

  1. Trigger — Jenkins/GitHub Actions invokes a Maven command (mvn test -DsuiteXmlFile=testng.xml).
  2. TestNG — reads testng.xml, resolves suites/groups/parallel settings, invokes @BeforeSuite → @BeforeClass → @BeforeMethod → @Test → @AfterMethod...
  3. Base Test / Hooks — @BeforeMethod initializes a WebDriver via a DriverFactory (ThreadLocal-scoped for parallel safety), reads config (browser, environment, base URL) via a config manager.
  4. Page Objects — the test calls high-level business methods on page objects (loginPage.loginAs(user)), which internally use the driver to locate elements and perform actions, with waits abstracted into a common utility layer.
  5. Assertions — TestNG/Hamcrest/AssertJ assertions validate expected vs actual state, optionally cross-checked against the database layer for backend validation.
  6. Reporting — Allure listeners capture steps, screenshots on failure, and logs; results are aggregated into an HTML report published by the CI pipeline.
  7. Teardown — @AfterMethod quits the driver and releases the grid/browser session.

Q32 Why do you use Page Object Model? What are its advantages?

POM separates UI structure (locators + page interactions) from test logic (business scenarios and assertions), one class per page/screen.

  • Maintainability — a UI change (locator, layout) requires editing exactly one page class, not every test that touches that page.
  • Reusability — the same page methods are reused across many test scenarios (login used in dozens of tests).
  • Readability — tests read like business flows (loginPage.login(user, pass); dashboardPage.verifyWelcomeMessage();) instead of raw Selenium calls, making them reviewable by non-automation stakeholders.
  • Reduced duplication — common waits/actions live in a shared BasePage.

Q33 POM vs PageFactory? Would you use PageFactory in a modern framework?

PageFactory is a Selenium utility built on top of POM that uses @FindBy annotations and PageFactory.initElements() to auto-initialize WebElement fields via dynamic proxies, instead of calling driver.findElement() manually in every method.

public class LoginPage {
    @FindBy(id = "username") WebElement usernameField;
    @FindBy(id = "password") WebElement passwordField;

    public LoginPage(WebDriver driver) {
        PageFactory.initElements(driver, this);
    }
}

Would I use it today? Generally no for a modern framework. PageFactory elements are lazily located but cached in a way that increases exposure to StaleElementReferenceException in highly dynamic SPAs (React/Angular), and it doesn't play as cleanly with Selenium 4's relative locators or with Playwright-style auto-waiting patterns. Most current frameworks use plain By locators returned fresh on each call, or fixture/component-object patterns (as in a Playwright framework), which give more explicit control over waiting and re-fetching.

Q34 How do you manage WebDriver in an automation framework?

public class DriverManager {
    private static ThreadLocal<WebDriver> driverThread = new ThreadLocal<>();

    public static void setDriver(WebDriver driver) { driverThread.set(driver); }
    public static WebDriver getDriver() { return driverThread.get(); }
    public static void quitDriver() {
        if (driverThread.get() != null) {
            driverThread.get().quit();
            driverThread.remove();
        }
    }
}

Driver lifecycle is managed centrally: created in @BeforeMethod (fresh session per test = isolation), stored via ThreadLocal so parallel threads never share a driver instance, and explicitly quit + removed in @AfterMethod to avoid memory leaks and orphaned browser processes on CI agents.

Q35 How do you execute Selenium tests in parallel? Why is ThreadLocal<WebDriver> useful?

<suite name="RegressionSuite" parallel="methods" thread-count="5">
    <test name="ChromeTests">
        <classes>
            <class name="tests.LoginTest"/>
        </classes>
    </test>
</suite>

TestNG's parallel="methods|classes|tests" with thread-count spins up multiple threads executing tests concurrently. Without ThreadLocal<WebDriver>, all threads would share one static driver instance, causing threads to interfere with each other's browser state (Thread A navigating away mid-way through Thread B's assertion). ThreadLocal gives each thread its own isolated driver instance, keyed internally by thread ID, so parallel execution is safe.

Q36 How do you manage configuration such as browser, environment, base URL, credentials, and test parameters?

  • Properties/YAML files per environment — config-qa.properties, config-staging.properties, loaded based on a -Denv=qa system property.
  • A ConfigReader singleton/utility that loads the right file once and exposes typed getters (getBaseUrl(), getBrowser()).
  • Environment variables / Jenkins credentials store for secrets (passwords, API keys) — never hardcoded or committed to the repo.
  • Command-line overrides via Maven -D system properties so CI can inject browser/environment per pipeline run without code changes: mvn test -Dbrowser=firefox -Denv=staging.
  • TestNG parameters in testng.xml for suite-level values, read via @Parameters/ITestContext.

This is exactly the "two-tier env management strategy" pattern — a base config layer plus environment-specific overrides that CI can select at runtime.

Q37 How do you handle failed tests? Explain screenshots, logs, reports, retry, and defect reporting.

  • Screenshot on failure — captured automatically in @AfterMethod (see Q29) and attached to the report.
  • Logs — structured logging (Log4j2/SLF4J) at each major step, so a failure's log trail shows exactly what the test was doing right before it broke, not just the final exception.
  • Reports — Allure/Extent aggregate pass/fail counts, step-by-step execution, screenshots, and historical trend (Allure history stitching across CI runs).
  • Retry — a bounded IRetryAnalyzer re-runs a failed test once or twice to rule out transient flakiness, but retried tests are flagged separately so they don't silently hide real bugs.
  • Defect reporting — genuine failures (reproducible after retry, with a clear expected-vs-actual mismatch not caused by test/environment issues) get logged in JIRA/Azure DevOps with steps to reproduce, screenshot, logs, and environment/build info attached.

Q38 How do you implement retry in TestNG? When should retry NOT be used?

public class RetryAnalyzer implements IRetryAnalyzer {
    private int count = 0;
    private static final int MAX_RETRY = 2;

    @Override
    public boolean retry(ITestResult result) {
        if (count < MAX_RETRY) {
            count++;
            return true;
        }
        return false;
    }
}

// Apply via annotation
@Test(retryAnalyzer = RetryAnalyzer.class)
public void testLogin() { ... }

// Or globally via an IAnnotationTransformer registered in testng.xml
// so you don't have to annotate every single @Test method

When NOT to use retry:

  • To mask a genuinely broken feature — retry should only smooth over environment/timing flakiness, never functional bugs.
  • For tests with side effects that aren't idempotent (e.g. a test that creates a unique bank account each run) — re-running blindly can cause duplicate-data errors that look like new failures.
  • As a permanent fix for a known-flaky test — retry buys time; the flaky root cause (bad wait, race condition) still needs to be fixed, and retried-but-passed tests should be visibly flagged in reports, not silently marked green.

Q39 How do you identify and reduce flaky tests?

Identify:

  • Track pass/fail history per test across runs (Allure trend/history) — a test that flips between pass/fail on the same code+data is a flakiness signal.
  • Run suspect tests repeatedly in isolation (e.g. TestNG invocationCount) to reproduce intermittent failures.
  • Correlate failures with parallel execution — tests that only fail under thread-count > 1 usually point to shared state/test-data collisions.

Reduce: replace hard sleeps with proper waits, isolate test data per test (Builder + Faker pattern generates unique data per run), avoid inter-test dependencies (each test should set up its own preconditions, not rely on execution order), stabilize the environment (pinned driver/browser versions, dedicated Grid nodes), and quarantine chronically flaky tests into a separate suite while root-causing them so they don't erode confidence in the main pipeline.

Q43 Explain INNER JOIN vs LEFT JOIN with an example.

  • INNER JOIN — returns only rows that have a match in both tables.
  • LEFT JOIN — returns all rows from the left table, plus matched rows from the right table; unmatched right-side columns come back as NULL.
-- INNER JOIN: only customers who have placed at least one order
SELECT c.customer_name, o.order_id
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id;

-- LEFT JOIN: all customers, including those with zero orders (order_id = NULL)
SELECT c.customer_name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

This directly sets up Q46 (customers who never placed an order) — that's a LEFT JOIN filtered to WHERE o.order_id IS NULL.

FROM (

Q49 Explain primary key vs foreign key.

  • Primary Key (PK) — uniquely identifies each row in a table; cannot be NULL, must be unique, and a table has exactly one (though it can be composite across multiple columns).
  • Foreign Key (FK) — a column (or set of columns) in one table that references the Primary Key of another table, enforcing referential integrity (you can't insert an order for a customer_id that doesn't exist in the customers table).
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(100)
);

CREATE TABLE orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);

Test relevance: understanding FK relationships is essential for writing correct joins in validation queries and for building test data that doesn't violate referential integrity constraints when seeding/cleaning up test data.

Q50 How do you use SQL in automation for backend/database validation? Explain a UI/API-to-database validation flow.

// JDBC assertion example

         PreparedStatement stmt = conn.prepareStatement(query)) {
        stmt.setString(1, orderId);
        try (ResultSet rs = stmt.executeQuery()) {
            return rs.next() ? rs.getString("status") : null;
        }
    }
}

Q55 How do you terminate a process? Explain kill vs kill -9.

kill <PID>       # sends SIGTERM (15) - graceful shutdown, process can clean up
kill -9 <PID>    # sends SIGKILL (9) - immediate, forceful termination, no cleanup

pkill -f chromedriver
killall chromedriver

kill (SIGTERM) asks the process to shut down gracefully — it can close file handles, flush logs, release locks first. kill -9 (SIGKILL) is handled by the OS kernel directly and cannot be caught or ignored by the process — it dies immediately with no cleanup, which can leave temp files or locked resources behind. Best practice: try plain kill first, escalate to -9 only if the process is genuinely hung and unresponsive (e.g. a stuck orphaned ChromeDriver process after a CI job crash).

Q56 Explain $? in shell scripting. How would you use it after executing Maven tests?

$? holds the exit status of the last executed command: 0 means success, any non-zero value means failure (Maven typically returns 1 on test failure or build error).

mvn test
if [ $? -eq 0 ]; then
    echo "All tests passed"
else
    echo "Build failed - tests did not pass"
    exit 1
fi

This is exactly how Jenkins/CI decides whether to mark a pipeline stage as passed or failed — the shell step's exit code propagates up and determines the overall build/pipeline status.

Q63 Explain the Software Testing Life Cycle (STLC).

  1. Requirement Analysis — understand what needs testing, identify testable requirements, raise ambiguity questions.
  2. Test Planning — define scope, strategy, resources, timelines, tools, entry/exit criteria.
  3. Test Case Design — write test cases/scenarios, identify test data needs, review cases.

Q64 How do you decide which test cases should be automated?

Good candidates for automation:

  • Repetitive, stable, high-frequency tests (regression suite, smoke tests run on every build).
  • Data-driven tests with many input/output combinations.
  • Time-consuming manual tests where automation saves significant effort (long end-to-end flows).
  • Tests requiring precision that's error-prone manually (financial calculations, large table validations).
  • Cross-browser/cross-environment checks that would multiply manual effort.

Poor candidates: one-off/exploratory tests, tests on UI still under active/frequent redesign (high maintenance cost for low ROI), highly subjective UX/visual judgment calls, and low-frequency edge cases where automation cost outweighs benefit.

The general rule of thumb is a cost-benefit calculation: automate when (execution frequency × manual effort saved) > (automation build + maintenance cost) over a reasonable time horizon.

Q65 A developer says "It works on my machine." How would you investigate the issue?

  2. Check configuration differences — base URL, environment-specific config, feature flags, database state/seed data that might differ.
  3. Check for environment-specific data — hardcoded local test data, local-only mocked services, or a local DB with different seed data than CI/QA.
  4. Reproduce with logs/screenshots — if it's an automated test, pull the CI run's logs, screenshots, and Allure report to see the actual failure point rather than guessing.
  5. Check network/timing differences — CI environments are often slower/under more load; a race condition invisible on a fast local machine can surface as a real timing bug in CI (ties back to Q19/Q30 on flakiness).

Git & Version Control (10 Questions)

Q66 Explain the difference between git fetch, git pull, and git merge.

  • git fetch — downloads commits/branches/tags from the remote into your local origin/* tracking branches, but does NOT touch your working directory or current branch. Safe to run anytime.
  • git pull — equivalent to git fetch followed by git merge (or git rebase if --rebase is used) — it fetches AND immediately integrates the remote changes into your current branch.
  • git merge — combines the changes of a specified branch into your current branch, creating a merge commit if the histories have diverged.
git fetch origin
git diff main origin/main       # inspect what changed before merging
git merge origin/main            # merge only when you're ready

# vs the shortcut that does both steps at once
git pull origin main
Interview angle: mention that you prefer fetch + review + merge over a blind pull on shared framework branches, since it lets you see incoming changes before they touch your working copy — relevant when several people modify the same POM classes or CI config.

Q67 What is the difference between git merge and git rebase? When would you use each?

  • git merge — preserves full history exactly as it happened, creates a merge commit joining two branch tips. Non-destructive, but history can get cluttered with many merge commits on an active repo.
  • git rebase — replays your branch's commits on top of the target branch's latest commit, producing a linear history with no merge commit. Rewrites commit hashes, so it's destructive to shared history if used incorrectly.
git checkout feature/kafka-validation
git rebase main
# resolve any conflicts, then:
git rebase --continue

When to use which: rebase your own local feature branch onto main before opening a PR, to keep history clean and linear. Never rebase a branch that others have already pulled/based work on — that rewrites shared commit history and breaks everyone else's local copies. Use merge (not rebase) when integrating a completed feature branch into main via a PR, since it preserves an honest record of when the feature landed.

Q68 How do you resolve a merge conflict? Walk through the process.

  1. Git pauses the merge/rebase and marks conflicted files, inserting conflict markers directly into the file:
<<<<<<< HEAD
public static final int DEFAULT_TIMEOUT = 10;
=======
public static final int DEFAULT_TIMEOUT = 15;
>>>>>>> feature/increase-timeout
  1. Open the file, decide which change (or a combination) is correct, and manually remove the conflict markers.
  2. Stage the resolved file: git add DriverConfig.java
  3. Continue the operation: git merge --continue or git rebase --continue (rebase may repeat this per commit).
  4. Run the affected tests locally before pushing, to make sure the resolution didn't silently break anything — conflict resolution is a common source of "worked before, broken after merge" bugs in automation config files like testng.xml or CI YAML.

Useful commands during conflict resolution: git status (lists conflicted files), git diff (shows conflict details), git merge --abort / git rebase --abort (bail out completely and return to the pre-merge state if things go wrong).

Q69 Explain git cherry-pick. When would you use it in a test automation context?

git cherry-pick <commit-hash> applies a single specific commit from one branch onto your current branch, without merging the entire branch.

git checkout release/v2.3
git cherry-pick a1b2c3d

# if the commit conflicts, resolve then:
git cherry-pick --continue

Automation use case: a critical bug fix (e.g. a broken locator or a wait-condition fix) lands on main but needs to also ship on an active release/v2.3 branch that's already diverged — cherry-pick lets you grab just that one commit onto the release branch without pulling in unrelated in-progress work from main.

Q71 How do you undo the last commit without losing your changes?

git reset --soft HEAD~1

This moves the branch pointer back one commit but keeps all changes staged in the index, so you can immediately re-commit with a corrected message or split it into multiple commits. Variants:

Q72 Explain git stash. When is it useful in a day-to-day automation workflow?

git stash temporarily shelves uncommitted changes so you can switch context cleanly — for example, you're mid-way through writing a new Karate feature file when an urgent production bug needs a hotfix branch. Stash your in-progress work, switch branches, fix the bug, switch back, then git stash pop to resume exactly where you left off without a half-finished commit cluttering history.

Q73 What is a detached HEAD state? How do you recover from it?

Normally HEAD points to a branch name, which in turn points to a commit. A detached HEAD happens when HEAD points directly to a specific commit instead of a branch — typically after git checkout <commit-hash> or checking out a tag. Any new commits made in this state aren't attached to any branch and can be lost once you switch away, since nothing references them.

# You're in detached HEAD and made commits you want to keep
git branch recovery-branch     # create a branch pointing at the current commit
git checkout recovery-branch   # now your commits are safely on a real branch

# If you didn't create a branch in time and already switched away
git reflog                     # find the "lost" commit hash in the history log
git checkout -b recovery-branch <lost-commit-hash>

git reflog is the safety net here — it records every HEAD movement locally (even ones not reachable from any branch), so accidentally "lost" commits are almost always recoverable as long as garbage collection hasn't run.

Q75 Describe a branching strategy you'd use for an automation framework repo (e.g. Git Flow, trunk-based).

For most automation framework repos, a lightweight trunk-based / feature-branch approach works better than full Git Flow, since test frameworks don't usually need long-lived release branches the way product code sometimes does:

  • main — always green/stable; every commit here should be safe for CI to run against any environment.
  • feature/* branches — one per new capability (e.g. feature/kafka-consumer-tests, feature/docker-grid-setup), short-lived, rebased onto main before merging via PR.
  • PR review + CI gate — every PR triggers the pipeline (smoke subset at minimum) before merge is allowed, so broken framework code never lands on main.
  • hotfix/* branches — for urgent fixes to a locator/config that's blocking the whole pipeline, merged and released fast, cherry-picked to any active release branch if one exists (see Q69).

If the project genuinely needs to support multiple parallel product release versions being tested simultaneously (e.g. testing v2.3 in production and v2.4 in staging at the same time), a release/* branch per active version is added, with fixes cherry-picked forward — but for a typical single-target automation suite, keeping it simple with trunk + short feature branches reduces merge overhead and keeps the framework easy to maintain.

API Testing: REST Assured, Karate & Kafka (10 Questions)

Q76 What is REST Assured and how does it fit into a Java automation framework?

REST Assured is a Java DSL library for testing REST APIs, built around a fluent given()/when()/then() syntax modeled on BDD-style readability. It handles request building, response parsing (JSON/XML), and assertions without needing a separate HTTP client library.

given()
    .baseUri("https://api.eventhub.com")
    .header("Content-Type", "application/json")
    .body(bookingPayload)
.when()
    .post("/v1/bookings")
.then()
    .statusCode(201)
    .body("status", equalTo("CONFIRMED"))
    .body("bookingId", notNullValue());

In a framework it typically sits as a separate API layer alongside the UI/Page Object layer, sharing the same config/environment management and reporting (Allure) infrastructure — the same request specs, base URIs, and auth tokens are reused across both hybrid API+UI tests and pure API-only test suites.

Q77 Explain the anatomy of a REST Assured test — what do given(), when(), and then() actually do?

  • given() — sets up the request context: base URI, headers, auth, query/path params, request body.
  • when() — specifies the HTTP action and endpoint: .get(), .post(), .put(), .delete(), .patch().
  • then() — validates the response: status code, headers, response time, and body content via JSON path assertions (hamcrest matchers).
Response response =
given()
    .pathParam("eventId", 4521)
    .queryParam("includeVenue", true)
.when()
    .get("/v1/events/{eventId}")
.then()
    .statusCode(200)
    .time(lessThan(2000L))
    .extract().response();

String venueName = response.jsonPath().getString("venue.name");

Reusable request specifications are typically extracted into a RequestSpecification builder (base URI, common headers, auth) so every test doesn't repeat boilerplate — analogous to how a BasePage centralizes common Selenium behavior.

Q78 How do you validate a JSON response's schema or structure, not just individual field values?

// Field-level assertions (fine for small/simple payloads)
.then()
    .body("customer.name", equalTo("Sai"))
    .body("items.size()", greaterThan(0))
    .body("items[0].price", greaterThan(0f));

// Full JSON Schema validation (better for larger/contract-critical payloads)
.then()
    .assertThat()
    .body(matchesJsonSchemaInClasspath("schemas/booking-response-schema.json"));

Field-by-field assertions are fine for a handful of values, but for larger payloads (or when you care about contract stability — required fields, types, enums) JSON Schema validation is far more maintainable: it validates the entire structure in one call and catches unexpected new/missing fields, not just the specific ones you remembered to assert on. This is especially valuable for banking/FinTech APIs where response contracts have compliance implications.

Q79 How do you chain data between API calls — for example, get an auth token, then use it in a subsequent request?

// Step 1: Authenticate and extract the token
String token =
given()
    .contentType("application/json")
    .body(Map.of("username", "sai", "password", "P@ssw0rd"))
.when()
    .post("/auth/login")
.then()
    .statusCode(200)
    .extract().path("accessToken");

// Step 2: Use the extracted token in the next request
given()
    .header("Authorization", "Bearer " + token)
.when()
    .get("/v1/bookings/mine")
.then()
    .statusCode(200);

.extract().path("...") (or .extract().response() for the full response object) pulls values out of one call's response for reuse. For longer chains (create booking → get bookingId → fetch booking details → cancel booking) this pattern extends naturally, and in Karate the same chaining is even more concise since response values are automatically available as variables in subsequent steps within the same feature file.

Karate is a BDD-style API testing framework where tests are written in Gherkin-like .feature files, combining API calls, assertions, and even UI/DB steps in one readable syntax — no Java glue code required for most scenarios.

Q81 How do you validate database state after an API call in a hybrid API+DB test?

// REST Assured + JDBC combined
Response response =
given().body(newOrderPayload)
.when().post("/v1/orders")
.then().statusCode(201).extract().response();

String orderId = response.jsonPath().getString("orderId");

// Independently verify the same data landed correctly in the DB
String dbStatus = getOrderStatusFromDB(orderId);  // JDBC query, see Q50
Assert.assertEquals(dbStatus, "CREATED");
Assert.assertEquals(response.jsonPath().getString("status"), "CREATED");

In Karate this is done via Java-interop calls to a helper class wrapping JDBC, or Karate's own karate.call to a Java utility, kept inside the same feature file so the full API-to-DB assertion chain reads as one scenario. The core principle mirrors Q50: never trust the API response alone for state-changing operations — independently confirm the backend actually persisted the expected state, since a "green" API response doesn't guarantee correct downstream persistence (especially with async processing via Kafka in between).

Q82 How do you handle authentication in API tests — Basic Auth, Bearer/OAuth2 tokens, and API keys?

// Basic Auth
given().auth().preemptive().basic("user", "pass")

// Bearer token (most common for modern APIs)
given().header("Authorization", "Bearer " + token)

// API key in header
given().header("X-API-Key", apiKey)

// OAuth2 - typically a 2-step flow: get token via client credentials, then use it
String token =
given()
    .auth().preemptive().basic(clientId, clientSecret)
    .formParam("grant_type", "client_credentials")
.when().post("/oauth/token")
.then().extract().path("access_token");

Framework design tip: centralize token acquisition into a reusable utility/fixture that fetches a token once per test suite (or caches it with an expiry check) rather than re-authenticating before every single test — this both speeds up execution and mirrors how a real client application would behave. Credentials themselves should come from the same secure config/secrets layer used for DB and environment credentials (see Q36, Q61), never hardcoded in test code.

Q83 How do you test asynchronous, event-driven APIs backed by Kafka?

Kafka-backed flows typically can't be validated with a simple synchronous request/response assertion, since the API call often just triggers a message onto a topic and the real processing happens asynchronously downstream. The general pattern:

  1. Trigger — call the API/UI action that's expected to publish a Kafka event.
  2. Consume — use a test Kafka consumer (Karate has built-in Kafka support; in pure Java, a lightweight KafkaConsumer subscribed to the relevant topic) to listen for the resulting message.
  3. Poll with timeout — since processing is async, poll/await (not a fixed sleep) for the expected message to arrive within a reasonable timeout, then validate its payload.
  4. Cross-check downstream effects — confirm the consumer service that reads that topic actually processed it correctly (e.g. the resulting DB row, or a follow-up status change visible via a separate API call).
# Karate's built-in Kafka support (conceptual)
* def producer = karate.producer('localhost:9092')
* producer.send('booking-events', bookingId, bookingEventJson)

* def consumer = karate.consumer('localhost:9092', 'booking-events')
* def result = consumer.poll(5000)
* match result.value contains { bookingId: '#(bookingId)', status: 'CONFIRMED' }

Key testing considerations: message ordering guarantees (or lack thereof) per partition, idempotency (does reprocessing the same message cause duplicate side effects), and consumer lag/timeout handling — all of which matter a lot in banking-style event pipelines where a lost or duplicated message has real financial impact.

Scenario-Based Questions (10 Questions)

S1 Selenium tests pass locally but fail in Jenkins. What could be the reasons and how would you debug?

Likely causes: different browser/driver versions on the CI agent; headless vs headed execution differences (some elements behave differently, e.g. viewport size affecting visibility); missing environment variables/credentials on the agent; slower CI hardware exposing timing/race issues masked locally; different OS (Linux CI agent vs Windows/Mac local) causing font-rendering or file-path differences; network/firewall restrictions blocking calls that work from a local machine; stale cached dependencies on the agent.

Debugging approach: pull the CI console log, screenshot, and video/trace if captured; diff the config/environment values used locally vs in the pipeline; try running the exact same Maven command locally with -Dheadless=true to rule out headless-specific issues; check driver/browser version pinning; if still unclear, SSH into the agent (or use a matching Docker image) to reproduce directly in that environment.

S2 A test fails randomly 1 out of 10 times. How would you investigate the flakiness?

Run it in isolation with a high invocation count (@Test(invocationCount = 20)) to reproduce reliably. Check for: race conditions (missing wait before an assertion that depends on async data), shared/mutable test data colliding under parallel execution, order dependency on other tests, environment resource contention (CI agent under load causing timing shifts), and non-deterministic sort order from the backend (e.g. asserting on list order when the API doesn't guarantee it). Add detailed step-level logging around the suspected area and re-run until it fails again with logs in hand, rather than guessing blind.

S3 Login normally takes 2 seconds but sometimes takes 15 seconds. How would you design synchronization?

Use an explicit/fluent wait with a generous upper-bound timeout (e.g. 20s) tied to the actual success condition — not a fixed sleep — so the fast case (2s) doesn't waste time and the slow case (15s) doesn't fail prematurely:

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(20));
wait.until(ExpectedConditions.visibilityOfElementLocated(By.id("dashboardHeader")));

If the app itself is inconsistent, it's also worth flagging as a real performance issue to the dev team rather than only compensating for it in tests — a 7x variance in login time (2s → 15s) is often an application health signal, not just a test synchronization problem.

S4 100 Selenium tests take 2 hours. How would you reduce execution time?

  • Parallel execution — TestNG parallel="methods" with a higher thread-count, or sharding across multiple CI runners/nodes.
  • Remove Thread.sleep() and unnecessary fixed waits — often the single biggest time sink (see Q19).
  • Shift left where possible — replace some slow end-to-end UI tests with faster API-level tests that validate the same business logic (hybrid API+UI approach), reserving UI tests for genuine UI-critical flows.
  • Grid/Docker scaling — add more browser nodes so parallel threads aren't bottlenecked on a single Chrome instance queue.
  • Test suite segmentation — split into smoke (fast, runs every commit) vs full regression (runs nightly/on schedule) so the fast feedback loop isn't blocked on the full 2-hour run.
  • Optimize setup/teardown — reuse authenticated sessions via API login instead of UI login for tests where login itself isn't the thing under test.

S5 Database says APPROVED but the UI says PENDING. How would you investigate end-to-end?

  1. Confirm the DB state directly via a JDBC query (rule out the DB read itself being wrong) — cross-check against a second read (e.g. an admin API) if available.
  2. Check for caching — the UI might be reading from a cached layer (Redis, CDN, browser cache) that hasn't been invalidated after the DB update.
  3. Check for async/eventual consistency — if the backend uses a message queue (Kafka) to propagate status changes, there could be a processing delay or a failed/stuck consumer.
  4. Check the API layer directly (bypass the UI) — hit the status endpoint via REST Assured/Karate to see what the API itself returns; this isolates whether the bug is in backend propagation or frontend rendering.
  5. Check logs around the transition — look for errors in the service responsible for pushing status updates to the UI (webhook failure, retry exhaustion).
  6. Document the full chain (DB value → API value → UI value, with timestamps) in the defect report so developers can pinpoint exactly where the state diverges.

S6 How would you design automation for a banking transaction?

  • Hybrid API+UI validation — initiate/validate via UI for user-facing flows, but cross-check the actual money movement/state directly at the API and DB layers, since UI-only assertions aren't sufficient for financial correctness.
  • Test data isolation — every test run uses freshly generated account/transaction data (Builder + Faker) to avoid balance/state collisions across parallel runs, especially critical for money-related assertions.
  • Idempotency & rollback checks — verify duplicate submission doesn't double-charge, and that failed/partial transactions roll back cleanly.
  • Audit trail validation — assert that every transaction produces the expected audit/log entry (regulatory requirement in banking).
  • Boundary and negative testing — insufficient funds, exact-balance edge cases, currency rounding, daily transfer limits, concurrent transactions on the same account.
  • Reconciliation — compare source system vs downstream ledger/reporting system totals (ETL-style validation) to ensure no data is lost or duplicated in transit.
  • Security-adjacent checks — session timeout behavior, re-authentication for high-value transfers, masking of sensitive fields in logs/screenshots.

S7 How would you manage test data for a large automation framework?

  • Dynamic generation over static fixtures — Builder pattern + Faker library generates unique, realistic data per test run, avoiding collisions in parallel execution.
  • Test data isolation — each test creates and owns its own data rather than sharing a global fixture that other tests might mutate.
  • Cleanup strategy — @AfterMethod/@AfterSuite teardown deletes/resets created data, or tests run against an ephemeral/refreshable environment (e.g. a nightly-reset QA DB, or containerized DB snapshots).
  • Environment-appropriate strategy — synthetic generated data for lower environments, carefully masked/anonymized production-like data only where realism is essential and compliance allows it.
  • Centralized data builders/factories — a single source of truth for how a "valid customer," "valid loan application," etc. is constructed, so changes to required fields only need updating in one place.

S8 How would you design a framework supporting Chrome, Firefox, and Edge?

  • Driver abstraction — a DriverFactory that returns the correct WebDriver implementation based on a config/CLI parameter, so tests never reference a browser-specific class directly.
  • Capabilities/Options per browser — ChromeOptions, FirefoxOptions, EdgeOptions configured centrally (headless mode, window size, download preferences).
  • Cross-browser matrix in testng.xml — parameterized <test> blocks per browser, run in parallel, so the same suite executes against all three without duplicating test code.
  • Grid/Docker backing — a Selenium Grid (or Docker Compose setup, as in the EventHubSeleniumRestAssured project) with Hub + Chrome/Firefox/Edge nodes lets the matrix actually run in parallel across real browser instances rather than sequentially on one machine.
  • Browser-specific handling isolated — any unavoidable browser quirks (e.g. a slightly different wait needed for a Firefox rendering delay) are isolated behind the abstraction layer, not scattered through test code.

S9 How would you execute only failed tests after a regression run?

TestNG automatically generates a testng-failed.xml file in the test-output directory after any run containing failures, listing exactly the failed test methods/classes. Re-run just that file:

mvn test -DsuiteXmlFile=test-output/testng-failed.xml

# Or reference it directly in a CI re-run stage
mvn test -Dsurefire.suiteXmlFiles=test-output/testng-failed.xml

This is commonly wired into a Jenkins pipeline as an automatic "retry failed tests" post-build stage, distinct from the in-suite IRetryAnalyzer (Q38) — this is a full separate re-run pass, useful for a final confidence check before marking a release build red/green.
