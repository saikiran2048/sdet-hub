Q1. Write a program to test a RESTful API — auth, GET, POST, response validation

$ context — REST Assured is the de-facto Java library for this. Interviewers want to see: base setup, auth handling (bearer token from a login call), a GET with validation, a POST with a request body, and assertions on status/headers/body/schema.

Design: a reusable BaseTest that fetches an auth token once, and test methods that use it via RequestSpecification.

ApiTest.java
import io.restassured.RestAssured;
import io.restassured.response.Response;
import io.restassured.specification.RequestSpecification;
import org.testng.annotations.BeforeClass;
import org.testng.annotations.Test;
import static io.restassured.RestAssured.given;
import static org.hamcrest.Matchers.*;

public class ApiTest {

    private static String baseUrl = "https://api.example.com";
    private static String authToken;

    @BeforeClass
    public void setup() {
        RestAssured.baseURI = baseUrl;
        authToken = fetchAuthToken();
    }

    // Handles authentication once, reused across all tests
    private String fetchAuthToken() {
        Response response = given()
                .contentType("application/json")
                .body("{ \"username\": \"tester\", \"password\": \"secret\" }")
                .when()
                .post("/auth/login")
                .then()
                .statusCode(200)
                .extract().response();
        return response.jsonPath().getString("token");
    }

    private RequestSpecification authenticatedRequest() {
        return given()
                .header("Authorization", "Bearer " + authToken)
                .contentType("application/json");
    }

    @Test
    public void testGetUserById() {
        authenticatedRequest()
                .when()
                .get("/users/101")
                .then()
                .statusCode(200)
                .body("id", equalTo(101))
                .body("email", notNullValue())
                .body("status", equalTo("ACTIVE"))
                .time(lessThan(2000L)); // response time SLA
    }

    @Test
    public void testCreateUser() {
        String requestBody = "{ \"name\": \"John Doe\", \"email\": \"john@example.com\" }";

        authenticatedRequest()
                .body(requestBody)
                .when()
                .post("/users")
                .then()
                .statusCode(201)
                .header("Content-Type", containsString("application/json"))
                .body("id", notNullValue())
                .body("name", equalTo("John Doe"));
    }

    @Test
    public void testUnauthorizedAccessIsRejected() {
        given()
                .contentType("application/json")
                .when()
                .get("/users/101")   // no auth header
                .then()
                .statusCode(401);
    }
}
talking points to say out loud
  • Auth token fetched once in @BeforeClass, not per test — avoids hammering the login endpoint.
  • Negative case included (no token → 401) — interviewers specifically look for this.
  • In a real framework, extract baseUrl/credentials to a config file per environment (dev/QA/staging), and add JSON schema validation with matchesJsonSchemaInClasspath().

Q2. Designing a multi-step test case where each step's output feeds the next

$ context — Classic chained/dependent workflow: e.g. Create Order → Get Order ID → Make Payment → Verify Payment Status. Two things interviewers want: a way to carry state between steps, and correct failure handling so step 2 doesn't run garbage data if step 1 fails.

Two common designs:

  • TestNG dependsOnMethods — simplest, chains methods in a class in sequence, skips downstream steps automatically if an upstream step fails.
  • Shared "TestContext" object — cleaner for real frameworks; avoids tight coupling between test methods and works well with data-driven/parallel runs.
OrderFlowTest.java
public class OrderFlowTest {

    private String orderId;
    private String paymentId;

    @Test(priority = 1)
    public void createOrder() {
        Response response = given()
                .body("{ \"item\": \"laptop\", \"qty\": 1 }")
                .post("/orders");

        response.then().statusCode(201);
        orderId = response.jsonPath().getString("orderId");   // output feeds next step
        Assert.assertNotNull(orderId, "Order ID must be generated");
    }

    @Test(priority = 2, dependsOnMethods = "createOrder")
    public void makePayment() {
        Response response = given()
                .body("{ \"orderId\": \"" + orderId + "\", \"amount\": 999.00 }")
                .post("/payments");

        response.then().statusCode(200);
        paymentId = response.jsonPath().getString("paymentId");
        Assert.assertNotNull(paymentId);
    }

    @Test(priority = 3, dependsOnMethods = "makePayment")
    public void verifyOrderStatus() {
        given()
                .get("/orders/" + orderId)
                .then()
                .statusCode(200)
                .body("status", equalTo("PAID"))
                .body("paymentId", equalTo(paymentId));
    }
}
talking points to say out loud
  • dependsOnMethods auto-skips (not fails) downstream steps if createOrder fails — reports it accurately instead of a confusing cascade of failures.
  • For a bigger framework, swap instance fields for a ThreadLocal TestContext class (holds orderId, paymentId, etc.) so the flow is thread-safe under parallel execution.
  • Mention this pattern maps directly to real BDD scenarios you've written — each Cucumber step passing data forward via a shared Scenario Context/World object.

Q3. Mocking external dependencies (e.g. a database) in a test

$ context — Use Mockito to isolate the class under test from the real DB. Goal: test business logic in UserService without a live database — mock the UserRepository and stub its return value.
UserServiceTest.java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.util.Optional;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)
public class UserServiceTest {

    @Mock
    private UserRepository userRepository;   // fake DB layer, no real DB hit

    @InjectMocks
    private UserService userService;          // class under test, mock injected automatically

    @Test
    public void shouldReturnActiveUser_whenUserExistsInDb() {
        User fakeUser = new User(101, "John Doe", "ACTIVE");

        // Stub: whenever the DB is asked for user 101, return the fake user
        when(userRepository.findById(101)).thenReturn(Optional.of(fakeUser));

        User result = userService.getActiveUser(101);

        assertEquals("John Doe", result.getName());
        verify(userRepository, times(1)).findById(101);  // confirms DB call happened exactly once
    }

    @Test
    public void shouldThrowException_whenUserNotFound() {
        when(userRepository.findById(999)).thenReturn(Optional.empty());

        assertThrows(UserNotFoundException.class,
                () -> userService.getActiveUser(999));
    }

    @Test
    public void shouldThrowException_whenDbTimesOut() {
        // Simulating a DB failure without needing an actual DB outage
        when(userRepository.findById(101)).thenThrow(new DataAccessException("Connection timeout"));

        assertThrows(DataAccessException.class,
                () -> userService.getActiveUser(101));
    }
}
talking points to say out loud
  • @Mock creates a fake UserRepository; @InjectMocks wires it into UserService automatically — no Spring context needed, so the test runs in milliseconds.
  • Mocking lets you simulate failure scenarios (timeout, empty result) that are hard to reproduce reliably against a real DB.
  • Distinguish this from Testcontainers, which you'd use instead when you specifically want to test real SQL/DB interaction — mocking is for isolating business logic, Testcontainers is for integration-level DB testing.

Q4. Count pairs in an array whose sum is divisible by k

Inputarr = [5, 9, 36, 74, 52, 31, 42], k = 3
Output7

Key insight: two numbers' sum is divisible by k only if their remainders (mod k) add up to k (or both remainders are 0). So instead of checking every pair (O(n²)), count how many elements fall in each remainder bucket, then combine buckets mathematically — O(n).

PairsDivisibleByK.java
public class PairsDivisibleByK {

    public static int countPairs(int[] arr, int k) {
        int[] remainderCount = new int[k];

        // Step 1: bucket every element by its remainder mod k
        for (int num : arr) {
            remainderCount[num % k]++;
        }

        int pairCount = 0;

        // Step 2: remainder 0 pairs with itself -> nC2
        pairCount += (remainderCount[0] * (remainderCount[0] - 1)) / 2;

        // Step 3: remainder r pairs with remainder (k - r)
        int i = 1, j = k - 1;
        while (i < j) {
            pairCount += remainderCount[i] * remainderCount[j];
            i++;
            j--;
        }

        // Step 4: if k is even, the middle remainder (k/2) pairs with itself
        if (k % 2 == 0) {
            pairCount += (remainderCount[k / 2] * (remainderCount[k / 2] - 1)) / 2;
        }

        return pairCount;
    }

    public static void main(String[] args) {
        int[] arr = {5, 9, 36, 74, 52, 31, 42};
        System.out.println(countPairs(arr, 3)); // 7
    }
}
Time: O(n + k) Space: O(k)
talking points to say out loud
  • Walk through the trace for the given input: remainders mod 3 → 5%3=2, 9%3=0, 36%3=0, 74%3=2, 52%3=1, 31%3=1, 42%3=0. Buckets: {0:3, 1:2, 2:2}.
  • Remainder-0 pairs: C(3,2) = 3. Remainder(1,2) pairs: 2×2 = 4. Total = 7 ✅ matches expected output.
  • If asked for a brute-force fallback first: nested loop checking (arr[i]+arr[j]) % k == 0, O(n²) — mention it, then optimize to the bucket approach to show you can improve on your own first pass.

Q5. Move all zeroes to the end, in place, O(1) extra space

Input[0, 1, 0, 3, 12]
Output[1, 3, 12, 0, 0]

Approach: two-pointer / "write pointer" technique. Walk through the array with a read pointer; whenever you find a non-zero, swap it into the next write position. Everything after the write pointer naturally ends up zero.

MoveZeroes.java
import java.util.Arrays;

public class MoveZeroes {

    public static void moveZeroes(int[] nums) {
        int writeIndex = 0;

        // Pass 1: shift all non-zero elements to the front, preserving order
        for (int readIndex = 0; readIndex < nums.length; readIndex++) {
            if (nums[readIndex] != 0) {
                int temp = nums[writeIndex];
                nums[writeIndex] = nums[readIndex];
                nums[readIndex] = temp;
                writeIndex++;
            }
        }
        // Everything from writeIndex onward is already 0 (or gets overwritten to 0
        // above via the swap) — no second pass needed since we swap instead of overwrite.
    }

    public static void main(String[] args) {
        int[] nums = {0, 1, 0, 3, 12};
        moveZeroes(nums);
        System.out.println(Arrays.toString(nums)); // [1, 3, 12, 0, 0]
    }
}
Time: O(n) Space: O(1)
talking points to say out loud
  • Using a swap instead of just overwriting with 0 means you don't need a second cleanup loop — the zero naturally gets carried backward into readIndex's old spot.
  • Relative order of non-zero elements is preserved because both pointers only ever move forward.
  • Common follow-up: "what if you couldn't use swap?" → overwrite non-zeros as you go, track writeIndex, then fill everything from writeIndex to end with 0 in a second pass. Still O(n) time, O(1) space.

Q10. Return elements that appear at least twice, in the order they first became duplicates

Input[4, 3, 2, 7, 8, 2, 3, 1]
Output[2, 3]

Approach: a HashSet to track "already seen" values, and a separate result list. The moment an element is seen for the second time, add it to the result — this naturally captures the order in which elements first became duplicates.

FirstDuplicatesInOrder.java
import java.util.*;

public class FirstDuplicatesInOrder {

    public static List findDuplicatesInOrder(int[] nums) {
        Set seenOnce = new HashSet<>();
        Set alreadyFlagged = new HashSet<>(); // avoid re-adding on 3rd, 4th occurrence
        List result = new ArrayList<>();

        for (int num : nums) {
            if (!seenOnce.add(num)) {
                // add() returns false if num was already in the set -> this is a repeat
                if (alreadyFlagged.add(num)) {
                    result.add(num); // first time we detect it's a duplicate
                }
            }
        }
        return result;
    }

    public static void main(String[] args) {
        int[] nums = {4, 3, 2, 7, 8, 2, 3, 1};
        System.out.println(findDuplicatesInOrder(nums)); // [2, 3]
    }
}
Time: O(n) Space: O(n)
talking points to say out loud
  • Set.add() returning a boolean is the trick that avoids a separate contains() check — one hash lookup instead of two.
  • The second set (alreadyFlagged) prevents duplicate entries in the result if a number appears 3+ times.
  • If asked for a LinkedHashMap-based alternative (counting occurrences, then filtering by insertion order) — mention it as a valid variant, but the two-set approach is cleaner and single-pass.

Q6. How do you handle a blocker in testing, and what strategies help overcome it?

My approach, in order:

  • Isolate and confirm — reproduce the blocker consistently before raising it, so it's not a flaky/false alarm (env issue, stale test data, wrong config).
  • Classify it — is it an environment issue, a missing test data/API dependency, a genuine application defect, or an access/permission issue? Each needs a different owner.
  • Communicate early — flag it in standup/Slack immediately with impact (which test cases/sprint goals are affected), not after sitting on it for a day.
  • Unblock in parallel — while waiting on the actual fix, work around it: mock the dependency, stub the API response, or reorder my test execution to cover unaffected areas first, so I'm never fully idle.
  • Track it formally — log it as a defect/blocker ticket with severity, so it's visible in the sprint board and doesn't silently slip.
analogy A blocker in testing is like hitting a closed road on a delivery route. You don't just sit at the barrier — you confirm it's actually closed, radio it in immediately so dispatch knows, and reroute through side streets to keep delivering the packages you can, while the main road gets fixed in parallel.

Q7. What strategy do you follow when starting a new project to ensure effective test coverage?

  • Understand the domain and requirements first — read specs/user stories, talk to BA/dev, identify critical business flows vs. edge flows (in BFSI: payment processing, loan disbursal, reconciliation are always P0).
  • Risk-based prioritization — map coverage effort to business risk and usage frequency, not just "test everything equally."
  • Define the test pyramid for the project — heavy unit/API coverage at the base, focused UI/E2E coverage at the top for the critical user journeys only.
  • Traceability matrix — map every requirement to at least one test case, so coverage gaps are visible, not assumed.
  • Environment & data strategy — decide test data approach (synthetic vs. masked prod data) and environment stability early, since this blocks everything downstream.
  • Automation-readiness assessment — decide what gets automated from day one vs. manually validated first (new/unstable features), and set up CI integration early rather than bolting it on later.
analogy It's like building a house: you don't start painting walls (UI automation) before the foundation is poured and inspected (API/unit coverage, environment stability, requirement traceability). Skipping that order means expensive rework later.

Q8. What is the shift-left approach, and a real scenario where it helped?

Definition: shift-left means moving testing activities earlier in the SDLC — involving QA at requirements/design stage instead of waiting for a "code-complete" build, so defects are caught before they're expensive to fix.

Real scenario: On the GM Financial engagement, instead of waiting for the full UI build to test a loan servicing notification flow, I got involved at the API contract design stage — reviewing the request/response schema with the dev team, writing API-level automated tests (REST Assured) against the API spec/mocked service before the UI even existed, and flagging a data-type mismatch in the notification payload (date format inconsistency between service and consumer) two weeks before UI testing would have caught it.

analogy Shift-left is like getting a routine health checkup instead of waiting until you're in the ER. Catching a problem at a checkup (requirements/design review) costs you 20 minutes; catching the same problem in the ER (post-release production bug) costs days of surgery and recovery — same underlying issue, wildly different cost depending on when you catch it.

Q9. Bugs encountered while implementing shift-left — how did you handle them?

Shift-left introduces its own class of problems, since you're testing against things that aren't fully finished yet:

  • Mocked responses drifting from the real API — early API tests were written against a mocked/contract-first spec; once the real service was deployed, a field the mock always returned turned out to be optional in reality, and my assertions were too strict. Fixed by making the mock a shared, versioned contract (updated alongside the real API) instead of something I maintained independently.
  • Flaky early-integration environments — testing against a service still under active development meant intermittent failures unrelated to real bugs. Handled by clearly separating "environment instability" from "test failure" in reporting, and retry-with-logging so genuine regressions weren't lost in the noise.
  • False sense of coverage — early API-level green checks sometimes masked UI-layer integration issues (e.g. how the frontend actually consumed a date field). Addressed by keeping a thin but real E2E layer on top, specifically for the highest-risk user journeys, rather than assuming API-green meant feature-done.
analogy It's like proofreading a book chapter-by-chapter as the author writes it, instead of waiting for the finished manuscript. You catch typos early — but you can also flag a plot hole based on an outline that changes before publication. The fix isn't to stop proofreading early; it's to keep syncing your notes against the latest draft instead of trusting your first read.
