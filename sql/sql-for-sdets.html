02foundations·SELECT · WHERE · ORDER BYbeginner

Reading data: the SELECT statement

Every query is a sentence: which columns, from where, filtered how, sorted how. Using the banking schema:

01_basic_select.sql
SELECT full_name, city, credit_score
FROM customers
WHERE credit_score >= 700
ORDER BY credit_score DESC
LIMIT 2;
result
full_namecitycredit_score
Meera IyerChennai820
Ravi TejaHyderabad780

Filtering operators you'll use daily

Comparison

= <> > < >= <= — standard comparisons. <> or != means "not equal".

BETWEEN

credit_score BETWEEN 600 AND 800 — inclusive range, cleaner than two AND conditions.

IN

status IN ('APPROVED','CLOSED') — matches any value in a list, replaces chained OR.

LIKE

full_name LIKE 'Ka%' — pattern match. % = any characters, _ = exactly one character.

IS NULL / IS NOT NULL

Never use = NULL — NULL means "unknown", so it never equals anything, even another NULL.

DISTINCT

SELECT DISTINCT city FROM customers — removes duplicate rows from the result.

02_filters.sql
-- loans that are still active or under review
SELECT loan_id, customer_id, loan_amount, status
FROM loans
WHERE status IN ('APPROVED', 'PENDING')
  AND loan_amount BETWEEN 100000 AND 600000;

-- loans that were never disbursed (still NULL)
SELECT loan_id, status FROM loans WHERE disbursed_date IS NULL;

-- customers whose name starts with 'Ka'
SELECT full_name FROM customers WHERE full_name LIKE 'Ka%';
Interview trap

"Write a query to find rows where a column is NULL" — candidates often write WHERE column = NULL, which silently returns zero rows every time. The correct form is always IS NULL / IS NOT NULL.

03foundations·aggregates & GROUP BY / HAVINGbeginner

Turning many rows into one number

Aggregate functions collapse a set of rows into a single summary value: COUNT, SUM, AVG, MIN, MAX. GROUP BY tells SQL to do that separately per bucket, and HAVING filters those buckets.

03_aggregates.sql
-- total balance and account count per customer
SELECT customer_id,
       COUNT(*)      AS num_accounts,
       SUM(balance)  AS total_balance,
       AVG(balance)  AS avg_balance,
       MAX(balance)  AS highest_balance
FROM accounts
GROUP BY customer_id
HAVING SUM(balance) > 10000
ORDER BY total_balance DESC;
result
customer_idnum_accountstotal_balanceavg_balancehighest_balance
31305000.00305000.00305000.00
12167000.0083500.00125000.00
Why HAVING and not WHERE

WHERE filters individual rows before grouping happens. HAVING filters groups after aggregation. You cannot write WHERE SUM(balance) > 10000 — at that point in execution, SUM doesn't exist yet. This is one of the most common SDET interview questions.

MySQL logical execution order (know this cold)

OrderClauseWhat it does
1FROM / JOINBuild the working set of rows
2WHEREFilter individual rows
3GROUP BYBucket rows into groups
4HAVINGFilter groups
5SELECTCompute output columns / aliases
6ORDER BYSort the final result
7LIMITTrim to N rows

This is exactly why you can ORDER BY a column alias, but you can't WHERE on one — the alias doesn't exist until step 5.

04the core skill·JOINS — explained from zerobeginner → advanced

JOINS: the one concept that shows up in every interview

Forget SQL syntax for a second. A join answers one plain-English question: "I have two separate lists — how do I combine rows that are related to each other?" Think of customers and loans as two spreadsheets. Every loan row has a customer_id that points back to a customer. A join is simply: "for every loan, go find and attach the matching customer."

The one rule to remember

A join always needs a shared column to match on — usually a primary key in one table (customer_id in customers) and a foreign key in the other (customer_id in loans). The join type only decides what happens when a match isn't found.

INNER JOIN

Only rows that match in both tables. No match = row disappears entirely.

LEFT JOIN

Every row from the left table, plus matches from the right. No match → right columns are NULL.

RIGHT JOIN

Every row from the right table, plus matches from the left. Mirror image of LEFT JOIN.

FULL OUTER JOIN

Everything from both sides. Unmatched rows on either side get NULLs for the other table. (Not native in MySQL — emulated with UNION.)

CROSS JOIN

Every row of A paired with every row of B. No matching column at all — pure cartesian product.

SELF JOIN

A table joined to itself, e.g. matching each employee to their own manager in the same table.

INNER JOIN — banking example

Get every loan alongside the customer's name and city. Customers with no loan row simply won't appear.

04_inner_join.sql
SELECT c.full_name, c.city, l.loan_amount, l.status
FROM customers AS c
INNER JOIN loans AS l
  ON c.customer_id = l.customer_id
ORDER BY l.loan_amount DESC;

The anti-join pattern: finding rows with NO match

Flip the LEFT JOIN idea around by filtering for the NULLs — this is one of the most-used real-world queries in data validation and reconciliation testing.

06_anti_join.sql
-- customers who have never taken a loan
SELECT c.full_name
FROM customers c
LEFT JOIN loans l ON c.customer_id = l.customer_id
WHERE l.loan_id IS NULL;
-- → Karthik Nair

-- same idea on the e-commerce schema: customers who never ordered
SELECT ec.name
FROM ec_customers ec
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.cust_id = ec.cust_id
);
-- → Sanjay

RIGHT JOIN and FULL OUTER JOIN

07_right_and_full.sql
-- RIGHT JOIN: same as LEFT JOIN with tables swapped — rarely used in practice
SELECT c.full_name, l.loan_id
FROM loans l
RIGHT JOIN customers c ON l.customer_id = c.customer_id;

-- FULL OUTER JOIN: MySQL has no native FULL JOIN — emulate with UNION
SELECT c.full_name, l.loan_id FROM customers c LEFT JOIN loans l ON c.customer_id = l.customer_id
UNION
SELECT c.full_name, l.loan_id FROM customers c RIGHT JOIN loans l ON c.customer_id = l.customer_id;

SELF JOIN — an employee and their own manager

The trick with self joins: you're joining one table to itself, so you must alias it twice to treat it as "two different tables" in your head.

08_self_join.sql
SELECT e.emp_name AS employee, m.emp_name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id;

CROSS JOIN

No ON clause — every row pairs with every row. Genuinely useful for generating combinations, e.g. "every product against every discount tier" for test data generation.

09_cross_join.sql
SELECT p.name, d.tier
FROM products p
CROSS JOIN (SELECT 'BRONZE' AS tier UNION ALL SELECT 'SILVER' UNION ALL SELECT 'GOLD') d;
-- 4 products × 3 tiers = 12 rows, every combination

Chaining three or more tables

Real queries almost always join more than two tables. Order of joins doesn't change the logical result — the optimizer decides execution order.

10_multi_join.sql
-- every order with customer name and product name and line total
SELECT ec.name AS customer, p.name AS product, o.qty, (o.qty * p.price) AS line_total
FROM orders o
JOIN ec_customers ec ON o.cust_id = ec.cust_id
JOIN products p     ON o.product_id = p.product_id
ORDER BY line_total DESC;
Interview trap: ON vs WHERE with outer joins

With a LEFT JOIN, putting a filter on the right table in WHERE silently turns it back into an INNER JOIN, because unmatched rows have NULL there and fail the WHERE condition. If you want to filter the right table without losing unmatched left rows, put that condition inside the ON clause instead: LEFT JOIN loans l ON c.customer_id = l.customer_id AND l.status = 'APPROVED'.

Avoid in real code

NATURAL JOIN auto-matches on any identically-named columns across tables. MySQL supports it, but it's dangerous in production queries — if someone adds an unrelated column with the same name later, the join silently changes behavior. Always use an explicit ON.

05intermediate·subqueriescore

A query inside a query

A subquery is just a SELECT nested inside another SELECT, INSERT, UPDATE, or DELETE. Use it when you need a value or a set of values before you can finish the outer question.

Scalar subquery

Returns exactly one value. Can be used anywhere a single value is expected.

Row / column subquery

Returns a list — used with IN, ANY, ALL.

Correlated subquery

References a column from the outer query — re-evaluated once per outer row. Powerful, but can be slow.

Non-correlated subquery

Runs independently of the outer query — evaluated once.

11_subqueries.sql
-- scalar subquery: customers with an above-average credit score
SELECT full_name, credit_score
FROM customers
WHERE credit_score > (SELECT AVG(credit_score) FROM customers);

-- non-correlated: customers who have at least one APPROVED loan
SELECT full_name FROM customers
WHERE customer_id IN (SELECT customer_id FROM loans WHERE status = 'APPROVED');

-- correlated: each customer's own highest loan amount, next to every loan row
SELECT l.loan_id, l.customer_id, l.loan_amount,
  (SELECT MAX(l2.loan_amount) FROM loans l2 WHERE l2.customer_id = l.customer_id) AS customer_max
FROM loans l;

-- subquery in FROM (a "derived table") — must always be aliased
SELECT t.city, t.avg_score
FROM (
  SELECT city, AVG(credit_score) AS avg_score
  FROM customers GROUP BY city
) AS t
WHERE t.avg_score > 650;
Interview question

"When would you use a subquery instead of a JOIN?" — Use a subquery in WHERE/EXISTS when you only need to filter, not pull columns from the other table. Use a JOIN when you need columns from both tables in the output. Correlated subqueries are logically equivalent to joins but often perform worse, since they can re-run once per outer row instead of once per join.

06intermediate·CTEs & recursive queriescore

Common Table Expressions (WITH clause)

A CTE is a named, temporary result set that only exists for the duration of one query. Think of it as giving a subquery a name so the rest of the query can read like plain English.

12_cte_basic.sql
WITH high_value_loans AS (
  SELECT customer_id, loan_amount
  FROM loans
  WHERE loan_amount > 250000
)
SELECT c.full_name, h.loan_amount
FROM high_value_loans h
JOIN customers c ON c.customer_id = h.customer_id;

CTEs really shine when chained — each one builds on the last, replacing what would otherwise be deeply nested subqueries:

13_cte_chained.sql
WITH per_customer AS (
  SELECT customer_id, SUM(loan_amount) AS total_borrowed
  FROM loans GROUP BY customer_id
),
ranked AS (
  SELECT customer_id, total_borrowed,
    RANK() OVER (ORDER BY total_borrowed DESC) AS borrow_rank
  FROM per_customer
)
SELECT c.full_name, r.total_borrowed, r.borrow_rank
FROM ranked r JOIN customers c ON c.customer_id = r.customer_id;

Recursive CTE — walking a hierarchy

Recursive CTEs solve the exact problem a self join can't: arbitrary-depth hierarchies (org charts, category trees). It has an "anchor" (the starting point) and a "recursive" part that keeps joining back to itself.

14_recursive_cte.sql
WITH RECURSIVE org_chain AS (
  -- anchor: top-level people (no manager)
  SELECT emp_id, emp_name, manager_id, 1 AS depth
  FROM employees WHERE manager_id IS NULL

  UNION ALL

  -- recursive step: find employees reporting to anyone already in org_chain
  SELECT e.emp_id, e.emp_name, e.manager_id, oc.depth + 1
  FROM employees e
  JOIN org_chain oc ON e.manager_id = oc.emp_id
)
SELECT * FROM org_chain ORDER BY depth;
SDET in practice

Recursive CTEs are the go-to when validating hierarchical test data — approval-chain workflows in banking apps (maker-checker-approver), category trees in e-commerce catalogs, or nested test-suite dependencies.

07intermediate·window functionssenior-level

Window functions: aggregate without collapsing rows

GROUP BY collapses rows into one per bucket. A window function calculates across a group of related rows ("the window") but keeps every original row intact — this is what makes ranking, running totals, and row-to-row comparisons possible.

FunctionPurpose
ROW_NUMBER()Unique sequential number per row within a partition — no ties
RANK()Same rank for ties, but skips the next number(s)
DENSE_RANK()Same rank for ties, no gaps in the sequence
LAG() / LEAD()Value from the previous / next row
SUM() OVER(...)Running total / cumulative sum
NTILE(n)Splits rows into n roughly equal buckets
15_window_ranking.sql
-- rank employees by salary within each department
SELECT emp_name, dept_id, salary,
  ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS row_num,
  RANK()       OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS dense_rnk
FROM employees
WHERE dept_id IS NOT NULL;

Interview question: Nth highest salary

This is asked constantly. The window-function answer is short and handles ties correctly, unlike the old LIMIT/OFFSET trick:

16_nth_highest.sql
SELECT emp_name, salary FROM (
  SELECT emp_name, salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = 2;  -- 2nd highest salary overall

Running totals and row comparisons

17_running_total_lag.sql
-- running total of order value per customer, and gap from previous order
SELECT ec.name, o.order_date, (o.qty * p.price) AS order_value,
  SUM(o.qty * p.price) OVER (PARTITION BY o.cust_id ORDER BY o.order_date) AS running_total,
  LAG(o.qty * p.price) OVER (PARTITION BY o.cust_id ORDER BY o.order_date) AS previous_order_value
FROM orders o
JOIN ec_customers ec ON o.cust_id = ec.cust_id
JOIN products p     ON o.product_id = p.product_id
ORDER BY ec.name, o.order_date;
SDET in practice

Window functions are exactly how you validate "top N per group" business rules in test automation — e.g. asserting the API's "top 3 products per category" widget matches a DENSE_RANK query against the same database, instead of hardcoding expected values.

08intermediate·set operationscore

UNION, UNION ALL, INTERSECT, EXCEPT

Set operations stack the results of two SELECT statements vertically instead of joining them side by side. Both SELECTs need the same number of columns, in compatible types.

UNION

Combines results and removes duplicate rows. Slightly slower — it has to check for dupes.

UNION ALL

Combines results and keeps duplicates. Faster — always prefer this when you know there won't be overlaps, or don't care.

INTERSECT

Rows that appear in both result sets. (MySQL 8.0.31+)

EXCEPT

Rows in the first result set that are not in the second. (MySQL 8.0.31+)

18_set_ops.sql
-- all cities that have either a customer or appear as a loan disbursal region (example combine)
SELECT city FROM customers
UNION
SELECT 'Pune' AS city; -- dupes removed automatically

-- customers who are in BOTH the "has a loan" and "has an account" sets
SELECT customer_id FROM loans
INTERSECT
SELECT customer_id FROM accounts;

-- customers with an account but NO loan at all
SELECT customer_id FROM accounts
EXCEPT
SELECT customer_id FROM loans;
Older MySQL versions

Before MySQL 8.0.31, INTERSECT/EXCEPT don't exist — emulate with JOIN (for intersect) or LEFT JOIN ... WHERE ... IS NULL / NOT IN (for except). Many production banking systems still run older MySQL, so know both approaches.

09data & schema·DML — insert / update / deletebeginner

Changing data: INSERT, UPDATE, DELETE

DML = Data Manipulation Language. These are the statements you'll run constantly to set up and tear down test data.

19_dml.sql
-- INSERT a single row
INSERT INTO customers (full_name, city, credit_score) VALUES ('Test User QA', 'Pune', 700);

-- UPDATE — always pair with a WHERE, or every row changes
UPDATE accounts SET balance = balance + 5000 WHERE account_id = 3;

-- DELETE — same warning applies
DELETE FROM loans WHERE status = 'REJECTED';

-- UPSERT in MySQL: insert, or update if the unique/primary key already exists
INSERT INTO accounts (account_id, customer_id, account_type, balance)
VALUES (3, 2, 'SAVINGS', 9000.00)
ON DUPLICATE KEY UPDATE balance = VALUES(balance);
The most expensive typo in SQL

Running UPDATE or DELETE without a WHERE clause applies it to every row in the table. Always run the equivalent SELECT ... WHERE ... first to confirm exactly which rows you're about to touch, especially against a shared test environment.

10data & schema·DDL & constraintsbeginner

Defining structure: CREATE, ALTER, DROP, TRUNCATE

DDL = Data Definition Language — it shapes the tables themselves, not the rows in them.

20_ddl.sql
ALTER TABLE customers ADD COLUMN email VARCHAR(100) UNIQUE;
ALTER TABLE customers MODIFY COLUMN credit_score INT NOT NULL DEFAULT 600;
ALTER TABLE customers DROP COLUMN email;

TRUNCATE TABLE loans;   -- wipes ALL rows instantly, resets AUTO_INCREMENT, can't be rolled back, skips triggers
DROP TABLE loans;      -- removes the table structure itself, gone entirely
ConstraintWhat it guarantees
PRIMARY KEYUniquely identifies each row; implies NOT NULL + UNIQUE
FOREIGN KEYValue must exist in the referenced table's key — enforces referential integrity
UNIQUENo two rows can share this value (NULLs are allowed, and don't conflict with each other)
NOT NULLColumn can never be empty/unknown
CHECKValue must satisfy a boolean condition, e.g. credit_score BETWEEN 300 AND 900
DEFAULTValue used automatically when none is supplied on INSERT
AUTO_INCREMENTMySQL generates the next sequential integer automatically
Interview question: DELETE vs TRUNCATE vs DROP

DELETE is DML, removes rows one at a time (optionally filtered), fires triggers, and can be rolled back inside a transaction. TRUNCATE is DDL, removes all rows at once by deallocating pages, is much faster, resets auto-increment, and in MySQL commits implicitly. DROP removes the table definition entirely — the table no longer exists.

11data & schema·indexes & query optimizationsenior-level

Making queries fast, and proving it with EXPLAIN

An index is a separate, sorted lookup structure (usually a B-Tree) that lets MySQL find rows without scanning the whole table. The tradeoff: indexes speed up reads but slow down writes, since every INSERT/UPDATE/DELETE has to maintain them too.

21_indexes.sql
CREATE INDEX idx_loans_customer ON loans(customer_id);
CREATE UNIQUE INDEX idx_customers_email ON customers(email);
CREATE INDEX idx_loans_status_amount ON loans(status, loan_amount); -- composite index

EXPLAIN SELECT * FROM loans WHERE customer_id = 2;
EXPLAIN output — what to look for
columnmeaning
typeALL = full table scan (bad) → ref/range (good) → const/eq_ref (best)
keywhich index MySQL actually chose to use (NULL = none used)
rowsestimated rows MySQL expects to examine — lower is better
Extra"Using filesort" or "Using temporary" are red flags worth investigating

Practical rules of thumb

Index foreign keys

Columns used in JOIN conditions almost always deserve an index.

Leftmost prefix rule

A composite index on (status, loan_amount) helps queries filtering on status alone, or status+loan_amount — but not loan_amount alone.

Don't over-index

Every index adds write overhead. Index what you actually query on, not every column.

SDET in practice

Performance/API test suites often assert on response time SLAs. When an endpoint suddenly slows down, EXPLAIN on the underlying query is usually the fastest way to prove — in a bug report — whether it's an application issue or a missing index, rather than guessing.

12data & schema·transactions & ACIDcore

Transactions: making multiple changes act as one

A transaction groups statements so they all succeed together, or all fail together — critical in banking systems where "debit one account, credit another" can never be allowed to happen halfway.

Atomicity

All statements in the transaction succeed, or none do.

Consistency

The database moves from one valid state to another — constraints are never violated.

Isolation

Concurrent transactions don't see each other's uncommitted changes.

Durability

Once committed, the change survives a crash — it's written to disk.

22_transaction.sql
START TRANSACTION;

UPDATE accounts SET balance = balance - 10000 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 10000 WHERE account_id = 3;

-- if anything looks wrong, undo everything since START TRANSACTION
ROLLBACK;

-- otherwise, make it permanent
COMMIT;

SDET in practice

Wrapping each automated test in START TRANSACTION / ROLLBACK (instead of DELETE-based cleanup) is a common pattern for keeping integration tests fast and side-effect-free against a shared database.

Reusable database logic

Views — a saved, reusable query

A view looks like a table but is really a stored SELECT — it always reflects live data, with no storage of its own.

23_view.sql
CREATE VIEW active_loans_view AS
SELECT c.full_name, l.loan_amount, l.status
FROM customers c JOIN loans l ON c.customer_id = l.customer_id
WHERE l.status = 'APPROVED';

SELECT * FROM active_loans_view; -- query it exactly like a table

Stored procedures — packaged logic

24_procedure.sql
DELIMITER $$
CREATE PROCEDURE get_customer_loans(IN cust_id INT)
BEGIN
  SELECT * FROM loans WHERE customer_id = cust_id;
END$$
DELIMITER ;

CALL get_customer_loans(1);

Triggers — logic that fires automatically

25_trigger.sql
CREATE TRIGGER trg_prevent_negative_balance
BEFORE UPDATE ON accounts
FOR EACH ROW
BEGIN
  IF NEW.balance < -5000 THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Balance cannot go below overdraft limit';
  END IF;
END;
Testing implication

Triggers and stored procedures hide business logic inside the database itself, invisible to your application code and your API tests. When validating data, be aware some values may be computed or blocked by trigger logic — not just by the application layer you're automating against.

14data & schema·normalizationcore

Normalization: designing tables that don't lie to you

Normalization removes redundant data so an update in one place can't leave stale, contradicting copies elsewhere.

FormRuleFixes
1NFEvery column holds one atomic value; no repeating groups"Products: Mouse, Keyboard" in one cell → split into separate rows
2NF1NF + every non-key column depends on the whole primary keyIn a composite key (order_id, product_id), a column like "product_name" that only depends on product_id gets moved out
3NF2NF + no non-key column depends on another non-key columnStoring both "city" and "state" when state is derivable from city → move to a separate lookup table
BCNFStricter version of 3NF for edge cases with overlapping candidate keysRare in interviews beyond a mention
Interview question

"Why would you ever denormalize?" — Read-heavy reporting/analytics systems sometimes intentionally duplicate data (e.g. storing a customer's city directly on every order row) to avoid expensive joins at query time. It's a deliberate tradeoff: faster reads, at the cost of update complexity and potential inconsistency — common in data warehouses, not in transactional banking systems.

Where SQL actually shows up in your framework

This is the part that separates "I know SQL" from "I use SQL to make automation trustworthy." Four recurring patterns:

1. Back-end assertion after a UI/API action

After a Karate/Playwright flow submits a loan application, don't just assert the API's 200 response — assert the row actually landed correctly in the database.

LoanDbAssertion.java
public class LoanDbValidator {
    public static Map<String, Object> getLoanById(int loanId) throws SQLException {
        String sql = "SELECT * FROM loans WHERE loan_id = ?";
        try (Connection conn = DriverManager.getConnection(DB_URL, USER, PASS);
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setInt(1, loanId);
            try (ResultSet rs = ps.executeQuery()) {
                rs.next();
                Map<String, Object> row = new HashMap<>();
                row.put("status", rs.getString("status"));
                row.put("loan_amount", rs.getBigDecimal("loan_amount"));
                return row;
            }
        }
    }
}
// assert row.get("status").equals("APPROVED") — trust the database, not just the API response body

3. Source-vs-target reconciliation (ETL / migration / Kafka testing)

When events flow from an app → Kafka → a downstream database (a pattern in your Kafka+Karate work), the real test is: did every message that went in actually land correctly on the other side?

26_reconciliation.sql
-- count mismatch check: row counts must match between source and target
SELECT (SELECT COUNT(*) FROM source_db.loans) AS source_count,
       (SELECT COUNT(*) FROM target_db.loans) AS target_count;

-- find rows present in source but missing in target (classic anti-join)
SELECT s.loan_id
FROM source_db.loans s
LEFT JOIN target_db.loans t ON s.loan_id = t.loan_id
WHERE t.loan_id IS NULL;

-- find rows that exist on both sides but with different values (data-drift check)
SELECT s.loan_id, s.status AS source_status, t.status AS target_status
FROM source_db.loans s
JOIN target_db.loans t ON s.loan_id = t.loan_id
WHERE s.status <> t.status OR s.loan_amount <> t.loan_amount;

4. Test data setup, teardown, and isolation

Seed once per suite

Load a known dataset in @BeforeSuite/CI pipeline step, so results are deterministic across Jenkins runs.

Transaction rollback per test

START TRANSACTION before, ROLLBACK after — the fastest way to keep tests independent without full re-seeding.

Idempotent seed scripts

Use ON DUPLICATE KEY UPDATE or TRUNCATE + re-insert so the same script can run safely on every pipeline execution.

The question senior SDET interviews actually ask

Not "write me a join." More often: "How would you validate that 10,000 records migrated correctly from a legacy system to a new one?" The strong answer covers: row-count parity, checksum/hash comparison per row (not column-by-column diffing at scale), anti-joins for missing/extra rows, and sampling + full reconciliation for high-value records (e.g. loans above a threshold) rather than relying on manual spot checks.

20 questions worth rehearsing out loud

1. Find the second highest salary without using LIMIT/OFFSET 
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
2. Find duplicate rows in a table 
SELECT full_name, city, COUNT(*)
FROM customers
GROUP BY full_name, city
HAVING COUNT(*) > 1;
3. Delete duplicate rows, keeping only the lowest id 
DELETE c1 FROM customers c1
JOIN customers c2
  ON c1.full_name = c2.full_name AND c1.city = c2.city AND c1.customer_id > c2.customer_id;
4. Department-wise top 2 earners 
SELECT * FROM (
  SELECT emp_name, dept_id, salary,
    DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
  FROM employees
) t WHERE rnk <= 2;
5. Customers who placed orders in every month they had activity (no gaps)

Compare COUNT(DISTINCT MONTH(order_date)) against the span between MIN and MAX month for that customer — if they're equal, there are no gaps.

6. Difference between WHERE and HAVING

WHERE filters rows before grouping/aggregation; HAVING filters groups after aggregation. WHERE can't reference an aggregate function result — HAVING can.

7. Difference between UNION and JOIN

JOIN combines columns from two tables side-by-side based on a related key. UNION stacks two result sets vertically — both need the same column count/types, and there's no "matching" involved at all.

8. Difference between CHAR and VARCHAR

CHAR(n) always stores exactly n characters, padding shorter values with spaces — faster for fixed-length data. VARCHAR(n) stores only the actual characters used plus a small length prefix — more storage-efficient for variable-length text.

9. Find employees who earn more than their manager 
SELECT e.emp_name AS employee, e.salary, m.emp_name AS manager, m.salary AS manager_salary
FROM employees e
JOIN employees m ON e.manager_id = m.emp_id
WHERE e.salary > m.salary;
10. Pivot rows into columns (e.g. loan status counts as columns) 
SELECT
  SUM(CASE WHEN status = 'APPROVED' THEN 1 ELSE 0 END) AS approved,
  SUM(CASE WHEN status = 'PENDING'  THEN 1 ELSE 0 END) AS pending,
  SUM(CASE WHEN status = 'REJECTED' THEN 1 ELSE 0 END) AS rejected
FROM loans;
11. What is a CASE expression used for?

Inline conditional logic inside a SELECT — SQL's version of if/else. Common uses: bucketing values (credit_score into "poor/fair/good"), pivot-style aggregation, and conditional formatting of output columns.

12. Difference between a primary key and a unique key

A table can have only one PRIMARY KEY (and it can't be NULL), but multiple UNIQUE keys — and UNIQUE columns can each hold one NULL, since NULL is never considered equal to anything, even another NULL.

13. Explain a clustered vs non-clustered index

A clustered index determines the physical row order on disk — a table has at most one (in MySQL/InnoDB, it's built on the primary key automatically). A non-clustered index is a separate structure that just points back to the row's location, and a table can have many.

14. Find the total order value per customer segment, only for segments with 2+ customers 
SELECT ec.segment, COUNT(DISTINCT ec.cust_id) AS customers, SUM(o.qty * p.price) AS segment_total
FROM ec_customers ec
JOIN orders o ON o.cust_id = ec.cust_id
JOIN products p ON p.product_id = o.product_id
GROUP BY ec.segment
HAVING COUNT(DISTINCT ec.cust_id) >= 2;
15. Why is SELECT * discouraged in production queries?

It pulls unnecessary columns (wasting I/O and network), breaks if the table schema changes column order, defeats "covering index" optimizations, and makes intent unclear to the next reader.

16. What is a deadlock, and how would you reproduce one for testing?

Two transactions each hold a lock the other needs, so neither can proceed. Reproduce it by having two connections update the same two rows in opposite order inside open transactions — MySQL's InnoDB will detect it and abort one automatically with a deadlock error, which you can assert on.

17. Write a query using LAG to flag suspicious jumps (fraud-style check) 
SELECT account_id, balance,
  balance - LAG(balance) OVER (PARTITION BY account_id ORDER BY account_id) AS balance_jump
FROM accounts;
18. Difference between EXISTS and IN

EXISTS stops scanning as soon as it finds one matching row and works well with correlated subqueries; IN materializes the full list first. For large subquery result sets, EXISTS is typically faster; for small static lists, IN reads more simply.

19. Find gaps in a sequential ID column (missing loan_ids) 
SELECT (l1.loan_id + 1) AS missing_id
FROM loans l1
LEFT JOIN loans l2 ON l1.loan_id + 1 = l2.loan_id
WHERE l2.loan_id IS NULL
ORDER BY missing_id;
20. How would you test for orphaned foreign keys as a data-quality check? 
-- accounts pointing to a customer_id that no longer exists
SELECT a.* FROM accounts a
LEFT JOIN customers c ON a.customer_id = c.customer_id
WHERE c.customer_id IS NULL;
