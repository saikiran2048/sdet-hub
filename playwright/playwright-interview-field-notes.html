Round 1

Playwright Technical

20–30 min · JS/TS

This is a positioning question, not a biography dump. Structure it as: current role → domain depth → core tech stack → one differentiator → why you're a fit for this role.

A tight framework for an SDET:

  • Who you are now: role, years of experience, domain (e.g., BFSI).
  • What you actually do: UI + API + DB automation, framework ownership, CI/CD integration — not just "I write test cases."
  • One standout: a scale number, a framework you built, or a problem you solved (flaky tests reduced by X%, migrated Selenium → Playwright, built a reconciliation validator).
  • Close with intent: why this role/company, tying your Playwright strength to what they're hiring for.
Timing

Keep it to 60–90 seconds. Interviewers use this to decide which follow-up questions to ask, so don't bury your strongest project — lead with it.

Playwright exposes the browser's network layer directly through the page object — no proxy or third-party library needed (unlike Selenium, which requires BrowserMob Proxy or DevTools Protocol hacks).

a) Listening to all requests/responses (passive capture)

typescript
page.on('request', request => {
  console.log('>>', request.method(), request.url());
});

page.on('response', response => {
  console.log('<<', response.status(), response.url());
});

await page.goto('https://example.com');

b) Waiting for a specific request/response (synchronous capture)

typescript
const [response] = await Promise.all([
  page.waitForResponse(resp => resp.url().includes('/api/orders') && resp.status() === 200),
  page.click('#submit-order'),
]);

const body = await response.json();
console.log('Order API response:', body);
Why this matters

waitForResponse/waitForRequest are also a synchronization mechanism — you can assert the UI only after the underlying API call actually completes, which eliminates a large class of flaky waits that Selenium can't solve natively.

Trade-off

Passive listeners (page.on('response', ...)) are good for logging/debugging entire flows (e.g., attaching all network logs to a test report on failure), while waitForResponse is for precise, single-call assertions.

Playwright can intercept and fulfill network calls via page.route(), letting you test the UI in isolation from the backend — useful for edge cases, error states, or backend not yet built.

typescript
await page.route('**/api/orders', route => {
  route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify({ orderId: 1234, status: 'CONFIRMED' }),
  });
});

await page.goto('https://example.com/orders');

Modifying a real response (not fully replacing it):

typescript
await page.route('**/api/orders', async route => {
  const response = await route.fetch();
  const body = (await response.text()).replace('"status":"PENDING"', '"status":"FAILED"');
  await route.fulfill({ response, body });
});

Simulating failures/timeouts:

typescript
await page.route('**/api/orders', route => route.abort('failed')); // network error
// or
await page.route('**/api/orders', route =>
  route.fulfill({ status: 500, body: JSON.stringify({ error: 'Internal Server Error' }) })
);
Interview angle

Distinguish contract-level mocking (fast, deterministic, good for negative/edge-case UI testing) from true E2E (validates the real integration). State explicitly that you use mocking to supplement, not replace, real API/E2E coverage.

Screenshots — three levels:

typescript
// Full page
await page.screenshot({ path: 'full-page.png', fullPage: true });

// Specific element
await page.locator('#summary-panel').screenshot({ path: 'panel.png' });

// On-failure only — Playwright Test does this natively via config
// playwright.config.ts
export default defineConfig({
  use: { screenshot: 'only-on-failure' },
});

Video recording — configured at context/project level:

typescript
// playwright.config.ts
export default defineConfig({
  use: { video: 'retain-on-failure' },
});

// or manually per context
const context = await browser.newContext({
  recordVideo: { dir: 'videos/', size: { width: 1280, height: 720 } },
});
Gotcha

Video is finalized only when the context closes — so await context.close() must be called for the file to be written and playable.

Interview angle

Talk about cost — video recording adds overhead and disk usage, so a mature framework typically only enables it conditionally (retain-on-failure, or on CI retry, not for every local run).

→ Basic Auth

typescript
const context = await browser.newContext({
  httpCredentials: { username: 'user', password: 'pass' },
});

→ Token-based Authentication — two common patterns:

1. Set an Authorization header on every request:

typescript
await context.setExtraHTTPHeaders({ Authorization: `Bearer ${token}` });

2. Programmatic login once, reuse storage state (most efficient pattern, and Playwright's recommended approach):

typescript
// One-time login — typically done in a global setup project
const page = await context.newPage();
await page.goto('https://app.example.com/login');
await page.fill('#username', 'user');
await page.fill('#password', 'pass');
await page.click('#login-btn');
await page.waitForURL('**/dashboard');
await context.storageState({ path: 'auth.json' });

// Reuse across all subsequent tests — skips UI login entirely
const context2 = await browser.newContext({ storageState: 'auth.json' });

In playwright.config.ts, this is usually wired up via a setup project + storageState in use, so every test project depends on auth being established once.

→ OAuth

  • Avoid automating the actual OAuth UI where possible — it's brittle, rate-limited, and sometimes blocked by bot detection (Google actively blocks headless automated logins).
  • Preferred: get a valid session token via the API directly (call the auth provider's token endpoint) and inject it into localStorage/cookies/storage state before navigating.
  • If UI automation of the OAuth flow is unavoidable, isolate it into a one-time global setup step + storage-state reuse, rather than repeating login per test.
Framework-design point

Storage-state reuse is the single biggest lever for both speed and stability — it removes login as a per-test dependency and point of flakiness.

Unlike Java (where retries need TestNG's IRetryAnalyzer), retries are a native, first-class feature of the Playwright Test runner:

typescript
// playwright.config.ts
export default defineConfig({
  retries: process.env.CI ? 2 : 0, // retry only in CI, not locally
});

Or scoped per-test/per-describe block:

typescript
test.describe.configure({ retries: 1 });

Retried tests are automatically tagged in the HTML report, and you can trigger tracing/video/screenshots only on retry (trace: 'on-first-retry') — so you get full forensic debugging data without paying that cost on every green run.

Important trade-off to raise unprompted

Retries mask flakiness rather than fix it. “I use retries as a safety net for environment-level flakiness (network blips, CI resource contention), not as a substitute for fixing real synchronization issues in the test. I keep local retries at 0 so flaky tests fail loudly in dev, and I track CI retry counts in reporting so silently-flaky tests get flagged, not hidden.” This is a senior-level distinction interviewers specifically listen for.

Round 2

Advanced Playwright

30–45 min · JS/TS

Structure your answer as a triage funnel, not a list of tools:

  1. Reproduce locally first — run headed with --debug or slow-mo to see if it's a genuine timing issue vs. environment-specific.
  2. Trace Viewer — the single most powerful tool; replays DOM snapshots, network, console logs, and actions frame-by-frame for the exact failing run.
  3. Check for anti-patterns: hard-coded waitForTimeout(), assertions racing against async UI updates, shared mutable state between parallel tests, test-order dependency.
  4. Isolate the failure category: network timing → use waitForResponse/waitForLoadState; animation/re-render race → rely on auto-waiting locators; environment-only flakiness (CI but not local) → check resource contention or headless rendering differences.
  5. Quarantine + track, don't silently retry — flag flaky tests (e.g., via test.fixme() or a flaky-tests dashboard) so they get real fixes, not permanent retry band-aids.
  • Parallelization: Playwright Test parallelizes by default across workers; tune workers in playwright.config.ts to match CI runner resources.
  • Storage-state reuse to skip UI login — often the single biggest win.
  • API-first setup/teardown: create test data via API calls instead of UI flows; only use the UI for the actual behavior under test.
  • Avoid waitForTimeout() — replace with condition-based waits and web-first assertions (expect(locator).toBeVisible()) that poll instead of sleeping.
  • Selective execution: tag-based test runs (@smoke, @regression via grep) so CI doesn't always run the full suite.
  • Sharding (--shard=1/4) to split one suite across multiple CI machines.
  • Headless in CI, headed only for local debugging.

“Dynamic” usually means one of: delayed rendering, changing DOM order, or non-deterministic attributes (auto-generated IDs). Handle each differently:

typescript
// Delayed rendering — Playwright's locators auto-wait, no explicit wait needed
await page.getByText('John Doe').click();

// Non-deterministic ID — anchor on stable attributes instead
await page.getByTestId('order-row').filter({ hasText: 'Order #1234' }).click();

// Element that appears after an async action
await page.locator('#confirmation-banner').waitFor({ state: 'visible' });

// List where order/count changes
const items = await page.locator('.list-item').allTextContents();
Key point

Favor data-testid/role-based locators (getByRole, getByTestId) over CSS classes/auto-generated IDs — this is both a dynamic-element and a maintainability answer.

This is a core conceptual question — get it precise:

page.locator()page.$() (querySelector)
TypeA lazy, re-evaluating reference to elements matching a selectorAn immediate snapshot handle (ElementHandle) to the element at call-time
Auto-waitYes — re-queries the DOM and waits for actionability before every actionNo — resolves once, immediately; if the element isn't there yet, returns null
Stale referencesNever goes stale — re-locates on every interactionCan go stale if the DOM re-renders after the handle was captured
Recommended usagePreferred, modern API for virtually all interactionsLegacy/low-level; Playwright's docs deprecate this in favor of locators
Lead with this

“locator() is a strategy, not a handle — it re-finds the element every time and waits for it to be actionable, which is why Playwright recommends it over page.$()/ElementHandle, which is a single point-in-time reference that can go stale.”

Enabling traces — config-driven (typical):

typescript
// playwright.config.ts
export default defineConfig({
  use: { trace: 'on-first-retry' }, // only capture on retry, not every green run
});

Or manually, mid-test:

typescript
await context.tracing.start({ screenshots: true, snapshots: true, sources: true });
// ... run test steps ...
await context.tracing.stop({ path: 'trace.zip' });

What you get: a timeline you can scrub through showing, for each action — a DOM snapshot before/after, the network calls in flight, console logs, and exact locator resolution. Open it with npx playwright show-trace trace.zip or the online trace viewer.

Why it beats traditional debugging

Instead of adding console.logs and re-running, you get a full forensic replay of a single CI run — including the exact DOM state at the moment of failure — without needing to reproduce the issue.

Give a concrete, specific scenario rather than a generic feature list:

Sample story

“On a banking UI with an async, multi-step payment confirmation (submit → backend processing → websocket push → UI update), Selenium required explicit WebDriverWait chains and still had intermittent flakiness because it has no native visibility into network state. In Playwright, I used page.waitForResponse() to synchronize directly on the confirmation API call completing, and Playwright's auto-waiting locators eliminated the need for manual ExpectedConditions. Trace Viewer then let me pinpoint the one race condition that remained — something that would've taken hours of log-diffing in Selenium's Grid setup.”

Also worth mentioning as breadth (not the main story): built-in parallelism via BrowserContext isolation (no Selenium Grid needed), native network interception, multi-tab/multi-origin support, and web-first assertions (expect(locator).toHaveText(...)) that auto-retry instead of failing on the first check.

typescript
import { Page, Locator } from '@playwright/test';

export class LoginPage {
  private readonly page: Page;
  private readonly usernameInput: Locator;
  private readonly passwordInput: Locator;
  private readonly loginButton: Locator;
  private readonly errorMessage: Locator;

  constructor(page: Page) {
    this.page = page;
    this.usernameInput = page.locator('#username');
    this.passwordInput = page.locator('#password');
    this.loginButton = page.locator('#login-btn');
    this.errorMessage = page.locator('#error-msg');
  }

  async login(username: string, password: string): Promise<DashboardPage> {
    await this.usernameInput.fill(username);
    await this.passwordInput.fill(password);
    await this.loginButton.click();
    return new DashboardPage(this.page);
  }

  async getErrorMessage(): Promise<string> {
    return this.errorMessage.textContent() ?? '';
  }
}

Design choices worth stating explicitly:

  • Locators as fields, initialized in the constructor (not re-queried as strings scattered across test methods) — one place to update if the UI changes.
  • Methods return the next Page Object (login() returns DashboardPage) — this “fluent navigation” pattern makes test flows read like user journeys and catches wrong-navigation bugs at compile time (with TypeScript).
  • No assertions inside Page Objects — assertions belong in the test layer; Page Objects only expose actions and raw data, keeping them reusable across positive and negative test cases.
  • Layer further with a Component Object pattern for repeated UI fragments (nav bar, modal, data table), and combine POM with fixtures (Q12) so tests receive ready-to-use page objects instead of constructing them inline.
  • API-driven setup/teardown: create/delete test entities via backend API calls (using Playwright's built-in request context — no separate HTTP client needed).
  • Test data factories/builders (TS): typed builder functions generating valid-by-default objects with overridable fields, avoiding giant static JSON fixtures that drift out of sync with schema changes.
  • Environment isolation: unique data per test run (UUID-suffixed usernames/emails) to avoid collisions in parallel/sharded runs.
  • External data sources: DB seeding scripts for larger datasets, JSON/CSV for parameterized tests.
  • Cleanup discipline: teardown via fixture use() + cleanup-after pattern, or test.afterEach, so failed runs don't leave orphaned data.

Playwright parallelizes at two levels:

  1. Browser/Context level: each BrowserContext is a fully isolated “incognito” session (separate cookies, storage, cache) within the same browser process — much cheaper than spinning up a new browser instance, and no shared state between tests.
  2. Worker/process level: Playwright Test spins up multiple workers (independent Node.js processes, each with its own browser instance), controlled by the workers config option — tests in different files run fully in parallel by default.
Practical framework note

Because contexts are isolated but cheap, Playwright Test's default pattern is one browser instance per worker, with a fresh BrowserContext + page per test (via the built-in page fixture). Add sharding (--shard) on top to split the worker pool across multiple CI machines for even larger suites.

LevelAnalogyScope
BrowserThe installed browser application itselfOne instance can spawn many contexts; expensive to create, so typically created once per worker
BrowserContextAn incognito windowIsolated cookies, storage, cache, permissions per context — this is your test isolation boundary
PageA single tab within that windowA context can have multiple pages (tabs); most tests use one page per context, but multi-tab scenarios use multiple
Close with

“I treat BrowserContext as my unit of test isolation — one fresh context per test guarantees no cookie/storage leakage between tests, without paying the cost of relaunching the whole browser. Playwright Test's built-in page fixture already gives you this for free per test.”

typescript
// playwright.config.ts
export default defineConfig({
  use: {
    headless: !!process.env.CI, // headless in CI, headed locally
  },
});

// or programmatically
const browser = await chromium.launch({ headless: false, slowMo: 50 });

Headless is faster and CI-friendly; headed (often combined with slowMo) is for local visual debugging, and test.only + --headed --debug together is the typical local-debug workflow. Toggling via an environment variable/config flag (rather than hardcoding) means the same test suite runs correctly in both local dev and pipeline without code changes.

Fixtures are Playwright Test's built-in dependency injection + setup/teardown mechanism — they provide pre-configured objects (an authenticated page, a seeded API client, a Page Object) to a test automatically, and clean them up after, without every test repeating boilerplate setup code.

typescript
import { test as base, expect } from '@playwright/test';
import { LoginPage } from './pages/LoginPage';

type MyFixtures = {
  loginPage: LoginPage;
  authenticatedPage: import('@playwright/test').Page;
};

export const test = base.extend<MyFixtures>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await use(loginPage);
  },

  authenticatedPage: async ({ browser }, use) => {
    const context = await browser.newContext({ storageState: 'auth.json' });
    const page = await context.newPage();
    await use(page);          // test runs here
    await context.close();    // teardown, runs automatically after
  },
});

export { expect };
typescript
// in a test file
import { test, expect } from './fixtures';

test('dashboard shows welcome message', async ({ authenticatedPage }) => {
  await authenticatedPage.goto('/dashboard');
  await expect(authenticatedPage.getByText('Welcome')).toBeVisible();
});

Why they matter, beyond just “less boilerplate”:

  • Composable: fixtures can depend on other fixtures (authenticatedPage could itself use an apiClient fixture to seed data first).
  • Automatic teardown: the code after await use(...) always runs, even on test failure — a safer cleanup guarantee than manually remembering afterEach.
  • Worker-scoped vs test-scoped: fixtures can be scoped to run once per worker (an expensive DB connection) or fresh per test (a clean page) via { scope: 'worker' }.
Interview signal to give proactively

Contrast this with Java, where this exact effect has to be hand-built via TestNG/JUnit lifecycle annotations and a base test class — native fixtures are one of the concrete advantages of the JS/TS runner over Playwright's Java bindings.

Dropdowns:

typescript
// Native <select>
await page.selectOption('#country', 'IN');

// Custom (div-based) dropdown — click to open, then click the option
await page.click('#custom-dropdown-trigger');
await page.getByRole('option', { name: 'India' }).click();

Frames/iFrames:

typescript
const frame = page.frameLocator('#payment-iframe');
await frame.locator('#card-number').fill('4111111111111111');

frameLocator() is preferred over the older page.frame({ name }) lookup because it auto-waits for the iframe itself to be attached, avoiding a race where the iframe hasn't loaded yet.

Alerts/Dialog boxes:

typescript
page.on('dialog', async dialog => {
  console.log('Dialog message:', dialog.message());
  await dialog.accept(); // or dialog.dismiss();
});
await page.click('#delete-btn'); // triggers the confirm() dialog
Important nuance

The listener must be registered before the action that triggers the dialog, since Playwright auto-dismisses unhandled dialogs by default — unlike Selenium, where you switch to driver.switchTo().alert() reactively after the fact.

This is the conceptual capstone question — answer it as a philosophy difference, not a feature list:

  • Selenium: waits are largely the test author's responsibility. You explicitly wrap actions in WebDriverWait + ExpectedConditions (visibility, clickability, presence), or fall back to implicit waits/sleep(), which is a common flakiness source.
  • Playwright: auto-waiting is built into every actionability check. Before any action (click, fill, check, etc.), Playwright automatically waits for the element to be attached, visible, stable (not animating), enabled, and receiving events (not obscured) — all before executing, with a single configurable timeout.
  • Playwright further extends this with web-first assertions (await expect(locator).toBeVisible()) that auto-retry until the condition is true or times out, plus network-aware waiting (waitForResponse, waitForLoadState) covering scenarios Selenium can't natively observe without third-party tooling.
Practical implication to close with

“This is why well-written Playwright suites rarely need explicit waits at all — waitForTimeout() in a Playwright codebase is usually a sign the locator strategy or an async dependency hasn't been properly identified, not a limitation of the tool.”

Java Coding + Managerial

Java · Coding & behavioural

java
public class VowelConsonantCounter {
    public static void main(String[] args) {
        String name = "Saikiran"; // example
        int vowels = 0, consonants = 0;

        for (char ch : name.toLowerCase().toCharArray()) {
            if (ch < 'a' || ch > 'z') continue; // skip non-letters
            if ("aeiou".indexOf(ch) != -1) {
                vowels++;
            } else {
                consonants++;
            }
        }

        System.out.println("Vowels: " + vowels);
        System.out.println("Consonants: " + consonants);
    }
}
Talking points if pressed to extend it

Handling mixed case, skipping spaces/hyphens (toLowerCase() + a letter check handles both), and Big-O — this is O(n) time, O(1) extra space, since we only scan the string once with fixed counters.

The constraint (“without Collections”) is testing whether you understand what a HashMap/Set is actually doing under the hood — so replicate that with a fixed-size array as a frequency table (since names are ASCII/lowercase letters, a 26-slot array works as a manual hash map).

java
public class UniqueDuplicateChars {
    public static void main(String[] args) {
        String name = "saikiran";
        int[] freq = new int[26]; // manual frequency table, replaces a HashMap

        for (char ch : name.toCharArray()) {
            freq[ch - 'a']++;
        }

        System.out.print("Unique characters: ");
        for (int i = 0; i < 26; i++) {
            if (freq[i] == 1) System.out.print((char) (i + 'a') + " ");
        }

        System.out.print("\nDuplicate characters: ");
        for (int i = 0; i < 26; i++) {
            if (freq[i] > 1) System.out.print((char) (i + 'a') + " ");
        }
    }
}
Say this explicitly

“This is O(n) time and O(1) space, since the frequency array is fixed at 26 slots regardless of input size — I'm replacing the HashMap with a manual array-based hash, which is the standard technique when Collections are off the table.”

This is the classic sliding window problem — almost certainly what “Longest Substring” means unless they clarify otherwise (if ambiguous in the actual interview, ask: “longest substring without repeating characters, or longest common substring between two strings?” — they're different problems).

java
import java.util.Arrays;

public class LongestSubstring {
    public static void main(String[] args) {
        String input = "abcabcbbde";
        System.out.println("Longest substring: " + longestUniqueSubstring(input));
    }

    public static String longestUniqueSubstring(String s) {
        int[] lastIndex = new int[128]; // ASCII frequency/index table, no Collections needed
        Arrays.fill(lastIndex, -1);

        int start = 0, maxLen = 0, maxStart = 0;

        for (int end = 0; end < s.length(); end++) {
            char ch = s.charAt(end);
            if (lastIndex[ch] >= start) {
                start = lastIndex[ch] + 1; // shrink window past the repeat
            }
            lastIndex[ch] = end;

            if (end - start + 1 > maxLen) {
                maxLen = end - start + 1;
                maxStart = start;
            }
        }
        return s.substring(maxStart, maxStart + maxLen);
    }
}
Complexity to state proactively

O(n) time — each character is visited by end once, and start only moves forward, never backward, so it's a single pass overall (not O(n²) despite the nested-looking logic). O(1) extra space (fixed 128-size array).

Structure this as a process, not a vague “I'd talk to my team” answer — interviewers are checking for decision-making under pressure:

  1. Triage first: list remaining work and classify by risk/impact — what's blocking release vs. nice-to-have, what's high-risk vs. low-risk.
  2. Match to skill, not just availability: assign the highest-risk/most complex pieces to the most experienced person on that area, and split parallelizable work broadly.
  3. Make dependencies explicit: identify what can run in parallel vs. what's sequentially blocked (e.g., API tests can't start until an endpoint is deployed).
  4. Communicate scope trade-offs upward early: if the deadline genuinely can't absorb all planned scope, flag it to the lead/manager immediately with options (cut scope, extend timeline, add hands).
  5. Check in short-cycle, not just at the end: quick daily syncs to catch a teammate stuck early enough to redistribute work.
  6. Protect quality on the critical path: flag a scope cut on low-risk items rather than ship untested high-risk functionality.
Close with a concrete anecdote if you have one

A real deadline crunch, how you split UI/API/DB validation work across the team, what you flagged upward — a real example lands far better than the abstract framework alone.
