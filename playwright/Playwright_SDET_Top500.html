Section A — Playwright: Core & Advanced (Q1–322)

Q1 What is the difference between Playwright and Selenium, and why would you choose Playwright for a new project?

Playwright communicates with browsers over a single WebSocket-based protocol (CDP for Chromium, and browser-specific protocols for Firefox/WebKit) instead of the WebDriver HTTP wire protocol Selenium uses — this makes it faster and removes the driver-binary management problem entirely. Playwright also has built-in auto-waiting and actionability checks, native support for multiple browser contexts (true parallel isolation without spinning up new browsers), first-class API testing, network interception, and tracing — all of which Selenium needs third-party libraries to approximate. For a greenfield project I’d pick Playwright for lower flakiness, faster execution, and a single framework that covers UI, API, and even component testing.

Q2 ExplainBrowser,BrowserContext, andPageand why context isolation matters.

A Browser is one browser process instance. A BrowserContext is an isolated, incognito-like session within that browser — its own cookies, storage, and cache — and a Page is a single tab inside a context. Playwright’s test runner spins up a new context per test by default, so tests never leak cookies/localStorage into each other, which is what lets you safely run hundreds of tests in parallel without one test’s login state bleeding into the next.

Q3 How does Playwright’s auto-waiting mechanism work, and what actionability checks does it perform?

Before most actions (click, fill, check), Playwright automatically waits for the element to be: attached to the DOM, visible, stable (not animating), enabled, and — for typing actions — receiving events (not obscured by another element). It polls these conditions until they’re satisfied or the timeout is hit, then performs the action. This is why Playwright tests rarely need explicit sleep/waitForTimeout calls, unlike raw Selenium.

Q4 Why ispage.waitForTimeout()discouraged, and when might a hard wait be justified?

A hard wait always waits the full duration even if the condition is met earlier (slowing the suite) and can still fail if the actual condition takes longer than the wait (flaky). Playwright’s web-first assertions (expect(locator).toBeVisible()) and waitForFunction/waitForResponse retry until success or timeout, adapting to actual conditions. A hard wait is only justified for something with no observable DOM/network signal — e.g., waiting out a fixed client-side animation/debounce with no transitionend hook — and even then I’d try to avoid it or make it configurable.

Q5 What isgetByRole, and why does Playwright recommend role-based locators over CSS/XPath?

getByRole locates elements by their accessible role (button, textbox, link) and accessible name — the same info a screen reader uses. It’s preferred because it ties tests to user-facing behavior, not implementation details (class names, DOM structure), so it’s resilient to refactors and also nudges the app toward better accessibility. CSS/XPath selectors break the moment a <div> becomes a <span> or a class is renamed; role-based locators usually don’t.

Q6 What is strict mode in Playwright, and how do you resolve a strict-mode violation?

Strict mode means an action fails immediately if a locator resolves to more than one element, instead of silently acting on the first match (a common source of hidden bugs in Selenium suites). To resolve it, you narrow the locator — chain a .filter(), use .nth(n), scope it under a more specific parent, or use a getByTestId/getByRole with an accessible name to disambiguate.

Q7 How do you handle authentication once and reuse it across many tests?

Use a global setup that logs in via UI or API once, then saves storageState (cookies + localStorage) to a JSON file. Each test project/config then loads that storageState so every test starts already authenticated — this is far faster than logging in through the UI in every single test and is the standard Playwright pattern for auth reuse.

// global-setup.ts
const browser = await chromium.launch();
const page = await browser.newPage();
await page.goto('/login');
await page.fill('#user', 'admin'); await page.fill('#pass', 'pass');
await page.click('#submit');
await page.context().storageState({ path: 'auth.json' });
// playwright.config.ts
use: { storageState: 'auth.json' }
Q8 What are fixtures, and how do custom fixtures differ frombeforeEach?

Fixtures are Playwright’s dependency-injection system for tests — you declare what a test needs (e.g., authenticatedPage) and Playwright resolves, sets up, and tears it down automatically, only when that fixture is actually used. Unlike beforeEach, fixtures are lazy (skip setup cost for tests that don’t need them), composable (fixtures can depend on other fixtures), and scoped per-test or per-worker — giving much finer control than a blanket hook that runs for every test in a file regardless of need.

Q9 What is the difference between test-level and worker-level fixtures?

A test-scoped fixture is created fresh for every single test (e.g., a page). A worker-scoped fixture is created once per worker process and reused across all tests that worker runs (e.g., a database connection, or an authenticated API client) — useful for expensive setup you don’t want to repeat per test, as long as the resource can be safely shared without one test’s usage affecting another’s.

Q10 How do you intercept and mock a network request/response in Playwright?

Use page.route(urlPattern, handler) to intercept matching requests before they hit the network, then either fulfill with a custom response, continue the real request (optionally modified), or abort it.

await page.route('**/api/orders', route =>
  route.fulfill({ status: 200, body: JSON.stringify({ orders: [] }) })
);

This is invaluable for testing error states, edge cases, and slow/unstable third-party dependencies without needing the real backend to cooperate.

Q11 How do you capture and use traces for debugging CI failures?

Set trace: 'on-first-retry' (or retain-on-failure) in the config so a trace is only captured for failing tests — full ones on every run are expensive. The trace file captures a DOM snapshot, network activity, console logs, and a timeline for every action; npx playwright show-trace trace.zip opens an interactive timeline where you can literally scrub through the test and see exactly what the page looked like at each step, which is usually enough to diagnose a CI-only failure without reproducing it locally.

Q12 What isexpect.poll(), and when would you use it over a standard assertion?

expect.poll() retries a given function (not just a locator) until it returns a value matching the assertion or the timeout expires — useful when you’re asserting on something that isn’t a DOM element directly, like an API response, a database value, or a computed value from multiple sources.

await expect.poll(async () => (await api.get('/job/1')).status).toBe('completed');
Q13 What is a soft assertion, and when would you use one?

expect.soft() records a failure but doesn’t stop test execution immediately — the test still fails overall, but only at the end, after running all remaining assertions. I use it when I want a single test run to report all the mismatches at once (e.g., checking 10 fields on a summary page) instead of stopping at the first failure and requiring 10 separate re-runs to find every issue.

Q14 How do you implement visual regression testing in Playwright?

expect(page).toHaveScreenshot('name.png') captures a screenshot and diffs it against a stored baseline pixel-by-pixel (with a configurable maxDiffPixelRatio/threshold for anti-aliasing noise). For elements with dynamic content (timestamps, ads), I use the mask option to blank them out before comparison so they don’t cause false failures. Baselines are regenerated deliberately with --update-snapshots and reviewed in PR, not auto-accepted.

Q15 How do you handle file uploads and downloads in Playwright?

Uploads: locator.setInputFiles('path/to/file') works even on hidden <input type="file"> elements without needing to interact with the OS file dialog. Downloads: wrap the triggering action with page.waitForEvent('download'), then call download.path() or download.saveAs() to access the file and assert on its contents (e.g., parse the CSV and check rows).

const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.click('#export-csv'),
]);
const path = await download.path();
Q16 How do you test an iframe in Playwright?

page.frameLocator('iframe-selector') returns a FrameLocator scoped to that iframe, and you chain normal locator methods on it exactly like the main page — no explicit switchTo step like Selenium requires. For nested iframes you just chain multiple frameLocator() calls.

Q17 What is test sharding, and how do you configure it?

Sharding splits the full test suite across multiple machines/CI jobs by file (not individual test), using --shard=2/4 (this machine runs shard 2 of 4). It’s how you cut a 2-hour suite down to ~30 minutes by running shards in parallel CI jobs, then merging the reports afterward.

Q18 How do you merge reports from sharded runs into a single report?

Configure each shard to output a blob reporter, upload each shard’s blob as a CI artifact, then in a final job download all blobs and run npx playwright merge-reports --reporter=html ./all-blob-reports to produce one consolidated HTML report reflecting the full suite’s results.

Q19 What’s the difference betweenpage.route()andcontext.route()?

page.route() intercepts requests only for that specific page/tab. context.route() applies the interception to every page opened within that browser context — useful when a flow opens new tabs/popups (e.g., OAuth) and you want the mock to apply everywhere, not just the original tab.

Q20 How do you emulate a mobile device in Playwright?

Use Playwright’s built-in device descriptors (devices['iPhone 14']) either as a project in the config or spread into browser.newContext() — it sets viewport size, user agent, touch support, and device scale factor to match that real device’s characteristics.

Q21 How would you test a WebSocket-driven real-time feature?

Playwright can intercept and inspect WebSocket frames via the page.on('websocket') event and its framesent/framereceived sub-events, letting you assert on messages sent/received without a UI-only proxy. For deterministic tests, I’ll often mock the WebSocket server response entirely so the test isn’t dependent on real-time backend timing.

Q22 How do you handle flaky tests caused by animations/transitions?

First, Playwright’s actionability checks already wait for an element to be “stable” (not moving) before acting, which handles most CSS transition flakiness automatically. If a specific animation still causes issues, I’ll either wait for a concrete signal (an animationend event, or a resulting state change like a class toggling) rather than a fixed sleep, or — if it’s purely cosmetic — disable animations in the test environment via a CSS override injected at context creation.

Q23 What’s the difference betweentoBeandtoEqualin Playwright/Jest-style assertions?

toBe uses Object.is (reference/strict equality) — fine for primitives, but two different objects with identical contents will fail. toEqual does a deep, structural comparison of objects/arrays, which is what you want when comparing an API response object against an expected shape.

Q24 How do you debug a test interactively during local development?

npx playwright test --debug opens the Playwright Inspector, which pauses before each action, lets you step through, and gives a live selector-picker to test locators against the actual page. I also use page.pause() inline for a specific breakpoint, and VS Code’s Playwright extension for setting real breakpoints and inspecting variables mid-run.

Q25 What is Playwright Component Testing, and when would you use it over E2E?

It lets you mount and test a single UI component (React/Vue/Svelte) in isolation inside a real browser, without needing the full application or backend running — you pass mock props and assert on rendered behavior directly. I’d use it for testing complex, reusable components (a date picker, a data grid) in isolation with fast feedback, while reserving full E2E tests for critical user journeys that cross multiple components/pages.

Q101 What istest.step(), and why use it for grouping actions in a report?

test.step() wraps a group of related actions under a named label that shows up as a collapsible, timed sub-section in the HTML report and trace viewer — instead of one flat list of low-level actions, you get “Login as admin” → “Add item to cart” → “Checkout” as readable checkpoints. This makes it dramatically faster to see where in a long test something failed without reading every individual click/fill call.

Q102 How do you control parallel worker count per project vs globally?

workers in the top-level config sets the default across the whole run, but you can override parallelism behavior per project (e.g., forcing a serial mode for a project that hits a rate-limited third-party sandbox) using fullyParallel: false or test.describe.serial() inside that project’s tests, while other projects still run fully parallel.

Q103 What istoPass(), and how does it differ from a normal retryable assertion?

expect(async () => {...}).toPass() retries an entire block of arbitrary code (not just a single locator assertion) until it stops throwing or the timeout is hit — useful when a “check” involves multiple steps (e.g., reload the page, then check three conditions) that need to be retried together as a unit, not just one web-first assertion.

Q104 How do you use ARIA snapshots (toMatchAriaSnapshot) to assert accessibility tree structure?

toMatchAriaSnapshot() captures the accessibility tree (roles, names, states) of an element or page and compares it against a stored YAML-like snapshot, similar in spirit to visual snapshots but for structure/semantics instead of pixels — it catches regressions like a button losing its accessible name or a region losing its landmark role, which a pixel screenshot wouldn’t reliably catch.

Q105 How do you test drag-and-drop when the app uses native HTML5 drag events vs mouse-simulated drag?

For native HTML5 draggable elements, locator.dragTo(target) dispatches the correct native drag events automatically. For libraries that implement drag purely via mouse listeners (common in Kanban/sortable-list components), native drag events won’t fire the right handlers — instead I simulate it manually with mouse.move(), mouse.down(), several intermediate mouse.move() calls (to trigger the library’s drag-tracking), then mouse.up().

Q106 How do you grant or deny browser permissions like camera, microphone, or clipboard in a test?

context.grantPermissions(['camera', 'microphone', 'clipboard-read']) grants them up front so the app never shows a permission prompt during the test, keeping the flow deterministic; omitting them (or calling clearPermissions()) lets you specifically test the app’s fallback/denied-permission UI path.

Q107 How would you test a<canvas>-based UI element, like a chart or signature pad?

Canvas content isn’t part of the DOM, so you can’t use normal locators to inspect what’s drawn — instead I either take a screenshot of just the canvas element and compare it visually, or (better, if the app exposes it) assert on the underlying data model that drives the canvas (e.g., a JS object or API response) rather than the pixels themselves, since that’s far less brittle.

Q108 What ispage.routeFromHAR(), and how would you use a recorded HAR file to mock a whole flow?

It replays network responses recorded in a HAR (HTTP Archive) file, letting a test run entirely against pre-captured real traffic instead of a live backend — useful for testing a complex multi-request flow deterministically and offline. I record the HAR once against a real environment, commit it, then point routeFromHAR() at it so the UI test is fast, stable, and independent of backend availability.

Q109 How do you configure a per-test timeout that differs from the global config default?

Pass test.setTimeout(60000) inside the test itself, or set it as the third argument in the test definition (test('slow import job', { timeout: 60000 }, async ({ page }) => {...})) — this overrides just that test without inflating the default timeout for the whole suite.

Q110 How would you test infinite-scroll behavior reliably without flakiness?

I assert on the item count before and after scrolling to confirm new items actually loaded (not just that scrolling happened), wait for a concrete signal like a loading spinner disappearing or a network response completing rather than a fixed delay, and scroll the actual scrollable container (not just window) via mouse.wheel() or evaluate() if the app uses a custom scroll container.

Q111 How do you usetest.describe.parallel()vs default serial execution within a file?

By default, tests within the same file run serially in the same worker unless fullyParallel: true is set globally. test.describe.parallel() explicitly opts a group of tests into running in parallel across multiple workers even without that global flag — useful when most of the suite needs serial execution for a specific reason, but one block of independent tests would benefit from parallelism.

Q112 How would you validate that a specific console error does NOT appear during a critical flow?

I attach a page.on('console', msg => {...}) listener at the start of the test, collect any error-type messages into an array, and assert that array is empty (or doesn’t contain a specific pattern) at the end — this catches silent JS errors that don’t visibly break the UI but indicate a real underlying bug.

Q113 How do you handle geolocation-based UI behavior in a deterministic, testable way?

Set a fixed geolocation (lat/long) and grant the geolocation permission at context creation, so the app always sees the same coordinates regardless of where the test actually runs (critical for CI, which has no real GPS) — this lets you test location-dependent UI (nearest-store finder, region-specific content) deterministically.

Q114 What happens when multiplepage.route()handlers match the same URL, and how is priority determined?

Route handlers are matched in last-registered-first order — the most recently added route() call gets first chance to handle a matching request, and it can choose to call route.fallback() to pass control to the next-most-recent matching handler instead of handling it itself. This lets you layer a specific override on top of a broader default mock.

Q115 How would you test copy-to-clipboard functionality?

Grant clipboard-read/clipboard-write permissions on the context, trigger the copy action, then read navigator.clipboard.readText() via page.evaluate() to assert the clipboard actually contains the expected text — this is more reliable than trying to inspect an OS-level clipboard from outside the browser.

Q116 How would you assert on two browser contexts interacting with the same backend resource, like a live chat?

Open two separate BrowserContexts (simulating two independent users) within the same test, have one send a message via its page, and assert the other context’s page receives/displays it — this is the standard way to test real-time multi-user features without needing two actual test runs.

Q117 How would you validate an upload progress indicator without waiting for a real large upload in CI?

I mock the upload endpoint’s response with page.route() and introduce an artificial delay before fulfilling it, which is enough to trigger and hold the progress UI state long enough to assert on it — this avoids needing to actually push a multi-hundred-MB file through CI just to see a progress bar render.

Q118 How do you usepage.emulateMedia()to test print styles or reduced-motion behavior?

page.emulateMedia({ media: 'print' }) makes the page apply its @media print CSS so you can screenshot/assert on the print layout without literally printing; emulateMedia({ reducedMotion: 'reduce' }) similarly lets you verify the app respects a user’s reduced-motion accessibility preference by disabling animations.

Q119 How would you design a test to verify a service worker correctly caches assets for offline use?

Load the page once online (to let the service worker install and cache assets), then use context.setOffline(true) and reload — assert the page still renders correctly from cache instead of showing a browser offline error. I’d also assert specific cached resources exist via the Cache Storage API through page.evaluate().

Q120 How do you decide when to usetoHaveScreenshot()vs a DOM-level assertion for the same UI change?

If the change is structural/behavioral (text content, an element’s presence, an attribute value), a DOM assertion is more precise, faster, and far less flaky than a screenshot. I reserve visual snapshots for things that genuinely can’t be expressed structurally — layout/spacing regressions, CSS-only styling bugs, or rendering differences that wouldn’t show up in the DOM at all.

Q201 What aretest.fail(),test.fixme(), andtest.slow()annotations, and when would you use each?

test.fail() marks a test as expected to fail — it still runs, but Playwright reports it as passing if it fails (and flags it if it unexpectedly passes), useful for tracking a known bug without a red build. test.fixme() marks a test as broken and skips it entirely, with intent to fix later — a clearer signal than commenting it out. test.slow() triples that test’s timeout, for a test that’s legitimately slow (large data setup) rather than actually stuck.

Q202 How do you create fixture “options” so a test file can override a fixture’s behavior viatest.use()?

Declare an “option” fixture (a plain value fixture, not one that returns a resource) with a default, then have your real fixture read that option to decide its behavior — a test file can then call test.use({ myOption: 'value' }) at the top of the file or inside a describe block to override just that option for those tests, without touching the fixture implementation itself.

export const test = base.extend<{ role: string; page: Page }>({
  role: ['user', { option: true }],
  page: async ({ browser, role }, use) => {
    const context = await browser.newContext({ storageState: `auth-${role}.json` });
    await use(await context.newPage());
  },
});
// in a test file: test.use({ role: 'admin' });
Q203 What doesexpect.configure()do, and when would you use it to scope custom assertion defaults?

It returns a version of expect with overridden defaults (like timeout or soft) scoped to just that call, without changing the global config — useful when one specific assertion legitimately needs a longer timeout (e.g., waiting on a slow report-generation feature) without inflating the timeout for every assertion in the suite.

Q204 What is the difference betweenlocator.evaluate()andlocator.evaluateAll()?

evaluate() runs a function against the single element the locator resolves to (throwing in strict mode if it matches more than one). evaluateAll() runs the function against the full array of all matching elements at once, returning an array of results — useful for extracting or computing something across every row of a table in one call instead of looping and calling evaluate() per row.

Q205 How and why would you usepage.exposeFunction()to inject a custom callback the page can call?

It registers a Node-side function that becomes callable from within the browser’s JS context (window.myFunction(...)), letting page-side code call back into your test code — useful for things like intercepting a client-side analytics call or letting the app under test notify your test of an internal event it wouldn’t otherwise expose through the DOM or network.

Q206 What ispage.addInitScript()used for, and how does it differ from running a script after page load?

It injects a script that runs before any of the page’s own scripts, on every navigation in that context — essential for things like stubbing Date.now(), mocking window.matchMedia, or setting a value in localStorage before the app’s own startup code reads it. A script run after load is too late for anything the app checks at initialization time.

Q207 How would you test content rendered inside a slotted Shadow DOM component?

Slotted content (light DOM children projected into a shadow tree’s <slot>) is still part of the regular DOM from Playwright’s perspective, so normal locators work on it directly — the piercing/Shadow DOM traversal Playwright does automatically is really only needed for elements defined inside the shadow root itself, not the projected slotted content.

Q208 When would you usebrowserType.launchPersistentContext()instead of a regular launched browser?

It launches a browser using a real, persistent user-data directory (cookies, extensions, cache) on disk instead of a fresh in-memory context — useful when testing behavior that depends on an actual installed browser extension, or when you deliberately want state to persist across multiple test runs (rare, and usually the opposite of what you want for isolated CI tests).

Q209 How do you override the browser’s user-agent or client hints for a test that depends on device/browser detection?

Set userAgent in browser.newContext() (or per-device via a device descriptor) to simulate a specific browser/OS combination — useful for testing user-agent-based feature detection or a “please update your browser” banner without needing to actually run that real browser.

Q210 What ispage.setExtraHTTPHeaders()used for, and how does it differ from route interception?

It attaches headers to every subsequent request from that page automatically (e.g., a custom X-Test-Run-Id for correlating test traffic in logs) without needing to intercept and modify each request manually via page.route() — simpler when you just need to add static headers, whereas route() is for more complex per-request logic.

Q211 How do you emulate a specific timezone and locale for a browser context, and why does it matter?

browser.newContext({ timezoneId: 'Asia/Kolkata', locale: 'en-IN' }) makes the browser report that timezone/locale to JS APIs like Intl and Date, letting you deterministically test date/time and locale-formatted displays regardless of what timezone the CI machine itself is actually running in — critical since CI runners are usually UTC and would otherwise mask locale bugs.

Q212 How do you handle a native multi-select<select multiple>dropdown in Playwright?

locator.selectOption([...]) accepts an array of values/labels and selects all of them at once on a multi-select element, replacing whatever was previously selected — you can pass values, labels, or element handles depending on what’s easiest to identify the options by.

Q213 How would you test a custom web component end-to-end?

Since a custom element’s internal shadow root is still accessible to Playwright’s piercing locators, you interact with it largely like any other element — the main extra consideration is waiting for the custom element to be fully “upgraded”/hydrated (its connectedCallback having run) before interacting, which usually just falls out of Playwright’s normal actionability waits but is worth being aware of for components with async initialization.

Q214 How do you enumerate all frames on a page usingpage.frames(), and when is that useful?

page.frames() returns every frame (main + all iframes) currently attached to the page as a flat list — useful for debugging (logging what frames exist when a locator can’t find something) or for a generic utility that needs to search across every frame without knowing their structure ahead of time, whereas frameLocator() is for when you already know which specific iframe you want to target.

Q215 How would you reliably test content that only renders once it scrolls into view?

Use locator.scrollIntoViewIfNeeded() to trigger the scroll, then assert with a normal toBeVisible()/toHaveText() — Playwright’s auto-waiting will hold until the lazy-loaded content actually appears (image loaded, IntersectionObserver callback fired), so you don’t need a manual wait as long as you scroll first and then assert.

Q216 What istoBeInViewport(), and how does it differ fromtoBeVisible()?

toBeVisible() checks the element is rendered and not hidden by CSS, regardless of whether it’s currently scrolled into the visible viewport. toBeInViewport() additionally checks it’s actually within the current scrollable viewport area — useful for testing things like “above the fold” placement or verifying an element that should require scrolling to reach isn’t accidentally visible without scrolling.

Q217 How would you test a “you have unsaved changes”beforeunloadbrowser warning?

Playwright auto-dismisses beforeunload dialogs by default; to test the behavior itself, you listen for the dialog event before triggering navigation and assert one fires, or check the page’s own custom in-app “unsaved changes” modal if the app implements its own instead of relying on the native browser prompt (which is increasingly common since native beforeunload dialogs are hard to customize).

Q218 How would you assert on an element’s exact pixel position/size usingboundingBox()?

await locator.boundingBox() returns { x, y, width, height } relative to the viewport, which you can assert directly for layout-sensitive tests (e.g., confirming two elements are aligned, or an element doesn’t overlap another) — useful for precise layout regression checks that a screenshot diff would flag but not explain numerically.

Q219 How would you test cross-tab communication implemented viaBroadcastChannelorlocalStorageevents?

Open two pages within the same BrowserContext (they share localStorage/BroadcastChannel scope), perform the triggering action on one page, and assert the other page’s UI updates in response — this validates the actual cross-tab messaging mechanism rather than just each tab’s behavior in isolation.

Q220 What is Playwright’s clock emulation (page.clock) used for?

page.clock.install() lets you control the page’s notion of time — fast-forwarding it, pausing it, or setting it to a fixed value — so you can deterministically test time-dependent UI (a countdown timer, a “session expires in 5 minutes” banner, a scheduled auto-save) in seconds instead of actually waiting real minutes for the behavior to occur.

Q221 How would you test that localStorage, sessionStorage, and IndexedDB are each cleared/isolated correctly between tests?

Since each test gets a fresh BrowserContext by default, all three are naturally isolated per test without extra work — to explicitly verify this isn’t broken (e.g., by a shared persistent context misconfiguration), I’d assert at the start of a test that these stores are empty, or intentionally write to them in one test and assert a following test doesn’t see that data.

Q301 What islocator.pressSequentially(), and when would you use it instead offill()?

fill() sets an input’s value directly in one atomic step, which is fast but skips real per-key events — pressSequentially() dispatches an actual keydown/keyup/input event for each character, simulating real typing. Use it when the field genuinely depends on per-keystroke behavior (a debounced live search, a masked input that reformats as you type, a custom autocomplete) where fill() wouldn’t trigger the same JS handlers.

Q302 How do you generate a PDF of a page usingpage.pdf(), and what are its limitations?

await page.pdf({ path: 'out.pdf', format: 'A4' }) renders the current page to PDF — but it only works in Chromium running in headless mode, so it can’t be part of a cross-browser matrix, and it’s better suited to generating a snapshot for a downstream check (e.g., an invoice’s printable layout) than to asserting on PDF content directly, which needs a separate PDF-parsing library.

Q303 How would you test that a Content Security Policy (CSP) violation is correctly reported by the browser?

Listen for page.on('console') messages matching CSP violation text, or better, assert on the actual report-uri/report-to endpoint receiving a violation report via page.route() when a deliberately CSP-violating script is injected — confirming both that the policy blocks the disallowed content and that violations are actually reported, not just silently swallowed.

Q304 What istestInfo.parallelIndex, and how might you use it to avoid data collisions between parallel workers?

It’s the numeric index (0, 1, 2…) of the worker currently running the test, stable for that worker’s lifetime — you can use it to derive worker-unique test data (e.g., a distinct database schema or a range of reserved IDs per worker) so parallel workers never collide on shared resources without needing fully random IDs for every single test.

Q305 How would you handle test flakiness caused by web font loading affecting layout/measurements?

I’d wait explicitly for fonts to be ready via document.fonts.ready (accessible through page.evaluate()) before taking a screenshot or measuring layout, since a page can be “loaded” by Playwright’s definition while a web font is still swapping in and shifting text width/height — a classic source of visual-regression false failures that has nothing to do with the actual application logic.

Q306 How would you test behavior involving the browser’s back/forward cache (bfcache)?

Navigate away from a page and then use the browser’s back button (page.goBack()) to trigger a potential bfcache restore, then assert the page’s state (e.g., a form’s contents) is preserved as expected — and separately test that anything that should specifically prevent bfcache (like an open WebSocket, in some browsers) actually does, if that’s a documented requirement for the app.

Q307 What is the difference betweenpage.unroute()and callingroute.continue()?

route.continue() is a per-request decision made within a route handler to let that specific intercepted request proceed to the network unmodified. page.unroute() removes the route handler itself so it stops intercepting future matching requests entirely — one is a per-call action inside the handler, the other deregisters the handler.

Q308 How would you test a scroll-snap carousel component reliably?

I’d trigger navigation via the carousel’s actual controls (next/prev buttons or keyboard) rather than simulating raw scroll/swipe gestures where possible, since that’s more stable and closer to real user interaction, then assert on the resulting active-slide indicator or the visible slide’s content rather than trying to assert on precise scroll-position pixel values, which tend to be brittle across browsers.

Q309 How would you test an application protected by HTTP Basic Authentication?

browser.newContext({ httpCredentials: { username, password } }) supplies the credentials automatically for every request in that context, so the native browser Basic Auth prompt never appears — letting the test proceed straight to the actual application content instead of needing to interact with an OS-level auth dialog.

Q310 How would you recover a test gracefully if the browser crashes mid-run?

Playwright surfaces this as a crash event on the page/browser you can listen for, but practically I rely on the test runner’s built-in retry mechanism to simply re-run the test in a fresh browser instance — a genuine browser crash is rare enough that “retry it cleanly” is more pragmatic than building custom recovery logic within the test itself.

Q311 How would you test video playback controls for an HTML5<video>element?

Since <video> exposes a real DOM API, I assert on its properties directly via page.evaluate() — video.paused, video.currentTime, video.duration — after triggering play/pause/seek through the UI controls, rather than trying to visually confirm playback, which is far less precise and more flaky.

Q312 What are Playwright “setup projects,” and how do you use them for shared one-time global setup?

A setup project (marked via testMatch for setup files, referenced by other projects’ dependencies: ['setup'] in the config) runs once before its dependent projects and can, for example, perform authentication and save storageState — Playwright’s more structured, composable evolution of a single globalSetup function, letting different projects depend on different setup chains if needed.

Q313 How would you managestorageStateacross multiple domains/subdomains for a single authenticated session?

storageState captures cookies scoped to whichever domains were visited during its capture, so as long as the login flow actually visits every relevant subdomain (e.g., both app.example.com and api.example.com if the API sets its own cookie) before saving state, all of them get included — the key is making sure the capture step exercises the full real login flow, not just the primary domain.

Q314 How would you test global keyboard shortcuts that aren’t tied to a specific focused element?

Trigger the key combination at the page level (page.keyboard.press('Control+K')) without first focusing a specific input, since global shortcuts are typically bound at the document/window level — then assert on the resulting UI change (a command palette opening, for example) the same as any other action.

Q315 How would you useroute.continue()to modify a request’s method or POST body before it’s sent? 
await page.route('**/api/submit', route =>
  route.continue({ method: 'POST', postData: JSON.stringify({ ...JSON.parse(route.request().postData()!), injected: true }) })
);

This lets you tamper with an outgoing request for a specific test (e.g., testing how the backend handles an unexpected extra field) without needing to change the front-end code that constructs the request.

Q316 What islocator.highlight(), and how is it useful during local test development?

It visually outlines the matched element directly in the browser (with Playwright’s Inspector running), letting you instantly confirm a locator is targeting the element you expect before writing the rest of the test — much faster feedback than writing an assertion and running the whole test to find out a locator is wrong.

Q317 How would you test that ARIAaria-labelledby/aria-describedbyreferences resolve to the correct accessible name/description?

I use getByRole() with the name option, which computes the accessible name the same way assistive tech does — following aria-labelledby references, falling back to visible text — so asserting the role/name combination resolves correctly indirectly validates the reference is wired up right; I’d complement this with an ARIA snapshot for a fuller structural check.

Q318 How would you test an application’s handling of an HTTP redirect chain?

page.goto() follows redirects transparently by default and response.request().redirectedFrom() lets you walk backward through the chain to assert on the actual sequence of URLs and status codes — useful for confirming a legacy URL correctly redirects through the expected hops to its final destination without an unexpected extra hop or redirect loop.

Q319 What iscontext.exposeBinding(), and how does it differ fromexposeFunction()?

Both let page-side JS call back into Node, but exposeBinding()’s callback also receives a source object with details about the calling frame/page, useful when the same binding needs to behave differently depending on which frame invoked it (e.g., in a multi-iframe page) — exposeFunction() is the simpler version when you don’t need that context.

Q320 How would you test a feature that depends on WebRTC/camera-microphone media streams?

Launch the browser with fake media device flags (Chromium supports --use-fake-device-for-media-stream and --use-fake-ui-for-media-stream) so the app receives a real, deterministic synthetic video/audio stream instead of needing an actual physical webcam — combined with granting the camera/microphone permissions on the context.

Q321 How would you test that a service worker correctly prompts the user to refresh when a new version is available?

Load the page with an old service-worker version registered, then trigger a deploy of a new version (or mock the update check), and assert the app’s “new version available — refresh” UI element appears — this specifically exercises the update-detection and user-prompt logic, which is easy to leave completely untested since it only matters after a real deploy in production.

Q322 How would you use Playwright’s codegen with--save-storageto bootstrap an authenticated recording session?

npx playwright codegen --save-storage=auth.json https://app.example.com opens a browser where you manually log in once, and on closing, saves the resulting storageState to that file — letting you then continue recording (or writing) tests against already-authenticated pages instead of the recorder capturing the login flow itself every single time.

Section B — Framework Design & Architecture (Q26–337)

Q26 How do you structure a Playwright TypeScript framework for scalability?

I separate by concern: /pages (Page Object classes), /tests (mirroring the app’s feature areas), /fixtures (custom fixtures, auth setup), /utils (data generators, API clients, helpers), /config (environment-specific settings), and /test-data. Page objects only expose actions and getters, never assertions — assertions live in the test file so failures are attributed to the right layer. This keeps the framework navigable as it grows past a few hundred tests.

Q27 What is the Page Object Model, and how do you implement it cleanly in Playwright?

POM encapsulates a page’s locators and interactions behind a class, so tests read like business steps (loginPage.login(user, pass)) instead of raw selector calls, and a UI change only requires updating one class instead of every test that touches that element. In Playwright I define locators as class properties initialized from the Page object in the constructor, expose intention-revealing methods, and keep the page object free of expect() calls — verification stays in the test.

Q28 How do you avoid a “God object” page class that tries to do everything?

I split by logical section rather than physical page — a checkout page might become CheckoutFormComponent, PaymentSectionComponent, and OrderSummaryComponent, each with a single responsibility, composed together where needed. If a class is accumulating unrelated methods or growing past a few hundred lines, that’s my signal to split it.

Q29 How would you design a framework to support multiple environments (dev/QA/staging/prod)?

Environment-specific values (base URL, credentials, feature flags) live in separate config files or .env.<environment> files, loaded based on an ENV variable at runtime — never hardcoded in tests. The playwright.config.ts reads this and sets baseURL accordingly, and CI pipelines pass the target environment as a parameter so the same test code runs unmodified against any environment.

Q30 How do you manage test data to keep tests independent and parallel-safe?

I favor generating fresh, unique data per test (random emails/usernames via Faker) rather than relying on shared static fixtures, so parallel workers never collide on the same record. For data that must pre-exist, I seed it via API/DB calls in a fixture’s setup and tear it down afterward — never depend on manually-seeded data that could be mutated by another test.

Q31 What’s your strategy for keeping locators resilient to UI refactors?

Priority order: getByRole/getByLabel/getByText (accessibility-based, most stable) → data-testid attributes (stable but require dev buy-in to add) → scoped CSS selectors as a last resort. I actively push back on relying on auto-generated classnames or deep DOM-position selectors like div > div:nth-child(3) > span, since those break on any restructuring.

Q32 How do you decide what NOT to automate?

Anything that changes constantly (still-in-flux UI), is one-off/rarely executed, requires subjective human judgment (visual aesthetics beyond pixel-diffing, usability), or where the cost of maintaining the automation exceeds the cost of occasionally running it manually. I weigh automation ROI against maintenance burden, not just “can it be automated.”

Q33 How do you handle shared components (nav bar, modals) across many page objects?

I create reusable component classes (e.g., NavBarComponent) instantiated once and composed into every page object that includes that UI element, rather than duplicating locators/methods across pages. This mirrors how the actual application composes shared UI, and a change to the nav bar only needs a fix in one place.

Q34 What is the AAA (Arrange-Act-Assert) pattern, and why does it matter?

Arrange (set up preconditions/data), Act (perform the action under test), Assert (verify the outcome) — structuring every test this way makes it immediately scannable for what’s being tested and keeps unrelated setup logic out of the assertion section. I enforce this in code review; tests that interleave actions and assertions randomly are harder to debug when they fail.

Q35 How would you migrate a large legacy Selenium/Java suite to Playwright/TypeScript?

I’d do it incrementally, not as a big-bang rewrite: run both frameworks in parallel during the transition, prioritize migrating the highest-value/most-flaky suites first (biggest immediate ROI), extract a shared “critical user journeys” list to make sure nothing is lost, and set a hard cutover date for the legacy suite once coverage parity is confirmed. I’d also use the migration as an opportunity to fix known anti-patterns rather than just porting bad patterns 1:1.

Q36 How do you enforce coding standards across a team contributing to the same framework?

ESLint + Prettier enforced via a pre-commit hook and a CI check that fails the build on violations, a documented style guide (naming conventions, POM rules, no hardcoded waits), and PR review checklists. I also try to catch systemic issues early by adding a custom ESLint rule (e.g., banning page.waitForTimeout) rather than relying on manual review to catch it every time.

Q37 How would you design a fixture for role-based logins (admin/user/guest)?

A parametrized fixture that accepts a role, looks up (or generates) credentials for that role, performs API-based login, and returns an authenticated page/context — tests simply declare test('...', async ({ adminPage }) => {...}) or use test.use({ storageState: getStorageStateFor('admin') }). This avoids re-implementing login logic per test and keeps role-switching declarative.

Q38 How do you organize a framework that has both UI and API tests?

Separate projects in the config (ui, api) so they can be run independently or together, with API tests using the request fixture directly and UI tests reusing shared API helpers for setup (e.g., creating a user via API before testing the UI login flow). Reporting stays unified since both run under the same test runner.

Q39 What’s your approach to logging/observability within a framework without being noisy?

I log key business-level steps (test.step() blocks — “Logging in as admin”, “Adding item to cart”) rather than every low-level action, so failures are easy to localize in the report, and I attach richer diagnostics (network logs, custom state dumps) only on failure, not on every passing run, to keep noise down.

Q40 How would you handle a framework where a shared change breaks many downstream tests?

Treat framework code with the same rigor as application code — PRs against shared page objects/fixtures require running the full affected suite (or at least a representative smoke set) in CI before merge, not just unit-level checks. I’d also version critical shared utilities if multiple teams depend on the framework at different paces, so a breaking change doesn’t force an unplanned migration on everyone simultaneously.

Q121 How would you design a “test data builder” that lets tests override only the fields they care about?

A builder function returns a sensible default object and accepts a partial override, merging the two — e.g., buildUser({ role: 'admin' }) returns a fully valid user object with every field defaulted except role. This keeps tests focused on what actually matters for that scenario instead of every test having to specify every field, and it stays resilient when new fields are added to the model since defaults live in one place.

function buildUser(overrides: Partial<User> = {}): User {
  return { id: uuid(), email: faker.internet.email(), role: 'user', ...overrides };
}
Q122 How do you validate yourplaywright.config.tsitself is correct before it silently misconfigures a whole CI run?

I keep the config in TypeScript (not JSON) so type errors are caught at compile time, add a lightweight smoke check in CI that runs npx playwright test --list first (fails fast if the config is broken, before spending time on the actual browser run), and avoid environment-specific logic scattered across many files by centralizing it in one validated config-loader function.

Q123 How would you design a framework plugin system so teams can add fixtures without touching core code?

Core framework exports a base test object; individual teams create their own test.extend() layer in their own package/folder that adds team-specific fixtures on top of the shared base, without modifying the shared repo. This mirrors how Playwright itself is designed (fixtures are composable by nature) and avoids a single shared file becoming a bottleneck for every team’s changes.

Q124 How do you share a common framework across multiple repositories/teams without creating tight coupling?

Publish the shared logic (base page objects, fixtures, API clients, config loader) as a versioned internal npm package rather than copy-pasting or using a git submodule — teams pin to a version and upgrade deliberately, so a breaking change in the shared package doesn’t silently break every consuming repo’s next CI run.

Q125 What tagging strategy would you use to distinguish smoke, regression, and slow tests?

Tag tests using Playwright’s @tag syntax in the title or test.info().annotations (e.g., test('login works @smoke', ...)), then run subsets with --grep @smoke for fast PR checks and the full untagged set for nightly regression. I keep tags to a small, well-documented set (@smoke, @slow, @flaky-quarantine) rather than letting an unstructured tag taxonomy grow unmanageably.

Q126 How would you plan a major Playwright version upgrade across a large existing suite with minimal breakage?

Read the release’s breaking-changes notes first, upgrade in a separate branch, run the full suite against it before merging, and fix issues in small batches rather than all at once. I’d also pin the exact version in package.json (not a caret range) so an upgrade is always a deliberate, reviewed action rather than something that happens silently on a fresh npm install.

Q127 What documentation would you consider essential for a new SDET joining a framework you built?

A README covering: how to run tests locally, the folder structure and where things live, the locator strategy/conventions the team follows, how auth/test data setup works, how to debug a failing CI run, and a short “common gotchas” section — I prioritize documentation that answers the first questions a new person actually asks, not an exhaustive but rarely-read architecture doc.

Q128 How would you use a CODEOWNERS file to manage review responsibility for shared framework code?

Map high-blast-radius paths (/fixtures/, /pages/base/, /playwright.config.ts) to specific senior owners who must approve any PR touching them, while leaving individual feature-level test files open to normal team review — this concentrates scrutiny where a mistake would affect everyone, without creating a bottleneck for routine test additions.

Q129 How would you design a dashboard to track flaky-test trends over time?

Store per-test pass/fail/retry outcomes from every CI run (test name, status, duration, retry count) in a simple database or time-series store, then visualize flakiness rate per test over a rolling window — a test that passes on retry 30% of the time is a very different problem from one that fails outright, and the dashboard should distinguish them so triage is prioritized correctly.

Q130 How do you decide the right level of abstraction between raw Playwright calls and an over-engineered DSL?

I abstract repeated, multi-step business actions (checkoutPage.completePurchase(cardDetails)) but avoid wrapping single Playwright calls in trivial one-line helpers that just rename the API — the test should still read naturally as “what is this test actually doing” without forcing every reader to jump into a dozen tiny wrapper functions to understand one line.

Q131 How would you handle secrets rotation without breaking scheduled CI runs?

Store secrets in a centralized secret manager (not hardcoded in CI config) referenced by name, so rotating the underlying value doesn’t require any pipeline change — and I’d add a lightweight pre-flight check in scheduled runs that fails fast with a clear “auth failed” message rather than letting a rotated secret cause confusing downstream test failures across the whole suite.

Q132 How would you set a “performance budget” for your test suite and enforce it over time?

Define a target max execution time (e.g., smoke suite under 5 minutes, full regression under 30), track actual duration per CI run, and fail or flag the build if it regresses past a threshold — treating suite performance as a metric to protect, not just something that quietly degrades until someone complains it’s “always been slow.”

Q133 How do you deprecate an old page object/helper method without breaking every test using it immediately?

Mark it @deprecated with a JSDoc comment pointing to the replacement, have it log a console warning (or fail only in a stricter lint pass) rather than throwing, and set a removal deadline communicated to the team — this gives consumers time to migrate on their own schedule instead of a single PR breaking dozens of unrelated tests at once.

Q134 How would you structure a framework to support both cloud-grid execution (e.g., BrowserStack) and local runs interchangeably?

Keep the connection details (local vs remote WebSocket endpoint) entirely in the config/environment layer, never in test code — tests interact only with the standard page/context fixtures regardless of where the browser is actually running, so switching between local and cloud execution is a config change, not a code change.

Q135 How do you handle two teams needing conflicting configuration defaults from the same shared framework?

Push team-specific differences down into each team’s own project entry in the shared config (or their own config that extends a shared base) rather than trying to force one global default that satisfies everyone — shared framework code should expose sensible extension points, not assume every consumer wants identical behavior.

Q222 How would you decide between a BDD framework (Cucumber-style Gherkin) versus plain Playwright Test syntax for a team transitioning from Selenium/Cucumber?

Gherkin’s value is giving non-technical stakeholders (product, business) a readable spec they can actually review — if that collaboration genuinely happens, BDD is worth the extra layer of indirection; if “Given/When/Then” is only ever written and read by engineers, it’s often just ceremony that adds an extra mapping layer between the readable step and the actual Playwright code, making tests slower to write and debug for no real audience benefit. I’d make the call based on who actually reads the specs, not habit from a previous stack.

Q223 How would you design a test-ownership matrix for a large shared suite?

Map each test folder/tag to the team whose feature it covers (often mirroring the app’s own service/module boundaries), enforced loosely via CODEOWNERS and more strongly via an on-call-style rotation for triaging failures in shared/cross-cutting suites — the goal is that a failing test always has an obvious first point of contact instead of becoming “everyone’s problem, so no one’s.”

Q224 What semantic-versioning strategy would you apply to a shared internal test framework package?

Standard semver: patch for bug fixes/non-breaking internal improvements, minor for new backward-compatible features (a new fixture, a new helper), major for anything that requires consumers to change their test code — paired with a changelog and, for major bumps, a migration guide, since a breaking change in a shared framework silently landing via an unpinned dependency range is exactly the kind of thing that causes a Monday morning full of red pipelines across every team.

Q225 How would you integrate a dedicated visual-testing tool like Percy or Applitools, and when is that preferable to Playwright’s built-in comparison?

These tools add perceptual/AI-based diffing (ignoring anti-aliasing noise, cross-browser rendering differences) and a proper review UI for approving visual changes across many screenshots at once — worth adopting once visual regression testing scales beyond a handful of screenshots that a developer can eyeball in a PR diff; for a small, targeted set of visual checks, Playwright’s built-in toHaveScreenshot() is usually sufficient and avoids an extra paid dependency.

Q226 How would you design a framework to test a micro-frontend architecture with multiple team-owned page sections?

I’d structure page objects/component objects along the same boundaries as the micro-frontends themselves (so a team’s page object maps 1:1 to what they actually own and can update independently), and rely on contract-style assertions at the integration points between micro-frontends rather than assuming any one team’s test suite has full visibility into another team’s internal implementation.

Q227 How would you build a reusable “pre-test hook” library to consistently dismiss cookie-consent banners across every test?

A shared beforeEach/auto-fixture that checks for and dismisses the known consent banner selector if present (using a short timeout so it doesn’t slow down runs where it’s absent), applied globally once in the framework rather than every individual test file needing to remember to handle it — this is exactly the kind of repetitive, easy-to-forget boilerplate that belongs in shared framework code, not scattered across hundreds of tests.

Q228 How would you add observability to your test framework to understand where CI time is spent?

Emit structured timing data (per-test, per-stage — install, browser launch, execution, report upload) to a metrics/tracing backend on every run, so you can answer “where did the 45 minutes actually go” with data instead of guessing — this becomes essential once a suite is large enough that intuition about what’s slow stops being reliable.

Q229 Would you build a custom internal CLI wrapper aroundnpx playwright test, and what would it add?

Yes, for things the raw command doesn’t natively do for your org: auto-selecting the right environment config based on a flag, validating required env vars are set before running (failing fast with a clear message instead of a confusing mid-run error), or wiring in your team’s specific reporting/notification conventions — the goal is reducing the chance of someone running tests against the wrong environment by accident, not reinventing Playwright’s actual test execution.

Q230 How do you handle test ownership when a single end-to-end test spans multiple services owned by different teams?

I favor keeping genuinely cross-service E2E tests to a deliberately small, high-value set (critical user journeys only) owned jointly with a clear primary maintainer, while pushing most coverage down to be as close as possible to the team that owns that specific piece — broad E2E coverage that nobody clearly owns tends to rot fastest.

Q231 How would you structure a framework to run the same test against multiple feature-flag variants of a UI?

Parametrize the test (or the fixture that sets up the browser context) with the flag state, and use Playwright’s projects or a data-driven loop to run the same logical test once per variant — keeping the actual test logic written once, with only the flag-setup step differing per run, rather than duplicating whole test files per variant.

Q232 What naming convention would you enforce fordata-testidvalues across a large team?

A predictable, hierarchical pattern (e.g., feature-component-element, like checkout-payment-submit-button) documented and lint-enforced where possible, so IDs are both human-guessable without cross-referencing the source and naturally avoid collisions between unrelated features — an unstructured free-for-all inevitably produces duplicate or ambiguous IDs as the app grows.

Q233 How would you approach evaluating build-vs-buy for test tooling?

Weigh total cost of ownership, not just sticker price — a “free” in-house dashboard still costs ongoing engineering time to maintain, while a paid tool has a licensing cost but offloads that maintenance; I’d lean toward buying for genuinely commoditized capability (reporting dashboards, visual diffing services) and building only for things tightly coupled to how your specific team actually works, where an off-the-shelf tool would force an awkward compromise.

Q234 What would you include in a framework “runbook” for common CI failures?

A short, searchable list of “if you see X error, it usually means Y, try Z” entries built from real recurring incidents (flaky third-party dependency, expired test credentials, a known infra hiccup) — the goal is that a non-framework-owner engineer can self-serve through the most common failure modes without pinging the framework owner every single time, which is what actually determines whether a framework scales past one person’s bandwidth.

Q235 How would you decide when a growing set of custom helpers has crossed into “we’ve built our own DSL,” and whether that’s a problem?

It’s a smell (not necessarily a hard problem) when a new team member needs to learn your helpers before they can read a Playwright test that would otherwise be self-explanatory to anyone who knows Playwright — I periodically audit whether a helper is genuinely earning its abstraction (hiding real complexity) versus just renaming a one-line Playwright call, and prune the latter.

Q236 How would you structure a framework’s README and contribution guide to keep pace with a growing team?

Keep it a living document owned by whoever last touches a given area (not a single person’s static writeup that goes stale), require a “docs updated” checkbox on PRs that change framework conventions, and periodically prune sections that no longer reflect reality — a README that’s wrong is often worse than no README, since it actively misleads instead of just being silent.

Q323 How would you design a framework to consistently assign the same A/B test bucket to a given test run?

Force the bucket assignment via a test-only override (a query param, header, or cookie the app respects specifically in test environments) rather than relying on the app’s real randomized assignment logic — so a given test deterministically exercises “variant A” or “variant B” instead of flipping unpredictably between runs.

Q324 What are the trade-offs between inline test data in code versus external fixture files?

Inline data keeps a test fully self-contained and readable without jumping to another file, which is ideal for small, test-specific values — external fixture files (JSON/YAML) are better for larger, reused datasets shared across many tests, but add a layer of indirection and a risk of the fixture silently drifting out of sync with what the tests actually assume about it. I lean inline by default and extract to a shared fixture only once genuine duplication appears.

Q325 How would you structure a framework using a “feature-first” folder layout versus a “layer-first” layout?

Feature-first (/checkout/checkout.page.ts, /checkout/checkout.spec.ts grouped together) keeps everything related to one feature in one place, which scales better as the app and team grow since a feature team can work almost entirely within their own folder — layer-first (/pages/, /tests/, /fixtures/ as top-level folders) is simpler for a small framework but becomes harder to navigate once there are dozens of unrelated features spread thinly across each layer folder.

Q326 How would you automate onboarding setup for a new engineer joining your framework?

A single setup script (npm run setup) that installs dependencies, installs Playwright browsers, verifies required env vars/credentials are present with clear error messages if not, and runs one known-good smoke test to confirm everything works end to end — turning “read three docs pages and hope you didn’t miss a step” into one command with a clear pass/fail signal.

Q327 Where would consumer-driven contract tests live relative to your Playwright E2E tests?

I’d keep them in a clearly separate suite/folder (often even a separate CI job) since they test a fundamentally different thing — the API contract between two services, independent of any UI — and typically run on every commit to either the consumer or provider service, faster and more targeted than a full E2E run.

Q328 Would you configure test retries globally or per-test?

Globally as a baseline (2 retries in CI, 0 locally) so the whole team gets consistent behavior without remembering to configure it per file, but with the ability to override per-project for suites with different risk profiles (e.g., zero retries for tests specifically designed to catch flakiness itself, since retrying those would defeat their purpose).

Q329 How would you prioritize framework technical debt against feature-team requests for new coverage?

I’d frame debt items by their actual cost (how much CI time/flakiness/developer friction they cause weekly) so they compete for priority using the same currency as feature requests, rather than debt living in a separate, perpetually-deprioritized backlog — a slow, flaky framework silently taxes every future feature-coverage request anyway, so ignoring it isn’t actually neutral.

Q330 How would you design a framework to test multiple white-label/SKU variants of the same product?

Parametrize the framework by brand/SKU config (theming, feature flags, base URL) at the project level, sharing the same underlying test logic and page objects across variants wherever the UI is genuinely the same, and only branching test logic for the specific places where white-label behavior actually diverges — avoiding a full duplicate test suite per brand.

Q331 How would you measure whether a new framework abstraction has introduced a performance regression?

Track total and per-test execution time before and after the change across a representative CI run (not just anecdotally), since an abstraction that feels elegant in code review can still add real per-test overhead (extra fixture setup, unnecessary waits) that compounds across a large suite in ways that are easy to miss without measuring.

Q332 How would you build a requirements-traceability view mapping tests back to product requirements?

Tag tests with a requirement/ticket ID (e.g., @req-JIRA-1234) and build a lightweight report cross-referencing tagged tests against the requirements tracker — giving a concrete answer to “is this acceptance criterion actually covered by an automated test” for compliance-sensitive contexts (relevant given BFSI audit requirements) rather than relying on institutional memory.

Q333 How would you design schema-per-worker database isolation for parallel DB-touching tests?

Each worker, on startup, creates (or is assigned) its own isolated schema/database seeded with baseline data, and all its tests operate only within that schema — avoiding cross-worker data collisions entirely without needing every individual test to generate perfectly unique data, at the cost of some setup overhead per worker that’s worth it once true parallel DB testing is needed at scale.

Q334 How would you standardize error handling and logging conventions across a framework with many contributors?

A small shared logging utility (wrapping console or a proper logger) with defined severity levels and a consistent format, plus a documented convention for what belongs in a test.step() label versus a debug log versus a thrown error — enforced via code review initially and ideally via lint rules once the pattern is stable enough to codify.

Q335 What factors would push you toward writing a new framework in TypeScript from day one?

Type safety catches an entire class of framework bugs (a fixture returning the wrong shape, a typo’d config key) at compile time instead of as a confusing runtime failure deep into a CI run, and it makes a large, multi-contributor framework’s public API self-documenting via types — for anything beyond a small, short-lived script, I’d choose TypeScript by default rather than needing a special justification not to.

Q336 How would you design your framework to make it easy to delete tests that are no longer valuable?

Track basic usage signals (last time a test actually failed for a real reason, not flakiness; how long since the feature it covers last changed) to surface deletion candidates periodically, and normalize deletion as a legitimate, positive framework activity in code review culture — a framework that only ever grows accumulates dead weight that slows everyone down, and “no one wants to be the one who deletes a test” is a cultural problem worth addressing directly.

Q337 How would you structure shared “given” setup steps so many tests can reuse a specific app state without duplicating setup logic?

Encapsulate each common precondition (e.g., “a logged-in user with an active subscription and two items in cart”) as its own composable fixture or setup function, so a test simply declares the state it needs rather than re-deriving it step by step — this both reduces duplication and makes each test’s actual intent clearer, since the boilerplate precondition is abstracted away from the part that’s actually being tested.

Section C — API Testing (Q41–350)

Q41 Does Playwright support API testing, and how does it work?

Yes — via request fixture / APIRequestContext, which sends real HTTP requests (no browser needed) and returns an APIResponse you can assert on status, headers, and JSON body. It shares cookies/auth with the browser context if used together, which makes API-for-setup + UI-for-verification patterns very natural in the same test.

const res = await request.post('/api/users', { data: { name: 'Test' } });
expect(res.status()).toBe(201);
expect(await res.json()).toMatchObject({ name: 'Test' });
Q42 Why combine API calls for test setup instead of doing everything through the UI?

UI steps are slow and more failure-prone (every login/navigation is another chance for flakiness) purely to get to a starting state that isn’t actually what the test is verifying. Creating that precondition via a direct API call is faster, more reliable, and keeps the UI test focused on what it’s actually meant to validate — e.g., use the API to create an order, then use the UI only to test the order-cancellation flow itself.

Q43 How do you validate a JSON response schema?

I use a schema validation library (Ajv for JSON Schema, or Zod for TypeScript-native schemas) to assert the response shape/types match a defined contract, rather than manually asserting every field — this catches structural regressions (a field type change, a missing required field) that value-only assertions would miss.

Q44 How do you handle authentication tokens that expire during a long test run?

I build a wrapper around the API client that checks token expiry (or catches a 401) and transparently refreshes the token before retrying the original request, so individual tests don’t need to know or care about token lifecycle. For very long-running suites, I’ll also proactively refresh on a timer rather than waiting for a failure.

Q45 How would you test pagination in a REST API?

I verify the first page returns the expected page size and a valid “next” cursor/link, follow that link to confirm the next page returns different, non-overlapping records, and check boundary behavior — an out-of-range page returns an empty set (not an error), and the last page correctly indicates there’s no further page.

Q46 How do you test rate limiting on an API?

Fire requests up to (and just past) the documented limit and assert the response transitions to 429 Too Many Requests with the expected Retry-After/X-RateLimit-* headers, then confirm requests succeed again after the window resets. I isolate this into its own test (often against a lower test-environment limit) so it doesn’t slow down or destabilize the rest of the suite.

Q47 How do you validate error responses (4xx/5xx) are handled correctly?

I explicitly test the negative paths — missing required fields, invalid types, unauthorized access, non-existent resource IDs — asserting both the correct status code and a well-formed, non-leaking error body (no stack traces or internal details exposed). These are often under-tested compared to happy paths but are exactly where real bugs hide.

Q48 What is contract testing, and how does it differ from regular API testing?

Regular API testing verifies the API behaves correctly against its own expected behavior. Contract testing (e.g., Pact) verifies that a provider’s API still satisfies what a consumer actually expects/uses, catching breaking changes before they reach integration — especially valuable in a microservices architecture where teams deploy independently and a UI test alone wouldn’t catch a backend contract break until it’s already in a shared environment.

Q49 How would you test for broken object-level authorization (BOLA/IDOR)?

As User A, capture a resource ID (e.g., an order ID), then attempt to access/modify that same resource while authenticated as User B — the API should reject it (403/404), not return A’s data. This is one of the most common real-world API vulnerabilities and a straightforward automated check to add for any resource with an ID in the URL/payload.

Q50 How do you handle testing an API with headers like Content-Type, Accept, and custom auth headers consistently?

I set sensible defaults (base URL, default headers, default auth) once at the APIRequestContext level in the config or a fixture, so individual tests only override what’s different for that specific case, instead of repeating boilerplate headers in every request call.

Q51 How would you test a GraphQL API using Playwright?

Since GraphQL typically exposes a single POST endpoint, I send the query/mutation and variables as the JSON body via the same request fixture, then assert on the data/errors fields in the response — the difference from REST is mainly in how you construct the request payload and that errors can appear in a 200 response body, so I explicitly check the errors array even when the status is 200.

Q52 How do you organize API and UI tests within the same repository/framework?

Separate them into distinct projects in playwright.config.ts (or distinct top-level folders) so they can run independently, on different schedules if needed (API tests are cheap enough to run on every commit; full UI regression maybe less often), while still sharing common utilities like the data-generation and API-client helpers.

Q136 How would you test an OAuth2 authorization-code flow end-to-end?

For automation, I avoid driving the full interactive consent screen on every run where possible — instead I obtain a valid token once via a service account/test client credentials grant and inject it directly, reserving the full UI-driven OAuth redirect dance for a small number of dedicated tests that specifically verify the login/consent flow itself works.

Q137 How would you test a webhook-based integration where your system receives callbacks from a third party?

I stand up a mock endpoint (or use a tool that captures incoming webhooks) that the system under test’s webhook is configured to hit, trigger the action that should fire the webhook, then assert the mock received a correctly-shaped payload — for negative cases, I also test retry/backoff behavior when the receiving endpoint is temporarily unavailable.

Q138 How do you design tests to cover both old and new API versions during a migration period?

I parametrize the test suite with the API version as a variable (base URL or header), run the same logical test cases against both versions where behavior should be equivalent, and add version-specific tests only for the parts that intentionally differ — this catches accidental behavior drift in the “supposedly unchanged” parts of the old version during the migration.

Q139 How would you test a Server-Sent Events (SSE) endpoint?

Since SSE is a long-lived HTTP connection streaming events, I open the connection via fetch/EventSource inside page.evaluate() (or a Node HTTP client for pure API-level testing), collect emitted events into an array over a bounded time window, and assert on the sequence and content of events received rather than a single request/response pair.

Q140 How do you validate HTTP caching headers behave correctly for a cacheable resource?

I request the resource, capture the ETag/Last-Modified value, then make a conditional follow-up request with If-None-Match/If-Modified-Since and assert the server correctly returns 304 Not Modified (not re-sending the full body) — confirming the caching contract actually works rather than just checking the headers exist.

Q141 How would you test a large file upload/streaming API without keeping huge files in your repo?

Generate the file in-memory or on-disk at test runtime (a stream of repeated bytes up to the required size) rather than committing a large binary fixture, and clean it up after the test — this keeps the repo lean while still exercising realistic payload sizes.

Q142 How do you test a bulk import endpoint’s partial-failure behavior?

Submit a batch that deliberately mixes valid and invalid records, then assert the response correctly reports per-record success/failure (not an all-or-nothing result unless that’s the documented contract), and verify only the valid records were actually persisted — this is a commonly under-tested edge case that causes real production data issues.

Q143 How would you clean up test data created via API calls when running against a shared environment?

Track every resource created during a test (IDs returned from creation calls) in a list, and delete them in a teardown step regardless of pass/fail — I avoid relying on a full environment reset (which a shared environment usually can’t tolerate) and instead make cleanup a first-class, per-test responsibility.

Q144 How do you test that a deprecated API version returns a correct deprecation warning?

Assert the response includes the documented deprecation signal (a Deprecation/Sunset header, or a warning field in the body) alongside the still-functioning response, and separately verify the documented sunset date/behavior once that date passes in a lower environment where it can be simulated.

Q145 How would you approach testing an API secured with mutual TLS (mTLS)?

The test client needs to present a valid client certificate alongside the request, which the HTTP client library must be configured to attach — I’d verify both the happy path (valid cert accepted) and the negative path (missing/invalid/expired cert correctly rejected with the right error), since mTLS failures are a common source of confusing, hard-to-diagnose outages.

Q146 How do you test an async “fire a job, poll for completion” pattern reliably?

Kick off the job via API, then poll the status endpoint with expect.poll() (bounded by a reasonable max timeout) rather than a fixed sleep, and once “completed” is observed, assert on the actual result payload — I also add a distinct test for the “job failed” status path, which is often untested compared to the happy “completed” path.

Q147 How would you use snapshot testing for API responses, and what risks does it introduce?

Snapshotting a full response body and diffing future runs against it catches unintended structural changes with very little test-writing effort — but it’s prone to noisy false failures from legitimately-changing dynamic fields (timestamps, IDs) unless those are explicitly excluded/masked, and it can hide the intent of what’s actually being verified, making failures harder to interpret than an explicit, targeted assertion.

Q148 How would you test that one tenant’s API calls can never access another tenant’s data?

As Tenant A, attempt every operation (read, update, delete, list) against resources known to belong to Tenant B, using Tenant A’s valid credentials, and assert every one is correctly rejected or scoped away — I treat this as a first-class test suite in any multi-tenant system, not an afterthought, since a tenant-isolation bug is a severe security issue.

Q237 How would you test that an API correctly supports response compression viaAccept-Encoding?

Send a request with Accept-Encoding: gzip and assert the response includes a Content-Encoding: gzip header and the body is correctly compressed/decompressible, then send a request without that header and confirm the server falls back to uncompressed — catching a misconfiguration where compression is either always-on (breaking clients that can’t decompress) or silently never applied despite being configured.

Q238 How would you test an API’s circuit-breaker behavior when a downstream dependency is failing?

Simulate the downstream failure (via a mock or a chaos-testing hook in a lower environment), send enough requests to trip the breaker, and assert subsequent calls fail fast with the expected “circuit open” response instead of hanging on the real timeout — then confirm the breaker correctly transitions back to closed once the downstream is healthy again (the half-open recovery behavior).

Q239 How would you test that API responses differ correctly based on an active feature flag?

Toggle the flag via whatever mechanism the app uses (a test-only API endpoint, a header override, or a config value in a lower environment) and assert the response shape/content changes as expected for both states — I’d avoid needing entirely separate environments per flag combination, since that doesn’t scale as flag count grows.

Q240 How would you verify correlation/trace IDs propagate correctly through a chain of API calls?

Send an initial request with a known trace ID header, then inspect logs or a tracing backend (if accessible in the test environment) to confirm that same ID appears in every downstream service call triggered by that request — a broken trace-ID propagation is a “silent” bug that doesn’t break functionality but seriously hurts production debuggability, so it’s worth testing explicitly rather than assuming it works.

Q241 How would you test that a soft-deleted resource is correctly excluded from normal reads but still exists for audit purposes?

Soft-delete a resource via the API, confirm it no longer appears in standard list/get endpoints (404 or filtered out), then confirm it’s still retrievable through whatever audit/admin-only path is meant to still see it — the two behaviors are easy to accidentally couple (fixing one can silently break the other) so I test them as explicitly separate assertions.

Q242 How would you test a bulk-delete endpoint’s behavior when some requested IDs don’t exist or aren’t authorized?

Submit a mixed batch (valid IDs you own, IDs that don’t exist, IDs belonging to another user) and assert the response correctly reports per-ID outcome — the valid ones actually deleted, the invalid ones reported as not-found, and the unauthorized ones rejected — rather than the whole operation silently succeeding or failing as an opaque all-or-nothing unit when the contract says otherwise.

Q243 How would you test an API’s input coercion behavior for a numeric field sent as a string?

Send the same logical value in multiple shapes ("42", 42, "42.0", "abc") and assert the API’s behavior is consistent and documented — either it strictly rejects non-numeric types with a clear 400, or it coerces predictably — since silent, inconsistent type coercion is a common source of subtle downstream data bugs.

Q244 How would you test a REST API that supports sparse fieldsets or partial responses?

Request with a fields query param specifying a subset, and assert the response contains exactly those fields (no more, no less) — including edge cases like requesting a field that doesn’t exist (does it error, or silently ignore it?) and requesting zero fields.

Q245 How would you test that a duplicate webhook delivery is handled idempotently?

Send the identical webhook payload (same event ID) twice in a row and assert the receiving system only processes the side effect once (e.g., an order isn’t charged or fulfilled twice) — this is a very common real-world bug source since most webhook providers explicitly guarantee “at least once” delivery, not exactly-once, so the receiver must handle duplicates itself.

Q246 How would you design a basic smoke-level test for API behavior under load shedding/backpressure?

Rather than a full load test, I’d fire a controlled burst of concurrent requests against a lower environment configured with a known, low capacity threshold, and assert the API degrades gracefully (a proper 503/429 with a retry hint) instead of hanging, crashing, or silently dropping requests — a lightweight smoke check for “does the failure mode make sense,” not a substitute for real performance/load testing.

Q247 How would you test long-polling behavior where a client holds a request open until new data or a timeout?

Send the long-poll request, then trigger the event that should produce new data from a separate call, and assert the held request resolves promptly with that data (not waiting out its full timeout) — separately, test the timeout path itself by not triggering new data and confirming the request correctly resolves (typically with an empty/no-change response) once the timeout elapses.

Q248 How would you verify an API correctly returns 404 (not a stale cached response) immediately after a resource is deleted?

Delete the resource, then immediately request it again and assert a 404, paying particular attention if there’s a caching layer (CDN, reverse proxy) in front of the API — a common bug is the delete succeeding at the database level while a cache in front of the read path continues serving the now-deleted resource for its TTL, which this test explicitly catches.

Q249 How would you test that API request/response logging doesn’t leak sensitive fields in plaintext?

Send a request containing known sensitive values (a password, a token) and inspect the actual application/access logs the API produces, asserting those specific values never appear unmasked — this is a check I’d want run automatically, not just trusted to a code review, since logging statements are exactly the kind of thing that silently starts capturing a sensitive field after an unrelated refactor.

Q338 How would you test that pagination cursors can’t be tampered with to access unauthorized data ranges?

Capture a valid cursor as User A, then attempt to modify it (decode and alter an offset/ID if it’s not opaque, or simply reuse a cursor obtained under different auth) and submit it as User B, asserting the API correctly rejects or re-scopes it rather than returning data outside what User B is authorized to see — cursors are often wrongly assumed to be inherently safe just because they look opaque.

Q339 How would you test client-side handling of an API request that times out with no response?

Mock the endpoint to simply never respond (or delay well beyond the client’s configured timeout) via route interception, and assert the UI correctly shows a timeout-specific error state rather than hanging indefinitely or showing a generic/misleading error — this path is commonly under-tested since it requires deliberately simulating “nothing happens,” which is easy to overlook compared to testing explicit error responses.

Q340 How would you test optimistic concurrency control using ETag/If-Match headers?

Fetch a resource and its ETag, then have a second “concurrent” request update the same resource (changing its ETag), and assert that a follow-up update using the now-stale original If-Match value is correctly rejected with a 412 Precondition Failed — confirming the API actually prevents the classic lost-update race condition it claims to guard against.

Q341 How would you test a saga/orchestration API’s compensating-transaction behavior?

Deliberately fail a specific step partway through a multi-step orchestrated flow (e.g., payment succeeds but inventory reservation fails) and assert the system correctly triggers the compensating action for the already-completed steps (refunding the payment) rather than leaving the system in a partially-completed, inconsistent state — this is a high-value but frequently under-tested class of bug in distributed systems.

Q342 How would you test that an API gateway correctly transforms a request before forwarding it to a backend?

Send a request to the gateway and, in a test environment where the backend is mockable or observable, assert the request the backend actually received matches the expected transformed shape (headers added/renamed, path rewritten, auth token exchanged) — testing the gateway’s transformation logic as its own explicit contract, separate from testing the backend’s own behavior.

Q343 How would you approach testing a gRPC API?

Since it’s not plain HTTP/JSON, I’d use a gRPC-aware client library (generated from the same .proto definitions the service uses) rather than trying to force it through an HTTP-oriented tool — the core testing principles (positive/negative cases, contract validation) stay the same, but the tooling and request/response serialization are protocol-specific.

Q344 How would you validate that an API’s actual behavior matches its published OpenAPI specification?

Use a spec-validation tool (like Dredd, or a Zod/JSON-Schema validator generated from the OpenAPI doc) to automatically check real responses from the live API against what the spec promises, catching the common and quietly damaging drift where the spec is updated but the implementation isn’t (or vice versa), which manually-written assertions wouldn’t necessarily catch.

Q345 How would you test that rotating an API key doesn’t cause downtime for clients?

Verify the system supports a dual-key overlap period (both old and new keys valid simultaneously for a window), rotate the key in a test environment while a client is actively making requests, and assert zero failed requests throughout the transition — a naive “revoke old key the instant new key is issued” approach breaks any client that hasn’t yet picked up the new key, which is exactly what this test is meant to catch before it happens in production.

Q346 How would you test conditional GET requests using Last-Modified/If-Modified-Since?

Similar to the ETag case: request a resource, capture its Last-Modified header, then make a follow-up request with If-Modified-Since set to that value and assert a 304 Not Modified if unchanged — then update the resource and confirm the same conditional request now correctly returns a fresh 200 with the new content.

Q347 How would you test an API that supports both XML and JSON based on the Accept header?

Send functionally identical requests with Accept: application/json and Accept: application/xml and assert both return the same underlying data, correctly formatted for that content type — plus test the fallback/error behavior for an unsupported Accept value (406 Not Acceptable versus silently defaulting, whichever is the documented contract).

Q348 How would you test an API’s behavior with an unusually large number of query parameters or oversized query string?

Send a request with an excessive number of parameters or a query string near/beyond common server or proxy limits, and assert the API fails predictably (a clear 414 URI Too Long or similar) rather than crashing, hanging, or behaving inconsistently — a basic but often-skipped resilience check against malformed or abusive input.

Q349 How would you precisely test a rate limiter’s reset-window boundary?

Exhaust the limit, then time requests to land just before and just after the documented reset instant, asserting the pre-boundary request is still rejected and the post-boundary request succeeds — this requires careful control of timing (often via a controllable clock in the test environment rather than real wall-clock waiting) to reliably hit the exact boundary rather than a rough approximation.

Q350 How would you test that an API correctly rejects a reused idempotency key sent with a different payload?

Send a request with a given idempotency key and payload A (succeeds), then send a second request reusing the same key but with a different payload B, and assert the API explicitly rejects this as a conflict (since idempotency keys are meant to deduplicate identical retries, not silently accept a different operation under the same key) rather than either silently returning the original response or processing the new payload.

Section D — Database / SQL Testing (Q53–359)

Q53 Why would an SDET need SQL/DB knowledge for UI/API automation?

UI/API assertions only confirm what’s exposed to the user or the client, not what’s actually persisted correctly — verifying directly against the database closes that gap (e.g., confirming a “cancelled” order is actually flagged correctly in the DB, not just displaying “Cancelled” text that’s hardcoded). It’s also essential for efficient test data setup/teardown that doesn’t route everything through slow UI/API calls.

Q54 How do you connect to and query a database from a TypeScript test framework?

Using the appropriate driver (pg for Postgres, mysql2 for MySQL, mssql for SQL Server) wrapped in a small utility/fixture that manages connection pooling, so tests call a simple db.query(sql) helper rather than managing raw connections themselves — with the connection closed cleanly in a global teardown.

Q55 Write a query to find duplicate email addresses in auserstable. 
SELECT email, COUNT(*) AS cnt
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

GROUP BY collapses rows by email, and HAVING COUNT(*) > 1 filters to only groups that appear more than once — HAVING is required here (not WHERE) because the filter is on an aggregate.

Q56 Write a query to find the 2nd highest salary in anemployeestable without usingLIMIT/OFFSET. 
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

The inner query finds the overall max; the outer query finds the max salary strictly less than that — which is the second-highest. This pattern generalizes to the Nth-highest with nested subqueries, though a RANK() window function is cleaner for that case.

Q57 How would you design a teardown to roll back DB changes made during a test?

Wrap the test’s DB-affecting operations in a transaction that’s opened before the test and rolled back after (regardless of pass/fail), so nothing persists — this is the cleanest approach when the driver/DB supports it. When that’s not feasible (e.g., the app under test manages its own connections), I track every record created during the test and explicitly delete it in an afterEach, even on failure.

Q58 What precautions do you take to avoid tests polluting a shared database?

Generate unique, test-run-scoped data (prefixed identifiers, random suffixes) instead of fixed values that could collide across parallel workers or runs, and always clean up what you create — never assume a shared DB is “empty” or in a known state. For anything destructive, I test against an isolated schema/test DB, never a shared environment other teams depend on.

Q59 How would you validate referential integrity between two related tables (e.g., orphaned records)? 
SELECT c.* FROM child_table c
LEFT JOIN parent_table p ON c.parent_id = p.id
WHERE p.id IS NULL;

A LEFT JOIN from child to parent where the parent side comes back NULL means the child references a parent that no longer (or never did) exist — a direct way to catch data-integrity bugs after deletions or migrations.

Q60 How would you approach testing a database migration (schema change)?

Before/after comparison: capture row counts and key sample data pre-migration, run the migration against a copy of production-like data, then verify row counts match, no data was silently dropped/truncated, new columns have correct defaults/nulls where expected, and existing application queries still function against the new schema. I’d also explicitly test the rollback path, not just the forward migration.

Q149 How would you test that a database view returns correctly joined/aggregated data as underlying tables change?

I insert/update known data in the base tables, query the view, and assert its output reflects those changes correctly — including edge cases like a base-table row being deleted (does the view correctly stop showing it, or does a LEFT JOIN-based view show a null-padded row as expected).

Q150 How would you useEXPLAIN/EXPLAIN ANALYZEas part of a QA process to catch a query regression?

I’d capture the query plan (and actual execution time) for critical, frequently-run queries as a baseline, and flag it in review if a schema or query change causes the planner to switch from an index scan to a full table scan — this is a proactive check that catches performance regressions before they show up as a slow production endpoint.

Q151 How would you test that a database trigger fires correctly and produces the expected side effect?

Perform the triggering action (e.g., an INSERT that should fire an audit-log trigger), then directly query the table the trigger is supposed to affect and assert the expected row/change exists — treating the trigger’s effect as an implicit contract that needs its own explicit test, since triggers are easy to silently break with a later refactor.

Q152 How do you ensure a database seed/setup script is idempotent?

Use INSERT ... ON CONFLICT DO NOTHING (or the equivalent upsert) instead of plain inserts, and design the script to check for existing state before creating it — then test idempotency directly by running the script twice in a row and asserting the second run doesn’t error or create duplicates.

Q153 When would you choose direct DB setup over API-based test data setup?

API-based setup is generally preferred since it exercises real application logic and stays valid even if the schema changes underneath — but direct DB setup makes sense when you need to create data in a state the API can’t produce directly (e.g., simulating a legacy/corrupted record) or when API-based setup is too slow for the volume of data a test needs.

Q154 How would your approach to testing data integrity differ for a NoSQL database vs a relational one?

Without enforced foreign keys or schema constraints, integrity checks that a relational DB gives you for free (referential integrity, type constraints) have to be verified explicitly at the application/test level for NoSQL — so I’d write tests that specifically check for orphaned references and inconsistent document shapes that a schema would have prevented in a relational system.

Q155 How would you test that a data-masking/anonymization job correctly obscures PII?

Seed known PII values (a specific name, email, SSN pattern) into a source dataset, run the masking job, then assert the output no longer contains those exact values in any recognizable form — including checking that masked values aren’t trivially reversible (e.g., not just a predictable character-shift) if that’s a stated requirement.

Q156 How would you test a database migration’s rollback script?

Run the forward migration, capture a data snapshot, run the rollback, and assert the schema and data return to their pre-migration state (not just that the rollback script executes without error) — a rollback that “runs successfully” but silently loses data is a dangerous false sense of safety.

Q157 How would you test behavior under different transaction isolation levels?

I’d simulate two concurrent transactions (e.g., one reading while another writes and commits) under a given isolation level and assert the observed behavior matches what that level guarantees — for example, confirming a READ COMMITTED transaction sees the pre-commit value while a later read after commit sees the update, versus SERIALIZABLE correctly preventing an anomaly the weaker level would allow.

Q158 How would you validate a computed/generated column always reflects the correct derived value?

Update the source column(s) the computed column depends on, then query the row and assert the computed column recalculated correctly — including boundary cases like a NULL in a source column, which can produce unexpected results in the derived value if not explicitly handled by the computation logic.

Q250 How would you test that a full-text search feature returns relevant results ranked correctly?

Seed a known set of records with deliberately varying relevance to a search term (exact match, partial match, unrelated), run the search, and assert both that irrelevant records are excluded and that the ranking order matches expectations (exact matches ranked above partial ones) — testing relevance ranking, not just “did any results come back.”

Q251 How would you test a time-series data retention/downsampling job?

Seed raw data spanning the retention boundary, run the job, and assert: data older than the retention window is aggregated (not just deleted, if downsampling is meant to preserve historical trend data at lower granularity) and the aggregated values are mathematically correct against the raw data that fed them, while recent data within the window is left untouched.

Q252 How would you test how your application behaves when the database connection pool is exhausted?

In a controlled lower environment, deliberately configure a very small pool size and drive enough concurrent load to exhaust it, then assert the application handles the resulting wait/timeout gracefully (a proper error or queued retry) rather than crashing or hanging indefinitely — this surfaces a class of production incident that’s otherwise very hard to reproduce outside of real peak load.

Q253 How would you test for acceptable replication lag in a multi-region/read-replica setup?

Write to the primary, then poll the replica (with a bounded timeout) until the write appears, measuring the actual observed lag — and separately test the application’s own behavior when lag exceeds its tolerance (does a “read your own write” flow correctly route to the primary when needed, or does it show stale data?).

Q254 How would you validate a database backup and restore process produces a fully consistent, usable copy?

Periodically (not just once) actually restore a backup into an isolated environment and run integrity checks against it — row counts matching the source at backup time, referential integrity intact, and critically, that the application itself can actually start up and function against the restored data — since an untested backup is really just an assumption, not a verified safety net.

Q255 How would you test querying and indexing on a JSON/JSONB column?

Insert records with varying JSON structures (including missing keys, nested objects, arrays), then test that queries filtering on specific JSON paths return correct results, and — if a JSON-specific index (like a GIN index in Postgres) is meant to accelerate those queries — use EXPLAIN to confirm the index is actually being used rather than the database falling back to a full scan.

Q256 How would you detect schema drift between environments?

Run an automated schema comparison (via a migration tool’s built-in diff, or a custom introspection query comparing information_schema across environments) as a periodic or pre-deployment CI check, flagging any manually-applied change in one environment that isn’t reflected in the tracked migration history — catching the classic “it works in staging because someone manually added a column there” bug before it reaches production.

Q257 How would you test that a bulk update operation is fully transactional?

Deliberately construct a batch where one record in the middle would fail a constraint, run the bulk update, and assert that none of the records were updated (not a partial commit) if the operation is documented as atomic — this is a case where the happy-path bulk update working correctly tells you almost nothing about the failure-path guarantee, which is the actual risk.

Q258 How would you test correct handling of Unicode/emoji/accented characters given a table’s collation?

Insert records containing emoji, accented characters (é, ñ), and multi-byte Unicode, then verify they’re stored, retrieved, and displayed correctly (not mangled or truncated), and that sorting/searching on those columns behaves sensibly for the configured collation — a surprisingly common source of production bugs when a column’s character set wasn’t originally designed with non-ASCII input in mind.

Q259 How would you test that a composite index is actually being used by queries meant to benefit from it?

Run EXPLAIN/EXPLAIN ANALYZE on the specific query pattern the index was added for, and confirm the plan shows an index scan using that composite index rather than a sequential scan or a different, less optimal index — column order in a composite index matters a lot, so I’d also test that queries filtering on a non-leading column of the index don’t unexpectedly bypass it.

Q351 How would you test that your application correctly detects and retries on a database deadlock?

In a controlled test, deliberately construct two concurrent transactions that lock resources in opposite order (the classic deadlock setup), triggering the database’s deadlock detector, and assert your application’s retry logic catches the resulting error and successfully completes the operation on retry rather than surfacing the deadlock error directly to the user.

Q352 How would you test that a partitioned table’s queries correctly prune to only relevant partitions?

Run EXPLAIN on a query filtered by the partition key and confirm the plan shows only the expected partition(s) being scanned, not every partition in the table — a broken partition-pruning configuration silently degrades to scanning everything, which won’t produce wrong results but will produce a serious, easy-to-miss performance regression.

Q353 How would you test a database encryption-key rotation process without data becoming unreadable mid-rotation?

Seed known data, begin the rotation process, and at intervals during the rotation (not just before/after), attempt to read that data and assert it’s always successfully decryptable — specifically testing the in-progress state, since a rotation process that works correctly at the start and end but has a race condition mid-way is exactly the failure mode a “before and after only” test would miss.

Q354 How would you test a stored function/UDF for correctness the same way you’d unit test application code?

Call the function directly with a range of representative and edge-case inputs (including NULLs and boundary values) and assert its output against expected results, the same discipline as a unit test — stored logic often gets far less test rigor than application code purely because it’s less visible, not because it’s inherently less important or less likely to have bugs.

Q355 How would you test that your application’s database user follows least-privilege?

Attempt (in a test/staging environment, never production) operations the application user should NOT be able to perform — dropping a table, altering schema, reading a table outside the app’s scope — using the actual configured application credentials, and assert they’re correctly rejected by the database’s own permission system, not just assumed to be safe because “the app never does that.”

Q356 How would you explicitly testON DELETE CASCADEbehavior?

Seed a parent record with a known, specific set of dependent child records (plus at least one unrelated child record belonging to a different parent), delete the parent, and assert exactly its own children were removed — no more (the unrelated parent’s children untouched) and no less — since a misconfigured cascade can either fail to clean up or, more dangerously, cascade further than intended.

Q357 How would you test your application’s retry/backoff behavior after a transient database connection failure?

Using a proxy or fault-injection tool between the app and database (or a feature flag in a lower environment that simulates a connection drop), interrupt connectivity briefly during an operation and assert the application retries with appropriate backoff and eventually succeeds, rather than failing the user-facing request outright for what should be a transient, recoverable blip.

Q358 How would you compare keyset versus offset-based pagination performance on a large dataset?

Seed a large dataset, then benchmark deep-page requests (e.g., page 500) under both strategies — offset-based pagination typically degrades because the database must still scan and discard all preceding rows, while keyset (cursor-based) pagination stays roughly constant time since it seeks directly via an indexed column — making this a concrete, measurable QA finding to justify a pagination strategy choice rather than a purely theoretical one.

Q359 How would you test a database trigger that calls out to an external service?

I’d treat this as a red flag worth flagging in review as much as a test to write — a trigger with an external dependency introduces transactional risk (the DB transaction may hold locks while waiting on a network call, and a failed external call can leave things in an ambiguous state) — but if it exists, I’d test both the success path and, critically, what happens to the DB transaction when the external call fails or times out.

Section E — CI/CD: Jenkins & GitHub Actions (Q61–372)

Q61 How do you integrate Playwright tests into a CI/CD pipeline?

Install dependencies and Playwright browsers (npx playwright install --with-deps), run the test command with the appropriate reporter for CI (e.g., blob for later merging, or html), then archive the report and any traces/screenshots as build artifacts so failures are debuggable without re-running locally. The pipeline should fail the build on test failure and make the report easily accessible from the CI UI.

Q62 What is a Jenkinsfile, and why is it preferred over UI-configured Freestyle jobs?

A Jenkinsfile defines the pipeline as code (Declarative or Scripted syntax) checked into the repo alongside the application, so pipeline changes go through the same code review and version history as any other code change — instead of living as untracked, hard-to-audit UI configuration that only admins can see or modify.

Q63 How would you write a Jenkins pipeline stage to publish a Playwright HTML report?

Using the HTML Publisher plugin in a post block to point at the generated playwright-report directory, so the report becomes directly viewable from the build’s Jenkins page rather than requiring someone to download and open a zip file.

post {
  always {
    publishHTML(target: [
      reportDir: 'playwright-report', reportFiles: 'index.html',
      reportName: 'Playwright Report'
    ])
  }
}
Q64 How do you handle secrets (API keys, credentials) securely in Jenkins?

Store them in Jenkins’ built-in Credentials store (not in the Jenkinsfile or repo) and inject them into the pipeline via the credentials() binding, which also automatically masks the value in console logs so it’s never accidentally exposed in build output.

Q65 How would you configure parallel shards in a Jenkins pipeline?

Using declarative parallel stages, each invoking the test command with a different --shard=N/M value, so all shards execute concurrently on separate (or the same, if resourced) agents — followed by a final stage that downloads all shard artifacts and merges the blob reports into one.

Q66 What is the difference between a GitHub Actions workflow, job, and step?

A workflow is the whole automation defined in a YAML file (triggered by an event); it contains one or more jobs, which run in parallel by default (unless dependencies are declared via needs:) each on its own runner; each job contains a sequence of steps that run in order on that same runner, sharing its filesystem.

Q67 How do you speed up a GitHub Actions workflow that installs Playwright browsers every run?

Cache the Playwright browser binaries directory (and node_modules) using actions/cache, keyed on the lockfile hash and Playwright version, so subsequent runs restore from cache instead of re-downloading browsers every single time — this alone often cuts several minutes off each run.

Q68 How would you configure a matrix strategy to run tests across multiple browsers in GitHub Actions? 
strategy:
  matrix:
    browser: [chromium, firefox, webkit]
steps:
  - run: npx playwright test --project=${{ matrix.browser }}

The matrix block causes GitHub Actions to spin up one job per combination automatically, running them in parallel, so you get per-browser results without writing separate workflow files.

Q69 How would you shard a Playwright suite across GitHub Actions jobs and merge the reports afterward?

Use a matrix over shard indices (shard: [1, 2, 3, 4] with total 4) to run each shard as its own job producing a blob report artifact, then a final job (needs: [test]) downloads all shard artifacts and runs npx playwright merge-reports to produce and upload the single consolidated HTML report.

Q70 How do you make PR checks block a merge if Playwright tests fail?

Configure the workflow’s test job as a required status check in the repository’s branch protection rules — GitHub will then prevent merging any PR where that check hasn’t passed, enforcing the quality gate at the platform level rather than relying on manual discipline.

Q71 How would you run Playwright tests inside Docker as part of CI?

Use the official mcr.microsoft.com/playwright image (pinned to match your installed Playwright version) as the container base, which already has all browser dependencies pre-installed — this avoids the common “works locally, fails in CI” class of issues caused by missing OS-level browser dependencies on a bare runner.

Q72 How do you handle flaky tests in a CI pipeline without masking real failures?

I configure a small number of automatic retries (e.g., retries: 2 in CI only) so a genuinely flaky test doesn’t block every build, but I track retry data over time — a test that needs a retry to pass is logged/flagged even if the build goes green, so it gets triaged and fixed rather than silently tolerated forever. Retries are a safety net for CI stability, not a substitute for fixing root causes.

Q159 How would you design a Jenkins Shared Library to standardize Playwright pipeline stages across dozens of repos?

Extract common stages (install deps, install browsers, run tests, publish report, notify on failure) into reusable Groovy functions in a shared library repo, then have each consuming Jenkinsfile just call those functions with its own parameters — so a pipeline-wide improvement (e.g., adding trace artifact upload) is a one-line change in the library instead of updating dozens of Jenkinsfiles individually.

Q160 How would you configure Jenkins to dynamically provision ephemeral agents via Kubernetes?

Using the Kubernetes plugin, Jenkins spins up a pod (based on a defined pod template with the right image/resources) on demand for each build, runs the pipeline inside it, then tears the pod down afterward — this avoids maintaining a fixed pool of static agents and scales naturally with actual CI load.

Q161 How would you write a reusable GitHub Actions workflow that other repos can call for their Playwright suite?

Define it with on: workflow_call and accept inputs (like the test command or environment), then each consuming repo’s workflow simply does uses: org/shared-repo/.github/workflows/playwright.yml@main with its own inputs — centralizing pipeline logic the same way a Jenkins shared library does, but in GitHub Actions’ native mechanism.

Q162 How would you set up OIDC-based authentication from GitHub Actions to a cloud provider instead of long-lived secrets?

Configure a trust relationship between the cloud provider (AWS/Azure/GCP) and GitHub’s OIDC token issuer for your specific repo/workflow, so GitHub Actions requests a short-lived token at runtime instead of the pipeline ever holding a static, long-lived credential — this significantly reduces the blast radius if a workflow or its logs are ever compromised.

Q163 How do you decide an artifact retention policy for test reports/traces?

I’d retain full traces/videos only for failed tests (they’re expensive to store) for a shorter window (e.g., 7–14 days, enough to debug an issue that surfaces a bit later), while keeping lightweight pass/fail summary data indefinitely for trend analysis — balancing “can still debug a recent failure” against unnecessary storage cost for artifacts nobody will look at again.

Q164 How would you gate a blue-green deployment on automated test results before shifting traffic?

Run the smoke/critical-path suite against the new (green) environment before the load balancer cuts over, and only proceed with the traffic shift if that suite passes — treating the test run as an explicit, blocking quality gate in the deployment pipeline rather than a check that happens after users are already on the new version.

Q165 How would you design a canary release testing gate?

Run automated tests against the canary instance specifically (not just the stable fleet) once it’s receiving a small percentage of real traffic, combined with monitoring key error-rate/latency metrics for that canary slice — expanding the rollout only if both the automated gate and the live metrics stay healthy for a defined observation window.

Q166 How would you build trend analysis to detect a gradual suite execution-time increase before it becomes a crisis?

Log total (and per-test) duration on every CI run into a time-series store, and set an alert that fires on a sustained upward trend (not just a single slow run, which could be noise) — catching a “death by a thousand cuts” slowdown early rather than only noticing when the suite has already become painfully slow.

Q167 How would you configure Allure report categories to group failures by likely root cause?

Define custom categories matched against failure message patterns (e.g., “Timeout” for TimeoutError, “Assertion Failure” for expect mismatches, “Environment Issue” for connection errors) so the report’s summary view immediately shows the shape of what’s failing across the run, instead of requiring someone to read every individual failure to spot a pattern.

Q168 How would you set up an alert specifically for a flaky-test-rate spike, not just outright failures?

Track the retry-to-pass ratio per run (tests that failed on attempt 1 but passed on retry) as its own metric distinct from the final pass/fail count, and alert when that ratio crosses a threshold — since a build going green after retries can otherwise hide a real, worsening flakiness problem from ever surfacing.

Q169 What levers would you pull to reduce CI compute cost for a large Playwright suite without sacrificing coverage?

Cache dependencies/browsers aggressively, right-size shard count (more shards isn’t free — there’s overhead per job), move genuinely low-value/redundant tests to a less-frequent schedule instead of every commit, and use API-based setup instead of slower UI-driven setup wherever possible — cost reduction should come from cutting waste, not from cutting real coverage.

Q170 How would you plan a migration of an existing Jenkins pipeline to GitHub Actions with minimal disruption?

Run both pipelines in parallel for a transition period (GitHub Actions non-blocking at first, Jenkins still the source of truth), compare their results for consistency, then flip GitHub Actions to be the required/blocking check once confidence is established, and decommission Jenkins last — never cutting over in one step without a verified parallel run first.

Q171 How do you decide which test results should trigger a page/on-call alert versus just a dashboard notification?

Only failures on the smoke/critical-path suite against production or a release-blocking pipeline warrant an active page — routine regression-suite failures during normal development go to a dashboard/Slack channel for triage during working hours. Over-paging on non-urgent failures trains people to ignore alerts, which defeats the purpose of having them.

Q260 How would you “test the pipeline itself” to catch a broken CI configuration before it silently stops running tests?

Add a lightweight meta-check — e.g., a scheduled job that verifies the last N pipeline runs actually executed a non-zero, expected number of tests (not zero, which can happen silently if a config change breaks test discovery) — since a pipeline that “passes” because it accidentally ran nothing is far more dangerous than one that visibly fails.

Q261 How would you automate a rollback if post-deployment smoke tests fail in production?

Wire the smoke-test job as a required step immediately after deployment, and on failure, trigger the deployment tool’s rollback mechanism automatically (redeploy the previous known-good version/image) rather than requiring a human to notice and manually intervene — with an immediate alert either way so a human is aware even though the rollback already happened.

Q262 How would you integrate secrets scanning into a CI pipeline to catch a committed credential before merge?

Run a secrets-scanning tool (like Gitleaks or TruffleHog) as a required PR check that scans the diff for credential-shaped patterns, blocking the merge and ideally also flagging the specific line — catching this at PR time is far cheaper than after a real secret has been pushed to a shared branch history, where it also needs to be rotated regardless of whether the commit is later removed.

Q263 How would you integrate a dependency vulnerability scan as a CI gate?

Run npm audit (or Snyk/Dependabot) as part of the pipeline, configured to fail the build only on vulnerabilities above a defined severity threshold (not every low-severity transitive-dependency finding, which would create constant noise) — paired with a scheduled, non-blocking scan that surfaces lower-severity findings for periodic triage rather than blocking every single PR on them.

Q264 What testing implications does “build once, deploy many” have compared to rebuilding for each environment?

It means the exact artifact tested in one environment is the same binary/image promoted to the next, so a passing test run genuinely validates what will actually ship — rebuilding per environment risks a subtle difference (a dependency resolving differently, an environment-specific build flag) between what was tested and what’s deployed, undermining the whole point of the test having passed.

Q265 How would you set up automated ephemeral test environments per feature branch/PR?

On PR open, a pipeline stage provisions a lightweight, isolated environment (often via containers/Kubernetes namespaces) seeded with baseline test data, runs the full suite against it, and tears it down on PR close/merge — giving each PR its own real, isolated environment to validate against instead of contending for a single shared staging environment that different PRs can accidentally interfere with.

Q266 How would you design a testing gate within a GitOps-based deployment workflow?

Since GitOps deploys based on the state of a Git repo (not a direct pipeline push), the test gate lives before the deployment manifest change is merged into the environment’s config repo — the CI pipeline runs tests against the proposed change, and only a passing run is allowed to open/merge the PR that GitOps then automatically syncs to the cluster.

Q267 How would you automate quarantining a consistently flaky test while still tracking it for a fix?

A scheduled job analyzes recent CI history, and any test crossing a flakiness threshold (e.g., failed-then-passed-on-retry more than X% of the time over Y runs) is automatically tagged/moved into a non-blocking “quarantine” suite that still runs and reports, just doesn’t gate merges — with a visible, tracked backlog item created so quarantine doesn’t quietly become a permanent hiding place for unfixed flaky tests.

Q268 How would you reduce alert/notification fatigue on a team that’s started ignoring CI failure notifications?

Audit what’s actually triggering alerts and cut anything that isn’t genuinely actionable (routine flaky-test noise shouldn’t page anyone), consolidate into a single digest for non-urgent findings instead of a message-per-failure, and reserve immediate, loud alerts only for the failures that are truly release-blocking — the fix for alert fatigue is almost always fewer, better-targeted alerts, not more insistent ones.

Q269 How would you attribute CI compute cost per team or pipeline?

Tag CI jobs/runners with team/project labels and pull usage data (runner-minutes, parallel job count) from the CI provider’s billing/usage API, aggregating it into a per-team cost view — making the cost of an inefficient or overly-broad test suite visible to the team that owns it, rather than it being an invisible shared-infrastructure line item nobody feels responsible for.

Q270 How would you run a disaster-recovery drill for your CI/test infrastructure?

Periodically simulate the CI provider being unavailable (or a critical shared resource like the test environment’s database being down) and verify the team has a known, documented fallback (a secondary CI provider, or a manual verification checklist) — treating CI availability itself as a dependency worth explicitly rehearsing failure for, the same way you would for the production system it tests.

Q271 How do you ensure a pipeline can be safely re-run without side effects like duplicate deployments or duplicate test data?

Design each stage to be idempotent by construction — deployments target a specific, immutable artifact version (re-running just redeploys the same thing, not a new build), and test-data setup uses upsert/unique-per-run identifiers rather than plain inserts that would duplicate on a second run — so “just re-run the pipeline” is always a safe first troubleshooting step, not a risky one.

Q272 How would you integrate a code-quality gate like SonarQube alongside your Playwright test gate?

Run it as a parallel, independent CI job (not blocking on the test job or vice versa, since they check different things and shouldn’t serialize unnecessarily), with both required as separate status checks before merge — keeping code-quality and test-correctness as distinct, clearly-attributed gates so a failure immediately tells you which category of problem to look at.

Q360 How would you configure change detection in a monorepo so a PR only triggers tests for the affected package?

Use path-based filters (GitHub Actions’ paths: trigger, or a dedicated tool like Nx/Turborepo’s affected-graph detection) to compute which packages actually changed and their downstream dependents, running only that subset’s tests — full-suite-on-every-commit doesn’t scale once a monorepo has many largely-independent packages.

Q362 How would you design a manual approval gate before a pipeline proceeds to a production-impacting stage?

Jenkins’ input step (or GitHub Actions’ environment protection rules requiring a reviewer) pauses the pipeline and waits for an explicit human approval before continuing — used deliberately and sparingly, since overusing manual gates undermines the whole point of CI/CD automation, but appropriate for genuinely high-risk production changes.

Q363 How would you test infrastructure-as-code changes before they’re applied?

Run terraform plan (not apply) in CI and require human review of the plan’s diff before a separate, explicit apply step — and where feasible, apply the change to an ephemeral/lower environment first as an automated smoke check that the infrastructure actually comes up healthy, before it’s ever applied to production.

Q364 How would you configure GitHub Actions concurrency groups to cancel outdated runs per-PR without canceling unrelated branches?

concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true } scopes the concurrency group to the specific branch/PR ref, so pushing a new commit to a PR cancels that PR’s own outdated run, while a different PR’s run (a different github.ref) is entirely unaffected.

Q365 How would you handle test differences that only appear on specific CI runner operating systems?

Reproduce locally on a matching OS (or a container mimicking it) rather than guessing from CI logs alone, since OS-specific issues are often about subtle things like file path separators, line endings, font rendering, or timing characteristics that are hard to diagnose purely by reading a remote log — and I’d only maintain true cross-OS CI runs for tests where OS actually matters to the app, not as a blanket default that triples CI cost for no real benefit.

Q366 How would you integrate a secrets manager like Vault into a pipeline instead of static CI secrets?

The pipeline authenticates to Vault at runtime (often via a short-lived token tied to the CI identity) and fetches secrets just-in-time for the job that needs them, rather than storing long-lived static secrets directly in the CI platform — this centralizes secret rotation/auditing in one place and reduces the blast radius of any single compromised pipeline.

Q367 How would you implement test result caching to skip re-running tests for unchanged files?

Hash each test file’s content (and its transitive dependencies), and skip re-execution for a file whose hash matches a previous successful run’s cached result — genuinely useful for a large, slow suite where most PRs touch a small fraction of files, though it requires careful cache-invalidation logic to avoid the classic “stale cache masks a real failure” trap.

Q368 How would you integrate license-compliance scanning for dependencies as a CI check?

Run a license-scanning tool (like license-checker or FOSSA) against the dependency tree, configured with an allow/deny list matching your organization’s legal policy, failing the build if a newly-added dependency carries a disallowed license (e.g., certain copyleft licenses incompatible with a commercial product) — catching this at PR time rather than discovering it in a legal audit much later.

Q369 How would you visualize a test suite’s dependency graph to help onboard new contributors?

A generated diagram (even a simple auto-generated one from fixture dependency declarations) showing which fixtures depend on which, and which projects/setup steps run before others — genuinely useful once a framework has grown complex enough that “just read the config” no longer gives a quick mental model, which is exactly the point where new contributors otherwise get stuck.

Q370 How would you configure a pipeline to reply in a Slack thread with updated status when a retried job completes?

Capture the original notification’s thread/message timestamp when the first failure is posted, then have the retry job’s completion step post its result as a threaded reply referencing that timestamp (most chat APIs support this) — keeping the conversation consolidated instead of spamming a new top-level message for every retry attempt.

Q371 How would you design a testing gate for a blue/green database migration?

Run the application’s full test suite against both the old and new schema simultaneously during the transition window (since both must work — the whole point of blue/green is zero-downtime cutover), and specifically add tests exercising the dual-write/dual-read compatibility layer that’s typically needed during that transition period, not just the end states before and after.

Q372 How would you decide which parts of your pipeline run on every commit versus only on merge to main?

Fast, high-signal checks (lint, unit tests, a smoke suite) run on every commit/PR push since quick feedback matters most there; slower or more expensive suites (full cross-browser regression, load tests) run on merge to main or on a schedule, where the cost is justified by validating what’s about to actually ship rather than every work-in-progress commit.

Section G — AI in Testing (Awareness-Level) (Q88–393)

Q88 What is self-healing test automation, and how does it work conceptually?

It’s the idea of a framework or tool automatically detecting when a locator no longer matches (due to a UI refactor) and proposing or applying an alternative locator that likely targets the same intended element — often using multiple signals (text content, position, attributes, accessibility role) rather than a single brittle selector. In practice, I treat this as assistive, not autonomous — I’d want any auto-suggested locator fix reviewed by a human before it’s merged, since a “healed” locator could silently start targeting the wrong element.

Q89 How could AI be used to prioritize a regression suite under time constraints?

By analyzing historical data — which tests have caught real bugs before, which areas of the codebase changed in this commit/PR, and which tests are correlated with those files — a model can rank tests by likelihood of catching a regression for this specific change, so a time-boxed CI run executes the highest-value subset first instead of an arbitrary or purely alphabetical order.

Q90 What is MCP (Model Context Protocol), and how might it apply to a test framework?

MCP is a standardized way for an AI assistant to discover and call external tools/data sources — instead of building a one-off integration every time you want an AI to interact with your systems. Applied to testing, an MCP server could expose actions like “trigger this test suite,” “fetch the latest report,” or “query failing tests from the last week,” letting an AI assistant answer questions or take actions against your real test infrastructure through a consistent, permissioned interface rather than screen-scraping or custom scripting.

Q91 What is RAG (Retrieval-Augmented Generation), and how could it help a testing team?

RAG retrieves relevant context (docs, past bug reports, existing test code) from a knowledge base and feeds it into an LLM prompt before generating a response — so answers are grounded in your team’s actual conventions rather than generic training data. For a testing team, this could mean an AI assistant that, when asked to write a new test, first retrieves your team’s existing page objects and naming conventions so the generated test actually fits the codebase instead of inventing a new, inconsistent pattern.

Q92 What’s your honest view on how much you’d trust an AI agent to autonomously write/maintain production test code today?

I see it as a strong accelerator for boilerplate and first drafts — generating a Page Object skeleton, suggesting a fix for a known-broken locator, or drafting a test from a manual test case — but I wouldn’t let it merge changes to shared framework code or critical test suites without human review. AI-generated code still needs to be checked for hardcoded waits, brittle selectors, and whether it actually tests the right thing versus just making an assertion pass; the judgment of what’s actually worth testing still needs a human in the loop.

Q187 How does AI-based visual testing reduce false positives compared to strict pixel-diff comparison?

Perceptual/DOM-aware visual AI tools understand that a button shifting by a few pixels due to a font-rendering difference is not the same kind of change as a button disappearing entirely — they classify differences by significance rather than flagging every pixel deviation equally, which is what makes traditional pixel-diffing so prone to noisy false failures on things like anti-aliasing or minor sub-pixel rendering differences across environments.

Q188 What makes a good prompt when asking an AI assistant to generate a Playwright test from a manual test case?

Give it concrete context, not just the test steps: your project’s locator conventions (role-based vs data-testid), an example of an existing page object to match the style, the specific assertions that matter, and explicit constraints (“no waitForTimeout, use web-first assertions”) — a vague prompt produces generic, framework-inconsistent code that needs heavy rework, while a well-scoped one produces something close to mergeable.

Q189 How could an LLM summarize a long CI failure log into an actionable root-cause hypothesis?

Feed it the relevant portion of the trace/log/stack trace along with context about what the test was trying to do, and prompt it to identify the most likely failure category (locator issue, timing issue, real app bug, environment issue) with its reasoning — this doesn’t replace human triage but can meaningfully cut the time a person spends just reading raw logs before they can start actually diagnosing.

Q190 What’s the risk of an AI-generated test containing a “hallucinated” assertion that always passes, and how would you catch it?

An LLM can generate a syntactically valid assertion that doesn’t actually verify meaningful behavior (e.g., asserting an element merely exists rather than asserting its actual expected value), giving false confidence. I’d catch this in review by deliberately breaking the feature locally and confirming the AI-generated test actually fails — a test that can’t fail when the thing it’s supposedly testing breaks isn’t providing real coverage, regardless of who wrote it.

Q191 How could an AI code-review bot flag anti-patterns in Playwright test PRs?

Configure it with your team’s specific rules (ban waitForTimeout, flag CSS selectors when a role-based locator would work, flag assertions with no message) as review criteria, so it leaves inline comments on PRs the same way a strict human reviewer would — catching common issues consistently and immediately, freeing human reviewers to focus on higher-level design/test-strategy feedback instead of repeatedly flagging the same style issues.

Q192 What cost/latency trade-offs would make you avoid calling an LLM inline during a CI run?

Section I — JavaScript & TypeScript Fundamentals (Q401–425)

Q401 What is the difference betweenvar,let, andconstin JavaScript?

var is function-scoped (or global) and hoisted with an initial value of undefined, which allows confusing bugs like accessing a variable before its declaration line without an error. let and const are block-scoped and live in a “temporal dead zone” until their declaration line, throwing a clear error if accessed early. const additionally prevents reassignment of the binding itself (though an object/array it points to can still be mutated). In modern code, const is the default, let only when reassignment is genuinely needed, and var is avoided entirely.

Q402 What is hoisting, and how does it affectvarvslet/const?

Hoisting is JavaScript’s behavior of processing variable and function declarations before executing code line by line. var declarations are hoisted and initialized to undefined, so referencing one before its declaration returns undefined instead of throwing. let/const declarations are hoisted too, but remain uninitialized in the “temporal dead zone” until their actual line runs, so referencing them early throws a ReferenceError — a much safer failure mode that catches real bugs instead of silently returning undefined.

Q403 What is the difference between==and===?

=== (strict equality) compares both value and type with no conversion — 1 === '1' is false. == (loose equality) performs type coercion before comparing, so 1 == '1' is true, which can produce surprising, hard-to-predict results ('' == 0 is true, for instance). I use === by default everywhere, and only reach for == in the rare, deliberate case where I actually want that coercion.

Q404 What is a closure, and can you give a practical example relevant to test automation?

A closure is a function that retains access to variables from its enclosing scope even after that outer function has finished executing. A practical automation example is a counter or ID-generator helper for test data: a function that returns an inner function which keeps incrementing a private counter variable each call, without exposing that counter directly — useful for generating sequential unique test identifiers across a test run.

function createIdGenerator() {
  let counter = 0;
  return () => `test-user-${++counter}`;
}
const nextId = createIdGenerator();
nextId(); // 'test-user-1'
nextId(); // 'test-user-2'
Q405 What isthis, and how does its value differ between a regular function and an arrow function?

In a regular function, this is determined dynamically by how the function is called (the object it’s called on, or undefined/global in strict mode if called standalone). An arrow function doesn’t have its own this — it lexically inherits this from its enclosing scope at the point it was defined, which is exactly why arrow functions are preferred for callbacks (like inside a class method or a .then()) where you want this to stay consistent with the surrounding context rather than being reset by how the callback happens to be invoked.

Q406 What is the event loop, and how do microtasks differ from macrotasks in execution order?

JavaScript is single-threaded, so the event loop is what allows async operations without blocking: synchronous code runs first, then all queued microtasks (Promise callbacks, queueMicrotask) run to completion before the loop picks up the next macrotask (setTimeout, I/O callbacks) — meaning a Promise.resolve().then() scheduled after a setTimeout(fn, 0) will still run before that timeout’s callback, which trips people up until they understand this ordering explicitly.

Q407 What is the difference betweennullandundefined?

undefined means a variable has been declared but not yet assigned a value (JavaScript’s own default) — null is an intentional, explicit assignment representing “no value,” set deliberately by the developer. I treat undefined as “this was never set” and null as “this was deliberately cleared/empty,” which matters when deciding how to check for either (== null conveniently matches both, while === undefined matches only the specific case).

Q408 What is prototypal inheritance, and how does it differ from classical inheritance?

In JavaScript, objects inherit directly from other objects via a prototype chain — when a property isn’t found on an object, the engine looks up its prototype, and so on, rather than instantiating from a rigid class blueprint the way classical (Java/C#-style) inheritance works. Modern class syntax in JS is largely syntactic sugar over this same prototypal mechanism underneath, which is worth knowing since debugging an unexpected inherited property/method often requires understanding the actual prototype chain, not just the class hierarchy as written.

Q409 What is the difference betweenObject.freeze()andconst?

const only prevents the variable binding from being reassigned to a different value — the object it points to can still be mutated (const obj = {a:1}; obj.a = 2 is perfectly legal). Object.freeze(obj) prevents the object’s own properties from being added, removed, or changed (in non-strict mode, mutation attempts fail silently; in strict mode, they throw) — the two solve different problems and are often needed together for truly immutable test fixture objects.

Q410 What are template literals, and what problem do they solve compared to string concatenation?

Template literals (backtick strings) support embedded expressions via ${...} and native multi-line strings, replacing verbose and error-prone 'text ' + variable + ' more text' concatenation with more readable, less mistake-prone syntax — especially valuable when building dynamic API URLs or assertion messages in test code where readability of the final string matters for quick debugging.

Q411 What is destructuring, and how would you use it to extract fields from an API response?

Destructuring lets you unpack specific properties from an object (or elements from an array) directly into named variables in one line, instead of accessing each via dot notation separately.

const { data: { id, status, items } } = await response.json();

This is especially useful in test code for immediately pulling out just the fields you’re actually going to assert on from a large, often deeply-nested API response.

Q412 What is the spread operator, and how does it differ from the rest parameter, given they use the same...syntax?

Spread expands an iterable into individual elements ([...arr1, ...arr2] to merge arrays, or {...obj, extra: 1} to shallow-copy and extend an object) — used where a value is being consumed/read. Rest collects multiple individual arguments/elements into a single array (function log(...args) {}) — used in a parameter/destructuring position where values are being gathered. Same syntax, opposite direction, and the position (left vs right of an assignment, or in a function signature vs a call) tells you which one applies.

Q413 What is a Promise, and what are its three possible states?

A Promise represents the eventual result of an asynchronous operation. It starts pending, and settles exactly once into either fulfilled (resolved with a value) or rejected (failed with a reason) — once settled, its state and result are permanent and any .then()/.catch() attached later still fires with that same outcome, which is what makes Promises reliably composable compared to raw callbacks.

Q414 What is the difference betweenPromise.all(),Promise.allSettled(),Promise.race(), andPromise.any()?

Promise.all() resolves when every promise resolves, but rejects immediately if any one rejects (fail-fast). Promise.allSettled() always waits for every promise to finish regardless of outcome, returning each one’s status individually — useful when you want to run several independent checks and see all results even if some fail. Promise.race() settles as soon as the first promise settles (resolve or reject), often used for implementing a timeout. Promise.any() resolves as soon as the first one fulfills, only rejecting if all of them reject.

Q415 What is async/await, and how does it relate to Promises under the hood?

async/await is syntactic sugar over Promises that lets asynchronous code read like synchronous code — an async function always returns a Promise, and await pauses execution within that function (without blocking the rest of the program) until the awaited Promise settles, then either returns its resolved value or throws its rejection as a normal catchable error. It doesn’t replace Promises; it’s just a much more readable way to consume them.

Q416 What is the difference between synchronous and asynchronous execution, given JavaScript is single-threaded?

Synchronous code runs to completion, blocking anything else from happening until it finishes. Since JS has only one thread, a long synchronous operation would freeze everything (including the UI, in a browser) — asynchronous operations (network calls, timers, file I/O) are instead handed off to the runtime/browser to handle in the background, with their callback/Promise resolution scheduled back onto the single thread via the event loop once ready, so the main thread stays free to keep running other code in the meantime.

Q417 What is a higher-order function? Give an example relevant to test automation.

A function that either takes another function as an argument, returns a function, or both. A practical automation example is a retry wrapper: a higher-order function that accepts any async function and returns a new version of it with retry logic built in, letting you apply the same retry behavior to many different operations without duplicating the retry logic itself.

Q418 What is the difference betweenmap(),forEach(), andfilter()?

map() transforms each element and returns a new array of the same length with the transformed values. forEach() also iterates every element but returns undefined — it’s for side effects (like logging), not producing a new collection. filter() returns a new array containing only the elements that pass a given test, potentially shorter than the original. Mixing these up (e.g., using forEach when you actually wanted a transformed array back) is a common source of subtly broken helper functions.

Q419 What is the difference between a shallow copy and a deep copy of an object?

A shallow copy (via spread {...obj} or Object.assign()) copies only the top-level properties — if a property’s value is itself an object/array, both the original and the copy still reference the same nested object, so mutating it through either affects both. A deep copy recursively clones every nested level so the copy is fully independent — relevant in test fixtures when you want to derive a modified variant of a shared base object without accidentally mutating the shared original that other tests also use.

Q420 What is TypeScript, and what problems does it solve that plain JavaScript doesn’t?

TypeScript is a typed superset of JavaScript that compiles down to plain JS, adding static type checking at compile time. It catches an entire class of bugs before code ever runs (passing the wrong shape of object to a function, a typo’d property name) that would otherwise only surface as a runtime error, often deep into a test run — and it gives much better IDE autocomplete/refactoring support, which matters a lot for a large, multi-contributor test framework.

Q421 What is the difference between aninterfaceand atypealias in TypeScript?

Both can describe an object’s shape, and for most everyday use they’re interchangeable — the practical differences: interface supports declaration merging (multiple interface declarations with the same name automatically combine) and reads slightly more naturally for object-oriented, class-implementing patterns, while type can represent things an interface can’t, like union types, intersections, and mapped/conditional types. I default to interface for plain object shapes and reach for type when I need those more advanced type-algebra features.

Q422 What are TypeScript generics, and why are they useful for reusable framework utilities?

Generics let a function or type work with a placeholder type parameter (<T>) instead of a fixed concrete type, preserving type safety across different uses instead of falling back to any. For a test framework, a generic waitFor<T>() helper or a generic API-response validator can be reused across many different data shapes while still giving full type-checking and autocomplete for each specific call site, rather than needing a near-duplicate helper per data type.

Q423 What is the difference betweenany,unknown, andnever?

any disables type checking entirely for that value — TypeScript trusts you completely and won’t catch mistakes, which defeats much of the point of using TypeScript at all. unknown is type-safe: you can assign anything to it, but you must narrow/check its actual type before doing anything with it, forcing deliberate validation. never represents a value that can genuinely never occur (a function that always throws, or an exhaustively-narrowed union with no remaining case) — useful for exhaustiveness checks that catch an unhandled case at compile time.

Q424 What are union types and intersection types in TypeScript?

A union type (string | number) means a value can be either of the listed types. An intersection type (TypeA & TypeB) means a value must satisfy all of the combined types’ requirements at once — commonly used to combine a base object shape with additional fields (User & { role: 'admin' }) without redefining the whole shape from scratch.

Q425 What is the difference between compile-time type checking and runtime validation, and why does a test framework often need both?

TypeScript’s type checking only exists at compile time — it has zero effect once the code actually runs, and it can’t protect you against genuinely untyped external input (an API response, user input, a config file) that might not actually match the shape you’ve declared. That’s why a framework often pairs TypeScript’s compile-time safety with a runtime validation library (Zod, Ajv) for anything crossing an external boundary — the type system protects your own code’s internal correctness, while runtime validation protects against the outside world not honoring that contract.

Section J — Data Structures & Algorithms (DSA) (Q426–450)

Q426 Reverse a string in place — what’s the most efficient approach, and its time/space complexity?

Since JS strings are immutable, “in place” really means converting to an array and swapping from both ends toward the middle, which is O(n) time and O(n) space (for the array conversion) — better than repeatedly concatenating, which would be O(n²) due to creating a new string on every concatenation.

function reverseString(s: string): string {
  const arr = s.split('');
  let left = 0, right = arr.length - 1;
  while (left < right) {
    [arr[left], arr[right]] = [arr[right], arr[left]];
    left++; right--;
  }
  return arr.join('');
}
Q427 How would you check if a string is a palindrome, and what’s the time complexity?

Compare characters from both ends moving inward, stopping early on any mismatch — O(n) time, O(1) extra space (ignoring the input itself).

function isPalindrome(s: string): boolean {
  let left = 0, right = s.length - 1;
  while (left < right) {
    if (s[left] !== s[right]) return false;
    left++; right--;
  }
  return true;
}
Q428 How would you find the first non-repeating character in a string?

Build a frequency count in one pass (O(n)), then scan the string again in original order and return the first character whose count is 1 — overall O(n) time, O(k) space where k is the alphabet size.

function firstUniqueChar(s: string): string | null {
  const counts = new Map<string, number>();
  for (const c of s) counts.set(c, (counts.get(c) ?? 0) + 1);
  for (const c of s) if (counts.get(c) === 1) return c;
  return null;
}
Q429 How would you check if two strings are anagrams?

Sort both strings and compare (O(n log n)), or the faster approach: build a character-frequency map for one string, then decrement it while scanning the other, confirming all counts return to zero — O(n) time, O(k) space.

function isAnagram(a: string, b: string): boolean {
  if (a.length !== b.length) return false;
  const counts = new Map<string, number>();
  for (const c of a) counts.set(c, (counts.get(c) ?? 0) + 1);
  for (const c of b) {
    if (!counts.get(c)) return false;
    counts.set(c, counts.get(c)! - 1);
  }
  return true;
}
Q430 How would you remove duplicates from an array without using aSet?

Track seen values in a plain object/Map while building a result array — O(n) time, O(n) space.

function dedupe<T>(arr: T[]): T[] {
  const seen = new Map<T, boolean>();
  const result: T[] = [];
  for (const item of arr) {
    if (!seen.has(item)) { seen.set(item, true); result.push(item); }
  }
  return result;
}
Q431 How would you find the maximum sum of a contiguous subarray (Kadane’s algorithm)?

Track a running sum, resetting it to the current element whenever the running sum would drop below just that element alone (since a negative running total can only hurt any future subarray), while tracking the best sum seen so far — O(n) time, O(1) space, a single-pass greedy/DP approach.

function maxSubArray(nums: number[]): number {
  let maxSoFar = nums[0], curr = nums[0];
  for (let i = 1; i < nums.length; i++) {
    curr = Math.max(nums[i], curr + nums[i]);
    maxSoFar = Math.max(maxSoFar, curr);
  }
  return maxSoFar;
}
Q432 How would you implement binary search, and what precondition must hold?

The array must already be sorted. Repeatedly compare the target to the middle element and discard the half that can’t contain it — O(log n) time, O(1) space.

function binarySearch(arr: number[], target: number): number {
  let lo = 0, hi = arr.length - 1;
  while (lo <= hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (arr[mid] === target) return mid;
    if (arr[mid] < target) lo = mid + 1; else hi = mid - 1;
  }
  return -1;
}
Q433 What is the difference between an array and a linked list in terms of time-complexity trade-offs?

An array gives O(1) random-access reads by index but O(n) insertion/deletion in the middle (everything after must shift). A linked list gives O(1) insertion/deletion once you already have a reference to the right node, but only O(n) access to a specific position since you must traverse from the head — the right choice depends on whether your workload is read-heavy-by-index or insert/delete-heavy.

Q434 How would you detect a cycle in a linked list (Floyd’s cycle detection)?

Use two pointers moving at different speeds — a “slow” pointer advancing one node at a time and a “fast” pointer advancing two — if there’s a cycle, the fast pointer will eventually lap the slow one and they’ll meet; if the fast pointer reaches the end (null), there’s no cycle. O(n) time, O(1) space, no extra data structure needed.

Q435 What is a stack, and how would you use one to check if a string’s parentheses are balanced?

A stack is a Last-In-First-Out structure. Scan the string, pushing each opening bracket; on a closing bracket, pop and check it matches the corresponding opener (returning false immediately on mismatch or an empty stack); at the end, the stack must be empty for the string to be balanced.

function isBalanced(s: string): boolean {
  const pairs: Record<string, string> = { ')': '(', ']': '[', '}': '{' };
  const stack: string[] = [];
  for (const c of s) {
    if ('([{'.includes(c)) stack.push(c);
    else if (c in pairs) { if (stack.pop() !== pairs[c]) return false; }
  }
  return stack.length === 0;
}
Q436 What is a queue, and where might it be relevant in a test automation context?

A queue is a First-In-First-Out structure. A relevant automation example is implementing a breadth-first crawl over an application’s pages/links (a simple internal-link checker): a queue holds URLs discovered but not yet visited, processed in the order they were found, which is the natural structure for a BFS-style traversal.

Q437 What is the difference between a stack (LIFO) and a queue (FIFO), mapped to real-world examples?

A stack behaves like a pile of plates — you add and remove from the same end (the top), which is exactly how an “undo” feature works (undo the most recent action first). A queue behaves like a checkout line — first person in line is the first served, which matches a print queue or a task queue processing jobs in the order they arrived.

Q438 How would you implement a basic LRU cache with O(1) get/put?

Combine a hash map (for O(1) key lookup) with a doubly linked list (to track recency order, moving an accessed node to the front in O(1) and evicting from the back when over capacity) — the map alone gives fast lookup but no ordering; the linked list alone gives ordering but slow lookup; together they give both in O(1).

class LRUCache<K, V> {
  private cache = new Map<K, V>();
  constructor(private capacity: number) {}
  get(key: K): V | undefined {
    if (!this.cache.has(key)) return undefined;
    const val = this.cache.get(key)!;
    this.cache.delete(key); this.cache.set(key, val); // refresh recency
    return val;
  }
  put(key: K, value: V) {
    if (this.cache.has(key)) this.cache.delete(key);
    else if (this.cache.size >= this.capacity) this.cache.delete(this.cache.keys().next().value);
    this.cache.set(key, value);
  }
}

(Map in JS preserves insertion order, which conveniently lets this simpler version stand in for the classic map + doubly-linked-list implementation.)

Q439 What is a hash map, and how does it typically achieve average O(1) lookup?

A hash map applies a hash function to a key to compute an index into an underlying array (bucket), so lookup, insert, and delete are all typically O(1) on average — degrading to O(n) worst case only if many keys collide into the same bucket, which a good hash function and dynamic resizing are designed to minimize in practice.

Q440 How would you find the intersection of two arrays efficiently?

Put one array’s elements into a Set for O(1) lookup, then filter the second array against that set — O(n + m) time overall instead of the O(n × m) a naive nested-loop comparison would produce.

function intersection(a: number[], b: number[]): number[] {
  const setA = new Set(a);
  return [...new Set(b.filter(x => setA.has(x)))];
}
Q441 What is a binary tree, and what’s the difference between DFS and BFS traversal?

A binary tree is a hierarchical structure where each node has at most two children. Depth-first traversal (in-order, pre-order, post-order) explores as far down one branch as possible before backtracking, typically implemented with recursion or an explicit stack. Breadth-first traversal explores level by level, using a queue — the choice depends on the problem: DFS variants are natural for things like validating a binary search tree’s ordering, while BFS is natural for finding the shortest path or level-by-level processing.

Q442 How would you check if a binary tree is balanced?

Recursively compute each subtree’s height while checking, at every node, that the height difference between its left and right subtrees never exceeds 1 — short-circuiting to return “unbalanced” as soon as any node fails that check, rather than computing every height fully before checking, for better average-case efficiency.

Q443 What is Big-O notation, and why does it matter when choosing between two working solutions?

Big-O describes how an algorithm’s runtime (or space use) scales as input size grows, ignoring constant factors — two solutions that both “work” on a small test input can behave very differently at real-world scale (an O(n²) solution might be fine for 100 items but unusable for 100,000). It’s the vocabulary for reasoning about that scaling behavior objectively, rather than relying on “it felt fast when I tried it.”

Q444 What is the time complexity of common array operations in JavaScript, and why doesshift()/unshift()differ frompush()/pop()?

push()/pop() operate on the end of the array and are O(1), since no other elements need to move. shift()/unshift() operate on the beginning, requiring every other element to be re-indexed (shifted over by one), making them O(n) — a detail that matters if you’re building a hot-path helper that processes a large array repeatedly from the front, where a queue-appropriate data structure might be a better fit than a plain array.

Q445 How would you merge two sorted arrays into a single sorted array efficiently?

Use a two-pointer approach, one per array, repeatedly taking the smaller of the two current elements and advancing that pointer — O(n + m) time, avoiding the O((n+m) log(n+m)) cost of concatenating and re-sorting from scratch.

function mergeSorted(a: number[], b: number[]): number[] {
  const result: number[] = [];
  let i = 0, j = 0;
  while (i < a.length && j < b.length) result.push(a[i] <= b[j] ? a[i++] : b[j++]);
  return [...result, ...a.slice(i), ...b.slice(j)];
}
Q446 What is recursion, and what’s the risk of unbounded recursion in JavaScript?

Recursion is a function calling itself to break a problem into smaller subproblems, with a base case that stops the recursion. Since JavaScript’s call stack has a finite size and (unlike some languages) doesn’t guarantee tail-call optimization in most engines, deep or unbounded recursion (a missing/incorrect base case, or genuinely very deep input) throws a RangeError: Maximum call stack size exceeded — for genuinely large inputs, an iterative approach is often safer than a naive recursive one.

Q447 How would you flatten a deeply nested array without usingArray.prototype.flat()?

Recursively check each element: if it’s an array, recurse into it and spread the result; otherwise, include it directly — handles arbitrary nesting depth.

function flatten(arr: any[]): any[] {
  return arr.reduce((acc, val) =>
    Array.isArray(val) ? acc.concat(flatten(val)) : acc.concat(val), []);
}
Q448 What is dynamic programming, and how does it differ from plain recursion?

Dynamic programming solves a problem by breaking it into overlapping subproblems and storing (memoizing) each subproblem’s result so it’s computed only once, rather than plain recursion re-computing the same subproblem repeatedly — the classic example is naive recursive Fibonacci being exponential time, while a memoized version is linear, because it stops redundantly recalculating the same values.

Q449 How would you find the Kth largest element in an unsorted array, and what are the trade-offs of different approaches?

A full sort then indexing is simple and O(n log n) — fine for small/one-off cases. A min-heap of size K gives O(n log k), better when k is small relative to n. The optimal average case is the Quickselect algorithm (a partition-based approach related to quicksort) at O(n) average time, though it has O(n²) worst case without care — in practice, I’d reach for the simple sort unless profiling actually showed this was a bottleneck worth the added complexity.

Q450 Why might a strong DSA foundation genuinely matter for an SDET role, beyond passing a coding interview round?

Framework code isn’t just glue — writing an efficient test-data deduplication step, a fast lookup for matching API responses against expected fixtures, or a sensible retry/backoff structure all draw directly on these fundamentals; and just as importantly, understanding complexity helps you recognize when a slow test suite is slow because of an accidentally O(n²) helper function buried in the framework, not just “flaky infrastructure” — a diagnosis that’s easy to miss without this background.

Section K — Manual Testing & QA Fundamentals (Q451–465)

Q451 What is the Software Testing Life Cycle (STLC), and what are its typical phases?

STLC is the structured sequence testing follows within a project: requirement analysis (understanding what needs testing), test planning (strategy, scope, resources), test case design, test environment setup, test execution, and test closure (summarizing results, archiving artifacts) — even in a heavily automated shop, these phases still happen, just compressed and often overlapping with development sprints rather than as a separate, sequential waterfall stage.

Q452 What is the difference between a test case and a test scenario?

A test scenario is a high-level statement of what to test (“verify login works with valid credentials”), while a test case is the detailed, step-by-step specification of how to test it (specific input values, exact steps, expected result) — a single scenario often expands into multiple concrete test cases covering different input variations.

Q453 What is the difference between smoke testing and sanity testing?

Smoke testing is a broad, shallow check that the build is stable enough to test further at all (“does the app even launch and load its main screens”) — typically run first, on every new build. Sanity testing is a narrower, deeper check focused specifically on a particular area after a small change or bug fix (“did fixing the login bug break anything nearby in that flow”) — smoke is breadth-first and build-level; sanity is depth-first and change-specific.

Q454 What is regression testing, and how do you decide what belongs in a regression suite?

Regression testing re-verifies that previously working functionality still works after a change. I prioritize including: critical business flows, areas with a history of frequently breaking, and anything the current change plausibly could have affected even indirectly — while deliberately excluding rarely-used edge cases or areas genuinely unaffected by the type of changes the codebase typically sees, since an unbounded “test everything, every time” regression suite becomes too slow to actually run regularly.

Q455 What is the difference between severity and priority, with an example where they diverge?

Severity is about technical impact (how badly is functionality broken); priority is about business urgency (how soon must it be fixed). A cosmetic typo on the homepage of a high-traffic site is low severity but can be high priority (visible to everyone, easy embarrassment, quick fix). Conversely, a crash in a rarely-used admin export feature used once a year might be high severity (it genuinely crashes) but low priority (very few users affected, can wait for the next release).

Q456 What is the defect life cycle, and what are its typical states?

New → Assigned → In Progress → Fixed → Retest → Closed (or Reopened if the retest fails, looping back) — with additional states like Duplicate, Rejected, or Deferred for defects that don’t proceed through the standard fix path. Understanding this flow matters for writing bug reports that move efficiently through it (clear repro steps, environment details, evidence) rather than bouncing back and forth due to ambiguity.

Q457 What is boundary value analysis, and how would you apply it to a 18–65 age field?

Boundary value analysis focuses test cases on the edges of valid ranges, since bugs disproportionately cluster there (off-by-one errors are extremely common). For an 18–65 valid range, I’d specifically test 17 (just below, should reject), 18 (exact lower boundary, should accept), 65 (exact upper boundary, should accept), and 66 (just above, should reject) — four precisely-chosen values instead of testing every possible age in between.

Q458 What is equivalence partitioning, and how does it reduce test cases needed?

It groups inputs into partitions expected to be handled the same way by the system, on the logic that if one representative value from a partition works correctly, the rest of that partition likely does too — so instead of testing every possible input value, you test one representative from each partition (valid range, below range, above range, wrong type) plus boundary values, dramatically reducing test count while still covering the meaningfully distinct behaviors.

Q459 What is exploratory testing, and how does it complement scripted/automated testing?

Exploratory testing is simultaneous learning, test design, and execution — a tester actively investigates the application without a pre-written script, following their judgment and curiosity about what might break. It complements automation because scripted tests (automated or manual) only find what they were specifically written to check, while exploratory testing is how genuinely unanticipated bugs and unusual edge cases actually get discovered.

Q460 What is the difference between verification and validation?

Verification asks “are we building the product right” — checking the product conforms to its specifications (reviews, walkthroughs, static analysis). Validation asks “are we building the right product” — checking the product actually meets the user’s real needs and intent, typically through actual testing/usage. A feature can pass verification (it does exactly what the spec said) while still failing validation (the spec itself didn’t capture what users actually needed).

Q461 What is a test plan, and what are its key components?

A test plan is the document defining the overall testing approach for a project or release: scope (what’s in/out), objectives, test strategy, environment/tooling requirements, resource and schedule estimates, entry/exit criteria, and risk assessment — it’s the reference document that aligns the whole team (not just QA) on what “adequately tested” means for this specific effort.

Q462 What is the difference between black-box, white-box, and gray-box testing?

Black-box testing evaluates the system purely from the outside, based on inputs and expected outputs, with no knowledge of internal code (most E2E/UI testing). White-box testing is done with full knowledge of the internal code structure (unit tests, code-coverage-driven test design). Gray-box sits between the two — some internal knowledge (e.g., knowing the database schema or API contract) informs black-box-style external testing, which describes a lot of practical SDET work.

Q463 What is usability testing, and why is it typically hard to fully automate?

Usability testing evaluates how intuitive, efficient, and satisfying an interface is for real users to actually use — it fundamentally requires human judgment about subjective qualities (is this confusing, does this feel slow, would a real user understand this label) that automation can’t meaningfully assess; automation can check that a button works, but not that a user would intuitively find it in the first place.

Q464 What are entry and exit criteria for a testing phase, and why do they matter for release sign-off?

Entry criteria define what must be true before testing can meaningfully begin (build deployed, test environment stable, test data available). Exit criteria define what must be true before testing is considered complete (a defined pass rate achieved, no open critical/high-severity defects, planned coverage executed) — having both explicitly defined and agreed on upfront prevents ambiguous, last-minute arguments about whether a release is “actually ready” under real deadline pressure.

Q465 How do you decide what to automate versus what should remain manual, given limited time before a release?

I prioritize automating what will be run repeatedly (regression-prone areas, critical business flows executed on every release) since that’s where automation’s upfront cost pays back fastest, while leaving genuinely one-off checks, highly subjective usability assessments, and areas still actively changing (where automation would need constant rework) as manual — the deciding factor is expected frequency of execution weighted against the cost of automating and maintaining it, not just “can this technically be automated.”

Section L — Security Testing Fundamentals (Q466–480)

Q466 What is OWASP, and what is the OWASP Top 10?

OWASP (Open Web Application Security Project) is a nonprofit that publishes widely-used, community-driven security guidance — the OWASP Top 10 is its regularly-updated list of the most critical web application security risks (things like broken access control, injection, cryptographic failures), used industry-wide as a baseline checklist for what to be aware of even for engineers who aren’t dedicated security specialists.

Q467 What is SQL injection, and how would you test for it at a basic level?

SQL injection happens when untrusted user input is concatenated directly into a SQL query instead of being properly parameterized, letting an attacker inject their own SQL logic. A basic functional test would submit classic probe strings (' OR '1'='1, a trailing -- comment) into input fields that eventually reach a database query, and confirm the application safely rejects/escapes them rather than returning unexpected data or erroring in a way that reveals query structure — a full security audit goes much deeper, but this basic check is well within reach for a functional SDET.

Q468 What is Cross-Site Scripting (XSS), and what’s the difference between stored, reflected, and DOM-based XSS?

XSS lets an attacker inject malicious script that executes in another user’s browser. Stored XSS persists the malicious script in the application’s data (e.g., a comment field) so it executes for every user who later views that content. Reflected XSS reflects unsanitized input immediately back in the response (often via a crafted URL), executing only for whoever clicks that specific malicious link. DOM-based XSS occurs entirely client-side, where JavaScript itself unsafely writes untrusted data into the page’s DOM, without the payload necessarily ever touching the server.

Q469 What is Cross-Site Request Forgery (CSRF), and how do applications typically defend against it?

CSRF tricks a logged-in user’s browser into unknowingly submitting a malicious request to an application they’re authenticated with (since browsers automatically attach cookies to requests regardless of which site initiated them). Defenses include CSRF tokens (a unique, unpredictable value the legitimate form must include, which an attacker’s forged request can’t know) and the SameSite cookie attribute, which prevents cookies from being sent along with cross-site requests in the first place.

Q470 What is the difference between authentication and authorization, and what’s a common testing mistake that conflates the two?

Authentication answers “who are you” (logging in, proving identity). Authorization answers “what are you allowed to do” (permissions, once identity is established). A common testing mistake is only verifying that an unauthenticated user is correctly blocked (authentication) while never testing that an authenticated user is correctly blocked from resources or actions they’re not authorized for (authorization) — the second is where subtle, serious bugs like BOLA/IDOR usually hide.

Q471 What is a session, and what security properties should a session cookie have?

A session is the server’s way of remembering a user is authenticated across multiple requests, typically via a session identifier stored in a cookie. That cookie should be HttpOnly (inaccessible to JavaScript, mitigating XSS-based theft), Secure (only ever sent over HTTPS), and have an appropriate SameSite setting (limiting when it’s sent on cross-site requests, mitigating CSRF) — testing that all three attributes are actually set is a quick, high-value functional security check.

Q472 What is HTTPS, and why does testing over plain HTTP in a production-like environment represent a real risk worth flagging?

HTTPS encrypts traffic between client and server, protecting against eavesdropping and tampering in transit. If a production-like environment (staging, UAT) is accessible over plain HTTP, credentials and sensitive data sent during testing are exposed on the network in plaintext — worth flagging as a finding even if it’s “just” a test environment, since test environments often still contain real-shaped sensitive data and are frequently less scrutinized than production.

Q473 What is the principle of least privilege, and how would you test it’s enforced in RBAC?

Least privilege means every user/system should have only the minimum access necessary to do their job, nothing more. To test it in a role-based access control system, I’d log in as each defined role and systematically attempt actions/resources that role should NOT have access to (not just confirm the actions it should have work) — the untested negative space (what a role can’t do) is where over-permissive access bugs usually live, and it’s the part teams most often forget to explicitly test.

Q474 What is sensitive data exposure, and where does it commonly leak accidentally?

It’s the unintended exposure of sensitive information (passwords, tokens, PII, internal system details) through channels that weren’t meant to carry it — common accidental leak points include verbose error messages/stack traces shown to end users, sensitive values logged in plaintext, data embedded directly in URLs (which get logged by proxies/browsers/analytics), and client-side storage (localStorage) holding something that should never leave the server.

Q475 What is a security header, and why would an SDET care about testing for its presence?

Security headers (Content-Security-Policy, X-Frame-Options, Strict-Transport-Security) instruct the browser to enforce protections the application itself can’t fully control client-side. An SDET can trivially and automatically assert these headers are present on every response as part of a routine functional/API test suite — a lightweight, high-leverage check that catches a real security regression (someone accidentally removing a security middleware) with almost no extra effort.

Q476 What is clickjacking, and how doesX-Frame-Options/CSPframe-ancestorshelp prevent it?

Clickjacking tricks a user into clicking something on a page that’s invisibly framed underneath what they think they’re clicking (e.g., a transparent iframe of a real banking action overlaid under a fake “claim your prize” button). X-Frame-Options (or the more flexible CSP frame-ancestors directive) tells the browser not to allow the page to be embedded in an iframe on another site at all, preventing this attack vector entirely.

Q477 What is the difference between encryption at rest and encryption in transit?

Encryption in transit protects data while it’s moving across a network (HTTPS/TLS). Encryption at rest protects data while it’s stored (database encryption, encrypted disk volumes) — a system can have one without the other, and both matter: data can be intercepted while moving, or exposed via a stolen backup/compromised storage even if every network transfer was properly encrypted.

Q478 What is a penetration test, and how does an SDET’s security-aware functional testing differ from it?

A penetration test is a dedicated, deliberate simulated attack conducted by security specialists actively trying to break into a system using deep, specialized techniques and tools. An SDET’s security-aware functional testing is much lighter-weight — checking for the presence of basic protections (headers, session cookie flags, obvious injection points, authorization gaps) as part of routine functional coverage — valuable as an early, continuous first line of defense, but not a substitute for a proper periodic pen test by specialists.

Q479 What is rate limiting, and why is it considered a security control, not just a performance one?

Rate limiting caps how many requests a client can make in a given time window. Beyond protecting infrastructure from overload, it’s a genuine security control because it mitigates brute-force attacks (repeatedly guessing passwords or OTP codes), credential stuffing, and scraping — testing that sensitive endpoints (login, OTP verification) are actually rate-limited is as much a security test as a performance one.

Q480 How would you responsibly report a security vulnerability you accidentally discovered while doing normal functional testing?

Stop actively probing further (don’t escalate into something that looks like an unauthorized attack), document exactly what you observed and how to reproduce it with the minimum necessary evidence, and report it privately and promptly through the organization’s defined security-disclosure channel (a security team, not a public ticket or Slack channel) — treating it with the same care and confidentiality you’d want if you were the one whose vulnerability was found.

Section M — Agile / Scrum & Software Process (Q481–490)

Q481 What is Agile, and how does it differ from the traditional Waterfall model?

Agile delivers software in small, iterative increments with continuous feedback and the ability to adapt requirements as understanding evolves, versus Waterfall’s sequential, phase-gated approach (requirements → design → build → test → release) where testing traditionally happens only at the very end, making late-discovered issues far more expensive to fix. Agile’s iterative nature is exactly what enables (and requires) testing to happen continuously throughout, not as a separate final phase.

Q482 What is Scrum, and what are its key ceremonies?

Scrum is a specific Agile framework organizing work into fixed-length sprints. Key ceremonies: sprint planning (deciding what will be worked on this sprint), the daily standup (a short sync on progress/blockers), the sprint review/demo (showing completed work to stakeholders), and the sprint retrospective (the team reflecting on what went well/poorly in the process itself and how to improve).

Q483 What is the role of a QA/SDET within a Scrum team, and how does it differ from a traditional, separate QA phase?

In Scrum, testing is embedded within the sprint itself, alongside development, rather than happening in a dedicated phase after development is “done” — an SDET is involved from story refinement (helping shape testable acceptance criteria) through implementation (writing tests alongside the feature being built) rather than only receiving a finished feature to test at the very end of a cycle, which is what shift-left testing concretely looks like in practice.

Q484 What is a user story, and what makes its acceptance criteria “testable”?

A user story is a short, informal description of a feature from the end user’s perspective (“As a [user], I want [goal], so that [benefit]”). Testable acceptance criteria are specific and unambiguous enough that two different people would independently agree on whether they’re met — “the page loads fast” isn’t testable; “the page loads in under 2 seconds on a standard connection” is.

Q485 What is the Definition of Done, and why does it matter for testing?

It’s the team’s explicit, agreed checklist of what “complete” means for any piece of work — typically including things like “unit tests written,” “acceptance criteria verified,” “no known critical defects,” “code reviewed.” Having testing explicitly baked into the Definition of Done prevents a feature from being considered finished purely because the code was written, closing the common gap where “done” quietly meant “developer thinks it works” rather than “actually verified.”

Q486 What is a sprint retrospective, and what’s a testing-related improvement you might raise in one?

It’s a recurring, dedicated meeting for the team to reflect on their own process and identify concrete improvements, separate from reviewing the actual product output. A testing-related example: raising that a specific class of bug keeps slipping through to a later stage repeatedly, and proposing a concrete process change (a new checklist item, an earlier test-design conversation during refinement) to catch that category earlier next sprint.

Q487 What is the difference between Scrum and Kanban?

Scrum works in fixed-length sprints with a committed, time-boxed set of work per sprint and structured ceremonies around that cadence. Kanban is a continuous flow model with no fixed iterations — work items move through defined stages on a board, with limits on how much work-in-progress is allowed at each stage, and there’s no sprint-boundary “commitment” the way Scrum has — Kanban tends to suit teams with more unpredictable, interrupt-driven work (like production support) better than Scrum’s fixed-sprint structure does.

Q488 What is technical debt, and how would you make a case for allocating sprint time to pay down test-automation-specific debt?

Technical debt is the accumulated cost of shortcuts or deferred improvements that make future work slower or riskier. To make the case for automation-specific debt, I’d translate it into terms the team already prioritizes by — quantify the recurring cost (hours lost weekly to flaky-test triage, CI time wasted on an inefficient suite) so it competes fairly for sprint capacity against feature work using the same “cost/benefit” language, rather than being framed as an abstract “we should clean this up sometime” ask.

Q489 What is a backlog, and how do defects typically get prioritized alongside new feature work?

The backlog is the full, ordered list of everything the team might work on — features, bugs, technical debt — ranked by priority. Defects usually get triaged by severity/impact into that same prioritized backlog (a release-blocking critical bug jumps to the top immediately, while a low-impact cosmetic bug competes on the same footing as any other lower-priority backlog item) rather than living in a separate, disconnected bug tracker that the team plans around independently.

Q490 What is shift-left testing, and how does it change when an SDET gets involved in a sprint?

Shift-left means moving testing activities as early as possible in the development process, rather than treating it as a final gate — concretely, an SDET participates in story refinement and design discussions before a single line of code is written, helping shape testable acceptance criteria and flagging edge cases upfront, and often writes test automation in parallel with (not strictly after) feature development, catching issues while they’re still cheap and easy to fix rather than after the feature is considered “complete.”

Section N — Version Control (Git) Fundamentals (Q491–500)

Q491 What is Git, and how does it differ from a centralized system like SVN?

Git is a distributed version control system — every developer has a full local copy of the entire repository’s history, not just a working copy synced against one central server. This means most operations (committing, branching, viewing history) work fully offline and are fast, and there’s no single point of failure the way a centralized server represents in SVN — the trade-off is a genuinely different mental model (local commits vs. server-tracked revisions) that takes some adjustment coming from a centralized system.

Q492 What is the difference betweengit mergeandgit rebase, and when would you prefer one?

git merge combines two branches’ histories with a new merge commit, preserving the exact history of how development actually happened (including all the back-and-forth), which is honest but can get noisy on a long-lived branch. git rebase replays your branch’s commits on top of the target branch’s latest state, producing a cleaner, linear history — I’d rebase a local feature branch before opening a PR (for a clean, readable history) but avoid rebasing a branch that others have already pulled from, since rewriting shared history breaks everyone else’s local copies.

Q493 What is a merge conflict, and how do you resolve one?

A merge conflict occurs when Git can’t automatically reconcile changes to the same lines (or the same file, depending on the conflict type) made independently on two branches. Resolving it means manually opening the conflicted file, deciding which changes to keep (or how to combine them), removing Git’s conflict markers, and committing the resolution — good communication with whoever made the conflicting change often matters as much as the technical merge itself, especially for a non-trivial conflict.

Q494 What is the difference betweengit fetchandgit pull?

git fetch downloads the latest changes from the remote into your local repository’s tracking branches, without touching your current working branch at all — a safe way to see what’s changed remotely before deciding what to do. git pull does a fetch and immediately merges (or rebases, depending on config) those changes into your current branch — more convenient for a quick sync, but less controlled than a deliberate fetch-then-review-then-merge workflow.

Q495 What is a Git branching strategy, and what’s the difference between GitFlow and trunk-based development?

A branching strategy is the team’s agreed convention for how branches are created, named, and merged. GitFlow uses long-lived develop and main branches plus dedicated feature/release/hotfix branches, with a more structured (and heavier) release process — well-suited to projects with formal, scheduled releases. Trunk-based development keeps everyone merging small, frequent changes directly into a single main branch (often behind feature flags for anything not yet ready), suited to teams practicing true continuous delivery who want to minimize long-lived branch divergence and merge pain.

Q496 What isgit stash, and when would you use it?

git stash temporarily shelves your uncommitted working-directory changes, restoring a clean working state, which you can later reapply with git stash pop. Useful when you need to quickly switch context (a production hotfix interrupts your in-progress feature work) without wanting to commit unfinished, half-working code just to switch branches.

Q497 What is a.gitignorefile, and what should always be excluded from a test automation repository?

It lists file/folder patterns Git should never track. For a test automation repo, I’d always exclude: node_modules/, generated test artifacts (playwright-report/, test-results/, trace files, screenshots/videos from local runs), .env files containing local secrets, and any IDE-specific config folders — nothing that’s either regenerable or sensitive belongs committed to the repository.

Q498 What is the difference betweengit resetandgit revert, and why is one safer for shared branches?

git reset moves the branch pointer backward, effectively rewriting history as if certain commits never happened — dangerous on a shared branch because anyone else who already has those commits will have a diverging, conflicting history. git revert creates a new commit that undoes the changes of a previous commit, leaving history intact and forward-only — the safe choice for undoing something on a branch other people are also working from.

Q499 What is a pull request, and what makes for a good PR description in a test automation repository?

A pull request proposes merging one branch’s changes into another, providing a structured place for review and discussion before the merge happens. A good PR description for a test-automation change states what changed and why (not just “updated tests”), notes any new flakiness risk or CI-time impact, links the related ticket/requirement, and — for a framework-level change — explicitly flags if it’s backward-incompatible for other consumers, since that context is what actually lets a reviewer give meaningful feedback rather than a rubber-stamp approval.

Q500 What isgit bisect, and how could it help find which commit introduced a broken test?

git bisect automates a binary search through commit history: you mark a known-good and a known-bad commit, and Git checks out the midpoint for you to test, narrowing the range by half each round until it pinpoints the exact commit that introduced the regression — dramatically faster than manually checking out and testing commits one by one, especially valuable for tracking down when a test started flaking or a bug was introduced across a long, undifferentiated commit history.
