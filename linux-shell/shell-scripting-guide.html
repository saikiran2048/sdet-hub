$ cat run_regression.sh

00

Absolute Beginner Primer

read this first if you've never used a terminal

Everything after this section assumes you're comfortable typing commands into a terminal. If you're not, start here — five minutes now saves confusion later.

What a terminal actually is

A terminal (also called a console or command line) is a text window where you type commands instead of clicking icons. You type a command, press Enter, and the shell (see §1) runs it and prints the result back. There is no "undo" button — every command runs immediately, so read a command before pressing Enter, especially anything with rm (delete) in it.

The prompt

Before every command you type, the terminal shows a prompt — a short line telling you who you are, what machine you're on, and where you currently are in the filesystem. It typically ends in $ (regular user) or # (root/admin user). For example:

terminal
sdet@qa-runner:~/projects/regression-suite$

Reading it left to right: sdet is the logged-in user, qa-runner is the machine's hostname, and ~/projects/regression-suite is the current directory (~ means "my home folder"). Everything you type appears after the $.

Files, folders, and paths

Linux organizes everything in one single tree starting at / (the root of the filesystem — unrelated to the "root" user). A path is the address of a file or folder in that tree.

Path typeExampleMeaning
Absolute/home/sdet/scripts/run.shStarts with / — same location no matter where you currently are
Relativescripts/run.shInterpreted starting from your current directory — changes meaning depending on where you are
Home shortcut~/scripts/run.sh~ expands to your home directory, e.g. /home/sdet
Current dir./run.sh. means "here" — required when running a script in your current folder
Parent dir../logs.. means "one folder up"

Commands you'll type before you ever write a script

terminal
# where am I right now?
pwd

# what's in this folder?
ls
ls -la          # -l = long/detailed list, -a = include hidden files (start with .)

# move into a folder
cd projects/regression-suite
cd ..            # go up one level
cd ~             # go to home directory
cd -             # go back to the previous directory

# create things
mkdir logs               # new folder
touch run.sh              # new empty file

# view a file's contents
cat run.sh                # dump whole file to screen
less run.sh                # scrollable viewer, press q to quit
head -n 20 run.sh           # first 20 lines
tail -n 20 run.sh            # last 20 lines
tail -f app.log               # "follow" — stream new lines live, e.g. watching a running test

# copy, move/rename, delete
cp run.sh run_backup.sh
mv run_backup.sh archive/
rm run_backup.sh          # permanent — no recycle bin
rm -r old_reports/         # -r = recursive, needed to delete a folder
Beginner trap rm -rf deletes recursively and forcefully with zero confirmation. Before running it, run ls on the same path first to see exactly what you're about to delete. There is no trash can to recover from.

Permissions, in plain terms

Every file has three permission groups — owner, group, and everyone else — and three permission types each: read, write, execute. ls -l shows them as a 10-character string like -rwxr-xr--.

terminal
# symbolic form — add (+) or remove (-) execute permission for the owner
chmod +x run.sh
chmod u+x run.sh

# numeric form — r=4, w=2, x=1, summed per group (owner/group/other)
chmod 755 run.sh     # owner: rwx(7), group: r-x(5), other: r-x(5)
chmod 644 config.yaml  # owner: rw-(6), group: r--(4), other: r--(4) — common for data files

You'll hit this constantly: a freshly written or freshly cloned script usually isn't executable yet, and ./script.sh fails with "Permission denied" until you run chmod +x on it.

PATH — how the shell finds commands

When you type mvn or java, the shell doesn't know where those programs live by magic — it searches a list of folders stored in the PATH environment variable, in order, until it finds a matching executable.

terminal
# see the search list (colon-separated)
echo $PATH

# find exactly which file will run for a given command
which java
which mvn

# add a folder to PATH for this session
export PATH="$PATH:/opt/maven/bin"

"Command not found" almost always means the program either isn't installed, or its folder isn't in PATH.

Exit codes — how the shell knows pass vs fail

Every command, when it finishes, sets an invisible number called its exit code. 0 means success; anything from 1–255 means some kind of failure. This single convention is what every if, &&, and CI pipeline pass/fail decision is built on.

terminal
ls /some/real/folder
echo "$?"     # prints 0 — the previous command succeeded

ls /nonexistent
echo "$?"     # prints 2 (or similar non-zero) — it failed
Why this matters for SDETs When your CI pipeline shows a build as "failed," it's almost always because some command in the pipeline exited non-zero — most importantly, your test runner (mvn test, for example) exits non-zero when any test fails. Understanding exit codes is understanding how CI/CD actually decides pass vs fail.

Foundations of the Linux Shell

runtime 0:29 – 6:56

What the shell actually is

The kernel is the core of Linux — it manages memory, processes, and hardware. You never talk to it directly. The shell is the program that sits between you and the kernel: it reads the commands you type, interprets them, and asks the kernel to execute them, then hands the output back to you.

When you run a script, you are not "programming Linux" — you are writing a sequence of instructions for the shell interpreter, which translates them into system calls.

bash

Bourne Again Shell. The default on almost every Linux distro and the one CI runners assume. Learn this first.

sh

The original POSIX shell. Scripts written for sh are more portable but lose bash-only features (arrays, [[ ]]).

zsh

Default on macOS since Catalina. Mostly bash-compatible for scripting; differences show up in interactive config, not scripts.

dash

A minimal, fast shell — often what /bin/sh actually points to on Debian/Ubuntu. Bash-isms silently fail here.

Checking your current shell

terminal
# what your login shell is set to
echo $SHELL

# what shell is actually running THIS process (more reliable)
ps -p $$

# bash-specific version info
echo $BASH_VERSION
SDET angle Docker images used by CI runners often use dash as /bin/sh, not bash. If your test-setup script uses arrays or [[ ]] but is invoked as sh script.sh inside a pipeline container, it will fail with cryptic syntax errors. Always confirm the shell your CI executor actually uses before assuming bash syntax is safe.

Why shell scripting matters for testing

As an SDET, shell scripts are the glue around your automation framework, not the framework itself. Typical uses: spinning up test environments, pulling/rotating test data, checking service health before a suite runs, parsing logs for failures, and wiring everything into CI schedules. A framework in Java/Python does the testing; the shell script decides when and under what conditions that framework runs.

Getting Started with Scripting

runtime 6:56 – 18:13

Your first script

setup_env.sh
#!/bin/bash
# Prepares environment variables before a test run
echo "Setting up test environment..."
export ENV=qa
echo "Environment set to $ENV"

The shebang line

#!/bin/bash on line 1 tells the OS which interpreter should execute the rest of the file. Without it, running the file directly falls back to whatever shell invoked it, which may not support the syntax you wrote. Common variants:

ShebangMeaning
#!/bin/bashAbsolute path to bash — most common, most predictable
#!/usr/bin/env bashFinds bash via PATH — more portable across systems where bash isn't at /bin/bash
#!/bin/shPOSIX shell — safest, most limited feature set

Running a script — three ways, three behaviors

terminal
# 1. Direct execution — needs execute permission + shebang
chmod +x setup_env.sh
./setup_env.sh

# 2. Explicit interpreter — shebang ignored, permission not required
bash setup_env.sh

# 3. Sourcing — runs in your CURRENT shell, not a subshell
#    variables/exports set here persist after the script ends
source setup_env.sh
# or
. setup_env.sh
Common trap If a setup script does export ENV=qa and you run it with ./setup_env.sh or bash setup_env.sh, that export dies with the subshell — your current terminal never sees $ENV. You must source it for exports to carry into your session. This is the #1 reason "my env var isn't set" bugs happen in test setup scripts.

Comments

terminal
# single-line comment

: '
this is a multi-line block comment,
a colon followed by a quoted string is a no-op
'

Variables, Arrays, and Strings

runtime 18:13 – 47:37

Variables

terminal
browser="chrome"          # no spaces around =
readonly MAX_RETRIES=3     # cannot be reassigned
export BASE_URL="https://qa.app.com"  # visible to child processes

echo "Running on $browser"
echo "Running on ${browser}_headless"  # braces avoid ambiguity

Arrays

browsers.sh
browsers=("chrome" "firefox" "edge")

echo "${browsers[0]}"        # chrome — indexing starts at 0
echo "${browsers[@]}"        # all elements
echo "${#browsers[@]}"       # array length -> 3

browsers+=("safari")          # append
unset 'browsers[1]'            # remove firefox

String operations

OperationSyntaxExample

User input

terminal
read -p "Enter test environment (dev/qa/prod): " env

Arithmetic

terminal
total=$((5 + 3))
retry=0
((retry++))                    # increment
let "count = count + 1"

# floating point needs bc — bash arithmetic is integer-only
avg=$(echo "scale=2; $total / 3" | bc)
SDET angle Use an array to hold suite names or browser targets and iterate it in your CI script, instead of hardcoding three near-duplicate commands. Use ${var//old/new} when sanitizing log lines before writing a summary report (e.g. stripping timestamps or replacing spaces so a filename is safe).

Logic, Conditions, and Loops

runtime 50:10 – 1:26:52

Conditionals

check_env.sh
if [[ "$env" == "prod" ]]; then
    echo "Refusing to run destructive tests against prod"
    exit 1
elif [[ "$env" == "qa" ]]; then
    echo "Running full regression suite"
else
    echo "Unknown environment, defaulting to smoke suite"
fi

case — cleaner than chained elifs

terminal
case "$env" in
    dev)  BASE_URL="https://dev.app.com" ;;
    qa)   BASE_URL="https://qa.app.com" ;;
    prod) BASE_URL="https://app.com" ;;
    *)    echo "Unknown env: $env"; exit 1 ;;
esac

[ ] vs [[ ]], and logical operators

[[ ]] is a bash keyword — supports &&, ||, pattern matching, and doesn't word-split unquoted variables. [ ] is the older POSIX test command — more portable, more footguns. Default to [[ ]] in bash scripts.

terminal
if [[ -f "config.yaml" && -n "$env" ]]; then
    echo "Config present and env set — proceeding"
fi

# short-circuit style, common in CI scripts
[[ -f "results.xml" ]] || { echo "No results file — failing build"; exit 1; }

Loops

cross_browser_run.sh
# for — iterate a fixed list, classic cross-browser run
for browser in chrome firefox edge; do
    echo "Launching suite on $browser"
    ./run_suite.sh "$browser"
done

# while — poll until a condition is true
retries=0
while ! curl -sf "$BASE_URL/health" &> /dev/null; do
    ((retries++))
    [[ $retries -ge 10 ]] && { echo "Service never came up"; exit 1; }
    echo "Waiting for service... attempt $retries"
    sleep 5
done

# until — inverse of while
until [[ -f "test-report.html" ]]; do
    sleep 2
done
Infinite loops while true; do ... done is a real pattern for long-lived watchers (e.g. a script that tails a log directory and triggers reruns on new failures), but every infinite loop in a test-automation context needs an explicit break condition or external kill signal — otherwise a CI job hangs until it times out and burns runner minutes.

Functions and Advanced Concepts

runtime 1:27:06 – 1:58:33

Defining and calling functions

lib.sh
function wait_for_service() {
    # $1, $2 = positional args passed to the function
    local url="$1"
    local timeout="${2:-30}"   # default to 30 if not passed

    for ((i=0; i<timeout; i++)); do
        if curl -sf "$url" &> /dev/null; then
            return 0     # exit code, not a value — 0 = success
        fi
        sleep 1
    done
    return 1
}

if wait_for_service "http://localhost:8080/health" 20; then
    echo "Service is up — starting tests"
else
    echo "Timed out waiting for service"; exit 1
fi
Return vs echo A bash function's return only carries an integer exit code (0–255), used for success/failure — not real data. To return actual data (a string, a computed value), have the function echo it and capture with command substitution: result=$(my_function).

Script-level arguments

terminal
# invoked as: ./run_suite.sh qa smoke 3
echo "$1"     # qa      — first argument
echo "$2"     # smoke   — second argument
echo "$#"     # 3       — total argument count
echo "$@"     # qa smoke 3   — all args as separate words
echo "$0"     # run_suite.sh — the script's own name

Connectivity checks

terminal
# is the host reachable at all?
if ping -c 1 -W 2 "db.internal" &> /dev/null; then
    echo "Host reachable"
fi

# is the actual HTTP endpoint healthy? (more useful for APIs)
status=$(curl -s -o /dev/null -w "%{http_code}" "$BASE_URL/health")
[[ "$status" == "200" ]] && echo "API healthy" || echo "API down: $status"

File and directory existence checks

TestMeaning
-f "$file"Regular file exists
-d "$dir"Directory exists
-e "$path"Path exists (file or directory)
-x "$file"File exists and is executable
-s "$file"File exists and is non-empty
SDET angle Guard every test run with a pre-flight check: [[ -f "testdata.json" ]] || { echo "missing test data"; exit 1; }. Failing fast with a clear message beats letting the framework fail 40 minutes later with a confusing null-pointer because a fixture file wasn't there.

Output redirection

Background execution with nohup

& backgrounds a process for the current session, but it still dies if the shell/SSH session closes. nohup detaches it from the controlling terminal's hangup signal, so a long regression suite keeps running after you disconnect.

terminal
# survives SSH disconnect — output goes to nohup.out by default
nohup ./run_full_regression.sh > regression.log 2>&1 &

# get the PID to check on it or kill it later
echo "Running as PID $!"

One-off scheduling with at

terminal
# run a single script once, tonight at 11pm
echo "./run_full_regression.sh" | at 23:00

# list pending at-jobs
atq

Recurring schedules with crontab

terminal
crontab -e     # open your crontab for editing
crontab -l     # list current cron jobs
FieldRange

month1–12
day of week0–6 (Sun–Sat)
crontab -e
# nightly regression suite at 1:30 AM, every day

# smoke suite every weekday at 8:00 AM before the team starts
0 8 * * 1-5 /home/sdet/scripts/run_smoke.sh

# health check every 15 minutes
*/15 * * * * /home/sdet/scripts/check_env_health.sh
Reliability tip Cron runs with a minimal environment — no PATH extensions, no shell profile sourced. A script that works fine when you run it manually can fail silently under cron because java, node, or your test binary isn't found. Always use absolute paths inside cron-triggered scripts, and always redirect output to a log file so failures are visible.
SDET angle This is the layer that turns a test suite into a real regression pipeline: nohup for suites too long for an interactive session, crontab for nightly/weekly cadences, and disciplined redirection so every run leaves a log you can actually debug from — instead of scrollback that vanished when the terminal closed.

07

End-to-End Scenario: Java + Selenium + TestNG + Maven

how every command above shows up in a real pipeline

The scenario You're the SDET on call. Every weeknight, before the team arrives, a regression suite should: pull the latest code, confirm the QA environment is actually up, build the project, run the TestNG regression suite through Maven, check whether it passed, archive the report, and post a Slack alert if it failed — all unattended, all logged, so you can check one file in the morning instead of re-running anything.

Below is that pipeline built up piece by piece. Each command is one you've already seen in §1–§6 — this section is about how they chain together in practice.

Step 1 — Get the latest code

The script starts by moving into the project folder and pulling the latest commit, so the nightly run always tests what was actually merged, not a stale local copy.

nightly_regression.sh — part 1
#!/bin/bash
set -e   # stop the whole script the instant any command fails

PROJECT_DIR="/home/sdet/projects/regression-suite"
LOG_DIR="$PROJECT_DIR/logs"
DATE=$(date +%F)
LOG_FILE="$LOG_DIR/nightly_$DATE.log"
SLACK_WEBHOOK="https://hooks.slack.com/services/XXX/YYY/ZZZ"

mkdir -p "$LOG_DIR"          # -p: no error if it already exists
cd "$PROJECT_DIR"

echo "[$(date)] Pulling latest code..." | tee -a "$LOG_FILE"
git pull origin main >> "$LOG_FILE" 2>&1

set -e is the single most important line in a CI script — without it, bash keeps executing later commands even after an earlier one fails, silently producing a "green" build on broken code. tee -a writes to both the screen and the log file at once, appending instead of overwriting.

Step 2 — Confirm the environment is actually reachable

No point running a 40-minute suite against a QA environment that's mid-deploy. This reuses the wait_for_service function pattern from §5.

nightly_regression.sh — part 2
wait_for_service() {
    local url="$1" timeout="${2:-30}"
    for ((i=0; i<timeout; i++)); do
        curl -sf "$url" &> /dev/null && return 0
        sleep 1
    done
    return 1
}

if ! wait_for_service "https://qa.app.com/health" 30; then
    echo "[$(date)] QA environment unreachable — aborting run" | tee -a "$LOG_FILE"
    exit 1
fi

Step 3 — Confirm the toolchain is present

Cron runs with a minimal environment (see §6's reliability tip) — this check catches a broken runner before it wastes 40 minutes.

terminal
java -version >> "$LOG_FILE" 2>&1  || { echo "Java not found"; exit 1; }
mvn -version >> "$LOG_FILE" 2>&1  || { echo "Maven not found"; exit 1; }

Step 4 — Build and run the suite through Maven

This is the command your framework actually runs on. mvn clean test is the standard Maven+TestNG entry point: clean wipes the previous build's output, test compiles the code and runs the test phase, which triggers Surefire to execute the TestNG suite XML.

nightly_regression.sh — part 3
echo "[$(date)] Starting Maven build + TestNG suite..." | tee -a "$LOG_FILE"

mvn clean test \
    -DsuiteXmlFile=testng-regression.xml \
    -Dbrowser=chrome \
    -DbaseUrl=https://qa.app.com \
    -Denv=qa \
    >> "$LOG_FILE" 2>&1

MVN_EXIT_CODE=$?   # capture exit code IMMEDIATELY — the next command overwrites $?
FlagWhat it does
cleanDeletes the target/ folder from any previous run — no stale class files
testRuns the Maven lifecycle through the test phase — compiles + executes tests
-DsuiteXmlFile=Tells the Surefire plugin which TestNG suite XML to run (your regression suite, not smoke)
-D<key>=<value>Passes a Java system property into the JVM — this is how shell variables reach your Java test code via System.getProperty("browser")
Why set -e is temporarily wrong here A failed test suite makes mvn test exit non-zero — with set -e still active, the script would stop dead at this line and never reach the reporting/notification steps below. In practice you either run this one command with set +e / set -e around it, or (as shown) explicitly capture $? and let the script continue on purpose so it can still report the failure.

Step 5 — Parse the results

Surefire writes machine-readable XML per test class to target/surefire-reports/. A quick grep across those files gives you pass/fail counts without needing to open a report viewer.

nightly_regression.sh — part 4
TOTAL_FAILURES=$(grep -h -oP 'failures="\K[0-9]+' target/surefire-reports/*.xml \
                  | awk '{s+=$1} END {print s}')
TOTAL_TESTS=$(grep -h -oP 'tests="\K[0-9]+' target/surefire-reports/*.xml \
             | awk '{s+=$1} END {print s}')

echo "[$(date)] Result: $((TOTAL_TESTS - TOTAL_FAILURES))/$TOTAL_TESTS passed" | tee -a "$LOG_FILE"

grep -oP extracts just the matched number instead of the whole line; awk '{s+=$1} END {print s}' sums a column of numbers across every file — a standard shell one-liner for tallying results scattered across multiple report files.

Step 6 — Archive the report

terminal
ARCHIVE="$LOG_DIR/surefire-report_$DATE.tar.gz"
tar -czf "$ARCHIVE" target/surefire-reports/
echo "[$(date)] Report archived to $ARCHIVE" | tee -a "$LOG_FILE"

Step 7 — Notify only on failure

nightly_regression.sh — part 5
if [[ $MVN_EXIT_CODE -ne 0 ]]; then
    curl -s -X POST "$SLACK_WEBHOOK" \
         -H 'Content-type: application/json' \
         -d "{\"text\":\"Nightly regression FAILED: $((TOTAL_TESTS - TOTAL_FAILURES))/$TOTAL_TESTS passed. See $LOG_FILE\"}"
    echo "[$(date)] Failure notification sent" | tee -a "$LOG_FILE"
else
    echo "[$(date)] All tests passed — no notification needed" | tee -a "$LOG_FILE"
fi

exit $MVN_EXIT_CODE

Exiting with $MVN_EXIT_CODE at the very end matters: it's what makes this script's own pass/fail status accurately reflect whether the tests passed, which matters if this script itself is ever wrapped by another CI tool (Jenkins, GitLab CI) checking its exit code.

Step 8 — Schedule it

The finished script gets one line in crontab, tying together everything from §6:

crontab -e
# every weeknight at 1:30 AM
30 1 * * 1-5 /home/sdet/projects/regression-suite/nightly_regression.sh
The full picture Notice nothing here is exotic — it's cd, export, if, a loop, a function, redirection, grep/awk, and crontab, chained around one mvn call. That chaining — not any single command — is what shell scripting contributes to a test framework: it's the difference between "a suite I run by hand" and "a pipeline that runs itself and only interrupts you when something's actually wrong."
Try it — extend the pipeline
Add a step between Step 5 and Step 6 that fails the script early (before archiving/Slack) if TOTAL_TESTS comes back as 0 — which would indicate the suite XML path was wrong and nothing actually ran, a silent failure mode that's easy to miss otherwise.
