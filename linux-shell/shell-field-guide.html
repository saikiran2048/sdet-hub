01 Navigation

The filesystem is a building, and you're standing somewhere in it

Think of the filesystem like an office building. / is the ground floor lobby. Every folder is a room, and rooms have rooms inside them (subfolders). At any moment you're standing in exactly one room — pwd asks "which room am I in?", ls asks "what's in this room?", and cd is you physically walking to another room.
pwd— print working directory
▶

Tells you the full path of the room you're standing in right now.

$ pwd/home/sai/test-automation
ls— list directory contents
▶

ls -l gives long format (permissions, size, date). ls -a shows hidden files (dotfiles like .env). ls -lh makes sizes human-readable (KB/MB instead of raw bytes).

$ ls -ladrwxr-xr-x 5 sai sai 4096 Jul 18 09:02 . -rw-r--r-- 1 sai sai 210 Jul 18 09:01 .env -rw-r--r-- 1 sai sai 1822 Jul 17 22:41 testng.xml drwxr-xr-x 3 sai sai 4096 Jul 17 22:40 src
SDET use: checking if a config or report file actually got generated after a test run, or spotting a hidden .env holding test credentials.
cd— change directory
▶

cd .. = go up one room. cd ~ or cd alone = go home. cd - = go back to the previous room you were in (very handy).

$ cd src/test/resources $ cd -/home/sai/test-automation
tree— show folder structure as a tree
▶

Not installed by default (sudo apt install tree). Gives you the whole building's floor plan at once instead of room by room.

$ tree -L 2. ├── src │ ├── main │ └── test └── testng.xml

02 Files & Directories

Creating, copying, moving, and deleting rooms and paperwork

If files are documents and folders are rooms: mkdir builds a new room, touch creates a blank sheet of paper, cp photocopies a document, mv physically relocates it (or renames the label on it), and rm shreds it — there's no recycle bin, so it's permanent.
mkdir— make directory
▶

-p builds nested folders in one go, creating parents that don't exist yet.

$ mkdir -p reports/2026/july
touch— create an empty file / update timestamp
▶
$ touch execution.log
cp— copy
▶

-r is required to copy a whole folder (recursive) — copying a room means copying everything inside it too.

$ cp config.properties config.properties.bak $ cp -r target/surefire-reports/ ~/backup-reports/
mv— move or rename
▶

There's no separate "rename" command in Linux — moving a file to the same folder with a different name IS renaming it.

$ mv old_testsuite.xml regression_suite.xml
rm— remove (permanent!)
▶

-r for folders, -f to force without asking. rm -rf is powerful and dangerous — always double check your pwd before running it.

$ rm old_screenshot.png $ rm -rf target/ # wipes the whole build output folder
find— locate files by name, type, or age
▶
$ find . -name "*.log" $ find . -mtime -1 -name "*.xml" # files changed in last 1 day
SDET use: hunting down which of hundreds of test result files got generated in the last run, or finding leftover temp screenshots from failed Selenium tests.

03 Viewing File Content

Reading a document without opening it in an editor

Imagine a huge printed log — you almost never want to unroll the whole scroll. cat dumps it all at once, less lets you scroll through it page by page, and tail/head just show you the last or first few lines, like peeking at the end or the start of a receipt.
cat— print whole file to screen
▶
$ cat pom.xml
less— scrollable pager
▶

Arrow keys to scroll, /searchterm to search inside, q to quit. Use this instead of cat for big files.

$ less execution.log
head / tail— first / last N lines
▶

tail -f is the big one — it "follows" a file live, printing new lines as they're written. This is how you watch a test run as it happens.

$ tail -n 50 execution.log $ tail -f jenkins-build.log # live-tails the file, Ctrl+C to stop
SDET use: tail -f a Jenkins console log or an app server log while your regression suite runs, to catch failures the moment they happen instead of waiting for the whole run to finish.

04 Permissions

Who's allowed to read, write, or run a file — like a badge access system

Every file has three badge levels: the owner, the group, and everyone else. For each, there are three permissions: read it, write/edit it, execute it (run it as a program). -rwxr-xr-- reads left to right: owner can do all three, group can read+execute, others can only read.
chmod— change permissions
▶

Numbers: r=4, w=2, x=1 — add them up per badge level. 755 = owner full (7), group read+execute (5), others read+execute (5).

$ chmod +x run_tests.sh # make a script runnable $ chmod 755 deploy.sh
SDET use: the classic "Permission denied" error when trying to run a shell script in a CI pipeline — 9 times out of 10 it just needs chmod +x.
chown— change file owner
▶
$ sudo chown sai:sai config.yaml
sudo— run a command as admin
▶

Short for "superuser do" — like using a manager's master key for one action only.

$ sudo apt update

05 Text Processing

This is where the shell becomes a search-and-filter machine for logs

If a log file is a giant spreadsheet of raw text, grep is Ctrl+F, cut and awk pull out specific columns, sort and uniq are Excel's "sort" and "remove duplicates," and wc just counts rows. This is the toolkit you'll use most as an SDET, hands down.
grep— search text by pattern
▶

-i ignore case, -n show line numbers, -r search recursively through folders, -v invert (show lines that DON'T match), -c just count matches.

$ grep -in "error" execution.log142:[ERROR] Element not found: #login-btn 310:[ERROR] Timeout waiting for response $ grep -r "FAILED" target/surefire-reports/
SDET use: the single most-used command in this whole guide. Grepping "FAILED", "Exception", or "ERROR" out of a huge automation log in seconds instead of scrolling manually.
sed— find and replace text (stream editor)
▶
$ sed 's/staging/production/g' config.properties
SDET use: swapping environment URLs in a config file before pointing a test run at a different environment.
awk— column-based text processing
▶

Think of it as picking a specific column out of space/comma-separated text. $1 = column 1, $2 = column 2, etc.

$ awk '{print $1, $4}' access.log # prints columns 1 and 4
cut— extract columns from delimited text
▶
$ cut -d',' -f2 users.csv # field 2 from a CSV
sort / uniq— sort lines / remove duplicates
▶

uniq only removes duplicates that are adjacent — that's why you almost always sort first.

$ sort error_codes.txt | uniq -c | sort -rn 47 500 12 404 3 401
SDET use: that exact one-liner above is a quick way to see which error code showed up most across thousands of failed API test logs.
wc— word/line/byte count
▶
$ wc -l execution.log2140 execution.log

06 Pipes & Redirection

This is the real superpower — chaining commands like an assembly line

A pipe | takes the output of one command and feeds it as input to the next — like handing a stack of papers from one desk to the next, each person doing one small job. Redirection (> and >>) instead sends output into a file rather than the screen — > overwrites the page, >> appends to the bottom of it.
| (pipe)— chain command output into the next command
▶
$ cat execution.log | grep "ERROR" | wc -l7 # "print the file, filter for ERROR lines, count them" — 3 tools, 1 line
> and >>— redirect output to a file
▶
$ mvn test > results.log # overwrite results.log $ echo "run complete" >> results.log # append a line
2>&1— redirect errors along with normal output
▶

Every command has two output streams: normal output (stdout, stream 1) and errors (stderr, stream 2). This merges stderr into stdout so both land in the same file.

$ mvn test > results.log 2>&1
SDET use: capturing a Jenkins shell step's full output — including stack traces — into one log file for debugging a broken build.

07 Processes

Every running program is a worker on the floor with an ID badge

ps and top are the manager's clipboard listing who's currently working and how hard. Every process has a PID (a badge number). kill sends that worker home — politely by default, forcibly with -9.
ps— snapshot of running processes
▶
$ ps aux | grep javasai 4821 12.0 3.2 java -jar selenium-server.jar
SDET use: checking whether a hung Selenium Grid node or chromedriver process is still eating CPU after a test run "finished."
top / htop— live process monitor
▶

htop is the nicer, colorized version (installed separately). q to quit.

$ top
kill— stop a process by PID
▶
$ kill 4821 # asks it nicely to stop $ kill -9 4821 # forces it to stop immediately
&, jobs, nohup— background and detach processes
▶

& at the end runs a command in the background so your terminal stays free. nohup keeps it running even after you log out — useful on a remote test server.

$ nohup ./run_regression.sh &

08 Environment Variables & PATH

Sticky notes the shell can read at any time, from anywhere

An environment variable is a labeled sticky note pinned to your session — $JAVA_HOME, $PATH. $PATH specifically is a list of folders the shell checks, in order, whenever you type a command name — like a list of storage rooms it searches through to find the tool you asked for.
export— set an environment variable
▶
$ export JAVA_HOME=/usr/lib/jvm/java-17 $ echo $JAVA_HOME/usr/lib/jvm/java-17
SDET use: a Jenkins job failing with "JAVA_HOME not set" — a classic environment variable issue you'll debug constantly running Maven/TestNG suites.
echo $PATH— see where the shell looks for commands
▶
$ echo $PATH/usr/local/bin:/usr/bin:/bin:/home/sai/bin
env / printenv— list all environment variables
▶
$ env | grep -i java
which— show which file a command actually runs
▶
$ which mvn/usr/bin/mvn

09 Networking Basics

Talking to servers the way your test framework does under the hood

If a URL is an address, ping just checks "is anyone home," curl actually knocks and asks for something (like your API test client does), and ssh is walking into someone else's building using your keys.
ping— check if a host is reachable
▶
$ ping -c 4 api.example.com
curl— make HTTP requests from the terminal
▶
$ curl -i https://api.example.com/healthHTTP/1.1 200 OK $ curl -X POST -H "Content-Type: application/json" -d '{"id":1}' https://api.example.com/orders
SDET use: sanity-checking an API endpoint from the terminal before writing a Rest Assured test for it — or debugging why a test is failing when Postman "works fine."
ssh / scp— remote login / secure copy
▶
$ ssh sai@10.20.30.40 $ scp report.html sai@10.20.30.40:/home/sai/reports/
SDET use: logging into a remote CI agent or Selenium Grid node to check why a job hung, or pulling test result files off a build server.
netstat / ss— see open ports and connections
▶
$ ss -tulnp | grep 8080

10 Shell Scripting Basics

Same logic as Java, just looser syntax and no compiler

Since you already think in Java: a shell script is like a class with one big main() and nothing else — no types, no semicolons needed, and everything is technically a string until proven otherwise. if, loops, and functions all exist, just with different punctuation.
Variables— no type declaration, no spaces around =
▶
#!/bin/bash ENV="staging" echo "Running against $ENV"
if / else— conditionals
▶

Java equivalent: if (result.equals("FAILED")) { ... } else { ... }

if [ "$RESULT" == "FAILED" ]; then echo "Test failed, sending alert" else echo "Test passed" fi
for loop— iterate over items
▶

Java equivalent: for (String env : envs) { ... }

for env in dev staging prod; do echo "Deploying to $env" done
Functions— reusable blocks
▶
run_suite() { mvn test -Dsuite=$1 } run_suite regression.xml
$? and exit codes— did the last command succeed?
▶

0 means success, anything else means failure — this is exactly how Jenkins decides if a pipeline stage passed or failed.

$ mvn test $ echo $?1 # non-zero = something failed
SDET use: Jenkins marks a pipeline "failed" purely based on the exit code of the last shell step — this is the mechanic behind every red build.

11 SDET Cheatsheet

One-liners you'll actually reach for on the job

Count failed tests in a log
$ grep -c "FAILED" execution.log
Watch a Jenkins log live while a build runs
$ tail -f /var/jenkins_home/jobs/regression/builds/lastBuild/log
Find test classes that reference a specific keyword
$ grep -rl "LoginTest" src/test/java/
Kill a stuck chromedriver / Selenium process
$ ps aux | grep chromedriver | awk '{print $2}' | xargs kill -9
Check disk space before a build fails mysteriously
$ df -h

13 Suggested 4-Week Roadmap

Little and often beats a single long binge

WEEK 1

Navigation, Files, Permissions

Do Linux Journey's "Grasshopper" unit end to end. Set up WSL2 or a VM and just live in the terminal — even for small things like making folders for your test projects.

WEEK 2

Text Processing + Pipes

Grab any real log file (export one from a past test run) and practice grep, sort, uniq, wc, and piping them together. Start OverTheWire Bandit levels 1–10.

WEEK 3

Processes, Environment, Networking

Practice ps/kill/curl against a public test API (e.g. reqres.in). Set environment variables and reference them in a script. Continue Bandit levels 10–20.

WEEK 4

Shell Scripting + Jenkins Tie-in

Write a small .sh script that runs a Maven test suite, checks the exit code, and greps the log for failures. Wire it into a local Jenkins Docker job as a build step.
