Q1Self Introduction and explain your current project in brief

This is a structured-narrative question, not a recall question — interviewers are scoring clarity, seniority signaling, and relevance, not facts. Use a Present → Past → Strength → Direction structure in under 90 seconds.

Structure to follow

  1. Current role (Present): "I'm a Senior SDET / Automation QA Consultant with ~4 years of experience, currently engaged on a General Motors Financial (GMF) project at Deloitte, where I work on automating BFSI-style workflows."
  2. Tech stack one-liner: "My core stack is Java, Selenium WebDriver, Cucumber BDD, TestNG, REST Assured, Maven, and Jenkins/Azure DevOps for CI/CD."
  3. Project in brief (what the system does + your scope): Describe the domain (financial transactions, loan/account workflows, etc.) and your specific ownership — UI automation, API layer, or both. Mention scale signals: parallel execution, data-driven suites, number of test cases automated.
  4. Differentiator (Past, brief): One sentence on prior BFSI experience — DBS Bank and USAA at TCS — to show domain depth across multiple banking clients.
  5. Close with direction: "I'm looking to bring that automation and BFSI testing experience into a product/GCC environment like Infosys."
Tip: Keep the project description outcome-focused ("reduced regression cycle time by automating X% of the suite") rather than purely descriptive. Infosys panels for 3–4 YOE roles weight communication clarity heavily in this opening question — rambling here often colors the rest of the interview.

Q3What is a Product Backlog and who owns it?

A Product Backlog is a prioritized, living list of everything that might be needed in the product — features, enhancements, bug fixes, technical debt items, and non-functional requirements. It's never "complete"; it evolves as the product and market understanding evolve.

Key characteristics

  • Items are ordered by priority/value (highest value at top)
  • Each item is typically a User Story with acceptance criteria
  • Continuously refined ("groomed") throughout the project

Ownership

The Product Owner (PO) owns the Product Backlog. They are accountable for:

  • Prioritizing items based on business value
  • Writing/clarifying acceptance criteria
  • Accepting or rejecting completed work against the Definition of Done
Note the distinction: Product Backlog (whole project, owned by PO) vs Sprint Backlog (subset committed for the current sprint, owned by the Dev Team).

Q4During Sprint Planning, how do you estimate story points for a user story?

Story points measure relative effort/complexity, not hours. Most teams use Planning Poker with Fibonacci-like values (1, 2, 3, 5, 8, 13, 21).

Factors considered while estimating

  • Complexity of the business logic involved
  • Effort — dev + test + automation effort combined
  • Uncertainty/Risk — unknowns, new integrations, third-party dependencies
  • Dependencies on other teams/APIs/data
  • Volume of test scenarios — for QA specifically: number of positive/negative/edge cases, cross-browser needs, API + UI + DB validation layers

Process

  1. BA/PO reads out the story and acceptance criteria
  2. Team asks clarifying questions
  3. Each member privately picks a point value (poker card or tool like Jira/Planning Poker plugin)
  4. Values revealed simultaneously; if there's a big spread, discuss and re-vote
  5. Converge on consensus value
As QA, you should explicitly call out testing complexity during estimation — e.g., a story needing new test data setup, mocking a third-party API, or DB validation should bump the points even if the dev change is small.

Q5Do all tickets require QA intervention? Can you give some examples?

No. Not every ticket needs QA testing — this shows you understand where QA effort adds value versus where it's wasted.

Tickets that typically DO need QA

  • New feature development (functional + regression impact)
  • Bug fixes (verify fix + regression around it)
  • UI/UX changes affecting user flows
  • API contract changes (request/response schema, status codes)
  • Configuration changes affecting business logic

Tickets that typically DON'T need QA (or need minimal QA)

  • Pure documentation updates (README, code comments, wiki pages)
  • Internal code refactoring with no functional change (covered by existing automated regression + unit tests)
  • Logging/monitoring additions that don't change behavior
  • Infrastructure/DevOps tickets (e.g., Jenkins pipeline tweaks) — may need a sanity smoke run rather than full QA cycle
  • Dependency version bumps with no API surface change — typically validated by automated regression suite, not manual QA
Good answer pattern: "I assess tickets based on whether they touch user-facing behavior or business logic. If it's purely internal/non-functional, I rely on the automated regression suite passing rather than allocating manual QA cycles."

Q6What is Regression Testing and why do we perform it?

Regression Testing is the practice of re-running existing test cases on a modified build to confirm that recent code changes (new features, bug fixes, config changes) haven't broken existing functionality.

Why it's performed

  • Software changes are interconnected — fixing one module can unintentionally break another ("ripple effect")
  • Ensures previously working features remain stable after every sprint/release
  • Builds confidence for production deployment
  • Critical in BFSI/financial systems where a regression bug can mean incorrect transaction processing

When it's run

  • After every bug fix
  • After every new feature merge
  • Before every release/deployment (full or targeted regression)
  • Nightly/on every CI build as automated regression (most mature setups)
Strong differentiator to mention: "We maintain an automated regression suite triggered via Jenkins/Azure DevOps pipelines on every merge to the main branch, which lets us catch regressions within minutes rather than waiting for a manual cycle."

Q9What is StaleElementReferenceException and in what scenarios have you faced it?

StaleElementReferenceException is thrown when a previously located WebElement is no longer attached to the DOM — Selenium holds a reference to an "old" version of the element that has since been replaced or removed.

Common scenarios that cause it

  • Page refresh/navigation after the element was located but before it's used
  • AJAX re-rendering — a section of the page (e.g., a table or grid) refreshes its DOM nodes after a filter/sort action, invalidating earlier references
  • DOM manipulation via JavaScript — element removed and re-added, even with identical attributes, creates a new DOM node
  • SPA frameworks (React/Angular) re-rendering components on state change

How to handle/avoid it

  1. Re-locate the element right before interaction instead of caching it in a variable for long
  2. Wrap interaction in a try-catch with retry logic:
public void clickWithRetry(By locator, WebDriver driver) {
    int attempts = 0;
    while (attempts < 3) {
        try {
            driver.findElement(locator).click();
            return;
        } catch (StaleElementReferenceException e) {
            attempts++;
        }
    }
    throw new RuntimeException("Element remained stale after retries");
}

3. Use ExpectedConditions.refreshed() combined with another condition in an explicit wait:

wait.until(ExpectedConditions.refreshed(
    ExpectedConditions.elementToBeClickable(locator)));
Real scenario to narrate: "In an account-transactions grid that re-renders after applying a date filter, I'd get StaleElementReferenceException if I located rows before the filter and tried clicking after. Fix was to re-locate the grid rows after the AJAX call completed, using an explicit wait on a 'loading spinner disappeared' condition."

Explicit Wait Local — applied to a specific element/condition Waits until a specific ExpectedCondition is true, or times out WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
wait.until(ExpectedConditions.visibilityOf(element));
Fluent Wait Local — most configurable Like Explicit Wait but lets you set polling frequency and exceptions to ignore while polling Wait<WebDriver> fluentWait = new FluentWait<>(driver)

Q11How do you handle dynamic web elements in Selenium?

Dynamic elements are those whose attributes (id, class) change on every page load/session — common in modern web apps with auto-generated IDs.

Strategies

  1. Relative/Partial locators using XPath functions: 
    // contains() for partially matching attribute values
driver.findElement(By.xpath("//button[contains(@id,'submit')]"));

// starts-with() when prefix is stable but suffix changes
driver.findElement(By.xpath("//input[starts-with(@id,'user_')]"));
  2. Text-based XPath when visible text is stable: 
    driver.findElement(By.xpath("//a[text()='Submit Application']"));
  3. Sibling/parent-child traversal using a stable nearby anchor element: 
    driver.findElement(By.xpath("//label[text()='Email']/following-sibling::input"));
  4. CSS attribute selectors as an alternative to XPath for performance: 
    driver.findElement(By.cssSelector("input[id^='user_']"));
  5. Combining multiple stable attributes (class + data-* attributes) rather than relying on a single volatile one
  6. For elements that appear/disappear dynamically (AJAX-loaded), always pair the locator strategy with an Explicit Wait on visibility/clickability rather than a static sleep

Q12How do you handle dropdowns when the Select class cannot be used?

Selenium's Select class only works on native HTML <select> tags. Many modern UIs use custom dropdowns built with <div>/<ul>/<li> (React-select, MUI, custom JS widgets) — Select class won't work there.

Approach for custom (non-native) dropdowns

  1. Click to open the dropdown trigger element
  2. Wait for the options list to render (explicit wait on visibility)
  3. Locate the desired option by visible text and click it
// Step 1: Click to open dropdown
driver.findElement(By.id("customDropdownTrigger")).click();

// Step 2: Wait for options panel
WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
wait.until(ExpectedConditions.visibilityOfElementLocated(By.className("dropdown-options")));

// Step 3: Click the matching option by text
List options = driver.findElements(By.cssSelector(".dropdown-options li"));
for (WebElement option : options) {
    if (option.getText().equalsIgnoreCase("California")) {
        option.click();
        break;
    }
}

Other techniques

  • Keyboard navigation — for some widgets, sending arrow keys + Enter via Actions class works when click targeting is unreliable
  • JavaScriptExecutor as a last resort to directly set values, though this bypasses real user interaction and should be used sparingly
  • For autocomplete-style dropdowns, type partial text into the input first to filter the list, then click the filtered result

Q13I have multiple browser windows opened. How will you switch from one window to another?

Selenium identifies each window/tab by a unique window handle (a string ID). To switch, you capture the handles and use driver.switchTo().window(handle).

// Store the original window handle
String parentWindow = driver.getWindowHandle();

// Action that opens a new window/tab (e.g., clicking a link with target="_blank")
driver.findElement(By.id("openNewWindowLink")).click();

// Get all window handles
Set allWindows = driver.getWindowHandles();

// Switch to the new window
for (String handle : allWindows) {
    if (!handle.equals(parentWindow)) {
        driver.switchTo().window(handle);
        break;
    }
}

// Perform actions on new window
System.out.println("New window title: " + driver.getTitle());

// Switch back to original window
driver.switchTo().window(parentWindow);

// To close the child window before switching back
driver.close();
driver.switchTo().window(parentWindow);
Key point to mention: getWindowHandles() returns a Set<String> (unordered), so never assume index-based access; always iterate and compare against the stored parent handle, or use Iterator/convert to a List carefully if you need positional access.

Q15How do you handle alerts and popups in Selenium?

Selenium handles native browser alerts (JavaScript alert(), confirm(), prompt()) using the Alert interface via driver.switchTo().alert().

// Switch to the alert
Alert alert = driver.switchTo().alert();

// Get alert text
String alertText = alert.getText();

// Accept (OK) the alert
alert.accept();

// Dismiss (Cancel) the alert
alert.dismiss();

// For prompt() alerts that need text input
alert.sendKeys("test input");
alert.accept();

Important distinctions

  • Native JS alerts (covered above) — block Selenium until handled; trying to interact with the page before switching to/handling the alert throws UnhandledAlertException
  • Modal popups built with HTML/CSS (Bootstrap modals, custom div overlays) are NOT true browser alerts — treat them as regular web elements (locate the close/OK button and click it normally)
  • Browser-level popups (file upload dialogs, print dialogs) — Selenium cannot interact with these natively since they're OS-level windows; typically handled via Robot class, AutoIT, or by setting the file path directly into a hidden <input type="file"> using sendKeys()
Good practice: always wrap alert handling with an explicit wait — wait.until(ExpectedConditions.alertIsPresent()) — before calling switchTo().alert(), since alerts can take a moment to render after the triggering action.

API Testing

Q17What is an API and how is it different from a Web Service?

API (Application Programming Interface) is a broad contract/set of rules that allows two software components to communicate — it doesn't have to involve a network at all (e.g., a Java library's public methods are an API).

Web Service is a specific type of API that operates over a network, typically using standard web protocols (HTTP/HTTPS).

AspectAPIWeb Service
ScopeBroad — any interface between software componentsNarrower — always network-based
Network requirementNot required (can be in-process, e.g., Java/C++ library API)Always requires a network connection
ProtocolsAny — function calls, HTTP, RPC, etc.Specific protocols — SOAP, REST, XML-RPC
Data formatAny formatTypically XML (SOAP) or JSON (REST)
ExampleJava Collections API, REST Assured library APIA payment gateway's REST endpoint, a SOAP-based banking service
Simple framing for the interview: "All web services are APIs, but not all APIs are web services. A web service strictly needs network communication; an API is the general contract for any inter-component communication."

Q18What is a JWT Token and Bearer Token?

JWT (JSON Web Token)

A JWT is a compact, self-contained, URL-safe token format used for authentication and information exchange. It consists of three Base64-encoded parts separated by dots:

header.payload.signature
  • Header — algorithm used (e.g., HS256, RS256) and token type
  • Payload — claims (user ID, roles, expiry/exp, issued-at/iat, etc.)
  • Signature — verifies the token hasn't been tampered with, using a secret key or public/private key pair

Because the payload is just Base64-encoded (not encrypted), it's readable but not editable without invalidating the signature.

Bearer Token

"Bearer" is an authentication scheme — it describes how a token is sent in the HTTP request, not the token's internal structure. Whoever "bears" (holds/possesses) the token is granted access, hence the name.

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Key relationship to articulate: "A JWT is commonly sent as a Bearer token in the Authorization header. JWT defines the token's format/content; Bearer defines the transport convention. You could technically send a non-JWT opaque token as a Bearer token too — they're related but distinct concepts."

In REST Assured

given()
    .header("Authorization", "Bearer " + accessToken)
    .when()
    .get("/api/accounts")
    .then()
    .statusCode(200);

Q19What validations do you perform while testing APIs?

1. Status Code Validation

response.then().statusCode(200);

Verify correct codes for each scenario: 200 (OK), 201 (Created), 400 (Bad Request), 401 (Unauthorized), 403 (Forbidden), 404 (Not Found), 500 (Server Error).

2. Response Body / Schema Validation

  • Field presence, correct data types, correct values against expected business logic
  • JSON Schema validation for contract adherence
response.then()
    .body("accountId", notNullValue())
    .body("balance", greaterThanOrEqualTo(0))
    .body("status", equalTo("ACTIVE"));

3. Response Headers Validation

response.then().header("Content-Type", containsString("application/json"));

4. Response Time / Performance

response.then().time(lessThan(2000L));

5. Negative / Edge Case Testing

  • Invalid/missing auth tokens, malformed payloads, boundary values, missing mandatory fields
  • SQL injection / special character handling in inputs (security-adjacent validation)

6. Data Integrity / DB Cross-validation

Confirm the API's persisted effect by querying the database directly — especially relevant in BFSI projects where a transaction API call must reflect correctly in ledger/account tables.

7. Authentication & Authorization Validation

  • Valid token → success; expired/invalid token → 401; valid token but insufficient role → 403

8. Idempotency & Concurrency (for relevant endpoints)

For POST/PUT operations like payment initiation, verify repeated identical requests don't create duplicate transactions.

9. Contract Testing

Validate that the API still matches the agreed request/response contract — particularly important when multiple consumers depend on a shared service.

Strong closing line: "I typically structure these validations into a REST Assured framework with POJO-based request/response models, reusable specification builders for headers/auth, and chain DB validation via JDBC where the business outcome needs to be confirmed beyond just the API response."
Java Coding

Q20Write a Java program to remove duplicate characters from a String

Approach 1: Using LinkedHashSet (preserves order, clean)

import java.util.LinkedHashSet;

public class RemoveDuplicates {
    public static String removeDuplicates(String input) {
        LinkedHashSet set = new LinkedHashSet<>();
        for (char c : input.toCharArray()) {
            set.add(c);
        }
        StringBuilder result = new StringBuilder();
        for (char c : set) {
            result.append(c);
        }
        return result.toString();
    }

    public static void main(String[] args) {
        String input = "programming";
        System.out.println("Original: " + input);
        System.out.println("Without duplicates: " + removeDuplicates(input));
        // Output: progamin
    }
}

Approach 2: Without using any built-in Set (manual logic — often asked as a follow-up)

public class RemoveDuplicatesManual {
    public static String removeDuplicates(String input) {
        StringBuilder result = new StringBuilder();
        for (int i = 0; i < input.length(); i++) {
            char current = input.charAt(i);
            if (result.indexOf(String.valueOf(current)) == -1) {
                result.append(current);
            }
        }
        return result.toString();
    }

    public static void main(String[] args) {
        System.out.println(removeDuplicates("automation")); // automin
    }
}
Time complexity: Approach 1 is O(n) using HashSet's O(1) lookups. Approach 2 is O(n²) due to the indexOf scan inside the loop — mention this trade-off if asked about efficiency.

Q21Write a Java program to print a pyramid star pattern

public class PyramidPattern {
    public static void main(String[] args) {
        int rows = 5;

        for (int i = 1; i <= rows; i++) {
            // Print leading spaces
            for (int j = 1; j <= rows - i; j++) {
                System.out.print(" ");
            }
            // Print stars
            for (int k = 1; k <= (2 * i - 1); k++) {
                System.out.print("*");
            }
            System.out.println();
        }
    }
}

/* Output for rows = 5:
    *
   ***
  *****
 *******
*********
*/
Follow-up they may ask: "Print an inverted pyramid" — just reverse the outer loop (for (int i = rows; i >= 1; i--)) while keeping the same inner logic.

Scenario-Based / Production Support

Q23Suppose a release is planned for tomorrow and you still have many tickets in your testing bucket. How will you manage the situation?

This is a prioritization-and-communication question — panels want to see risk-based thinking, not panic or silent overtime.

Step-by-step approach

  1. Immediately communicate the risk to the Scrum Master/PO/lead — don't wait till the last hour. Transparency early gives the team options.
  2. Triage and prioritize by risk & business impact:
    • Critical/high-business-value tickets get tested first
    • Low-risk, cosmetic, or low-usage feature tickets can be deferred
  3. Leverage automation — run the existing automated regression suite in parallel with manual focus testing on new functionality, to cover ground faster.
  4. Divide and conquer — if teammates are free, redistribute tickets based on domain familiarity.
  5. Negotiate scope, not quality — propose deferring specific low-priority tickets to the next release/hotfix rather than rushing through testing and risking a production defect.
  6. Document what was NOT tested — give the release/business team an explicit "known risk" list so the decision to ship is informed, not assumed.
Key phrase to use in the interview: "I'd rather flag a realistic risk early and negotiate scope than silently rush testing and let a defect slip into production — especially in a BFSI context where a missed validation could have financial impact."

Q24What will be your approach if a critical defect is found just before Production deployment?

  1. Stop and assess severity/impact — is it a blocker (data corruption, security, financial miscalculation) or something with a workaround?
  2. Immediately escalate to the release manager, tech lead, and PO — critical defects pre-deployment are a go/no-go decision, not a QA-alone decision.
  3. Provide clear reproduction steps, logs, and impact analysis so the team can make a fast, informed call.
  4. Evaluate options as a team:
    • Hotfix and retest if there's enough time before the deployment window
    • Roll back the specific feature/change causing the defect (feature flag off) while shipping the rest
    • Delay the entire release if the defect is severe enough and no safe workaround exists
  5. Post-decision: If shipped with a known issue, ensure it's documented and monitored closely in production with a fast-follow fix planned.
Emphasize judgment: "I don't unilaterally decide to block or allow a release — my job is to surface the defect with enough clarity and urgency that the right business/technical stakeholders can make that call quickly."

Q25Have you ever faced a Production issue? What was your role in identifying or resolving it?

Answer this with a real (or realistic, structured) example from your background — your Post Production Validation (PPV) experience and Applause Award context are strong material here.

Structure (STAR format)

  • Situation: Briefly describe the production environment and what went wrong (e.g., a data mismatch post-deployment, a Kafka pipeline lag, an API returning incorrect values for a specific edge case)
  • Task: Your specific responsibility — were you doing Post Production Validation sign-off, monitoring, or called in to investigate?
  • Action: How you isolated it — checked logs, compared QA vs Prod data/config, ran targeted API/DB queries, reproduced with prod-like data
  • Result: Outcome — root cause found (config diff, data volume difference, timing/race condition), fix deployed, validation confirmed
Since your background includes formal PPV ownership at GMF/Deloitte, you can speak directly to owning deployment sign-off — describing how you validate key transactions/flows immediately post-deployment before giving the "go" confirmation, which is exactly what this question is probing for.

Q26A bug is reproducible in Production but not in QA. How will you investigate the issue?

This is a classic "environment parity" debugging question. Systematic investigation approach:

1. Compare environment configuration

  • Application config values (feature flags, environment variables, API endpoints)
  • Database schema/version differences, stored procedure versions
  • Third-party service versions or mocked vs real integrations in QA

2. Compare data

  • Production has real-world data volume, edge-case data, and legacy/historical records that QA's synthetic test data often doesn't replicate
  • Check for data-specific triggers — special characters, null/empty fields, very large datasets causing pagination or performance issues

3. Check infrastructure differences

  • Load balancers, caching layers (Redis), CDN behavior present in Prod but not QA
  • Network latency/timeouts that only manifest under production traffic load

4. Review logs and monitoring

  • Production logs (application logs, APM tools like Dynatrace/New Relic, Splunk) for the exact error/stack trace
  • Correlate timestamp of the issue with any deployment, config change, or traffic spike

5. Attempt controlled reproduction

  • Try to replicate using a copy/subset of production-like data in a staging environment
  • Check for concurrency/race conditions that only surface under real multi-user load (hard to simulate in QA with low parallel users)

6. Check recent changes

  • Was there a hotfix, config change, or infra change applied directly to Prod that wasn't reflected in QA?
Strong answer anchor: "Given my experience with mTLS/SSL-based service-to-service communication and Kafka pipeline validation, I'd specifically check certificate/keystore differences and message-queue timing differences between environments — these are common silent causes of 'works in QA, fails in Prod' issues in BFSI systems."

B3What is the Page Object Model and why use it?Bonus

Page Object Model (POM) is a design pattern where each web page (or significant component) is represented as a class, with locators as fields and user actions as methods.

public class LoginPage {
    WebDriver driver;

    @FindBy(id = "username")
    WebElement usernameField;

    @FindBy(id = "password")
    WebElement passwordField;

    @FindBy(id = "loginBtn")
    WebElement loginButton;

    public LoginPage(WebDriver driver) {
        this.driver = driver;
        PageFactory.initElements(driver, this);
    }

    public void login(String user, String pass) {
        usernameField.sendKeys(user);
        passwordField.sendKeys(pass);
        loginButton.click();
    }
}

Benefits

  • Maintainability: Locator changes only need updating in one place
  • Reusability: Page methods reused across multiple test classes
  • Readability: Test scripts read like business actions (loginPage.login(user, pass)) instead of raw Selenium calls
  • Separation of concerns: Test logic stays separate from UI interaction logic

B5What is Shift-Left Testing?Bonus

Shift-Left Testing means moving testing activities earlier in the SDLC — "left" on the timeline — rather than testing only after development is complete.

Practical examples

  • QA participating in requirement/story refinement to catch ambiguous acceptance criteria before development starts
  • Writing BDD/Gherkin scenarios collaboratively (Three Amigos) before coding begins, so acceptance criteria double as test cases
  • Developers running unit + contract tests in CI before merging, catching defects before they reach the QA environment
  • API contract testing early using mocked/stubbed services before the actual backend is ready
Why it matters: defects caught earlier in the SDLC are exponentially cheaper to fix than those caught in QA or, worse, in Production — a well-known principle interviewers expect you to articulate with the cost-of-defect curve reasoning.

B6How do you integrate your automation suite with a CI/CD pipeline (Jenkins/Azure DevOps)?Bonus

  1. Trigger: Pipeline triggers on code merge/PR to main branch, or on a schedule (nightly regression)
  2. Build stage: Maven compiles the project, resolves dependencies
  3. Test execution stage: Maven Surefire/Failsafe plugin runs TestNG suite via testng.xml, often parameterized by environment and test group (smoke/regression)

B8How do you handle test data management for automation, especially in BFSI/regulated environments?Bonus

  • Data masking/anonymization: Production-like data is scrubbed of PII (names, account numbers, SSNs) before use in lower environments — critical for regulatory compliance
  • Synthetic data generation: Tools/scripts to generate realistic but fake data matching production data shapes and edge cases
  • Data-driven frameworks: Externalize test data via Excel (Apache POI), JSON, or a dedicated test DB, with a "RunMode" flag (Y/N) to control which data sets execute
  • Test data refresh strategy: Scripted setup/teardown (via API or direct DB calls) before/after test runs to keep data state predictable and avoid test pollution between runs
  • Idempotent test design: Tests create their own data rather than depending on pre-existing static records that can drift over time

B9What is Flaky Test and how do you deal with it?Bonus

A flaky test is one that produces inconsistent results (pass sometimes, fail other times) without any actual change in the code under test.

Common causes

  • Improper waits (static Thread.sleep() instead of dynamic waits)
  • Test order dependency / shared mutable state between tests
  • Environment instability (network latency, third-party service downtime)
  • Race conditions in async operations (AJAX calls, message queues)

How to deal with it

  • Replace static sleeps with Explicit/Fluent waits tied to actual conditions
  • Make tests independent and idempotent (each test sets up its own data)
  • Implement a controlled retry mechanism (IRetryAnalyzer in TestNG) — but cap retries and report flaky tests separately rather than silently hiding them
  • Quarantine chronically flaky tests into a separate suite for investigation rather than letting them block every pipeline run
  • Track flakiness rate over time as a quality metric, not just pass/fail
