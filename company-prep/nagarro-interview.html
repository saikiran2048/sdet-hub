2.1 Shift all even numbers to the left side of an array, odd numbers to the right side

This is a partitioning problem, same pattern as the "Dutch National Flag" / partition step in quicksort. Use two pointers.

javapublic class EvenOddPartition {
    public static void partition(int[] arr) {
        int left = 0, right = arr.length - 1;
        while (left < right) {
            // move left forward while it's even
            while (left < right && arr[left] % 2 == 0) left++;
            // move right backward while it's odd
            while (left < right && arr[right] % 2 != 0) right--;
            if (left < right) {
                int temp = arr[left];
                arr[left] = arr[right];
                arr[right] = temp;
            }
        }
    }
    public static void main(String[] args) {
        int[] arr = {12, 7, 5, 8, 3, 10, 9, 4};
        partition(arr);
        System.out.println(java.util.Arrays.toString(arr));
    }
}
  • Time complexity: O(n), single pass with two pointers.
  • Space complexity: O(1), in-place swap.
  • Note: this does not preserve original relative order (it's not "stable"). If asked for a stable version, mention you'd need an auxiliary array (O(n) space) — collect evens in order, then odds in order, then merge.
2.2 Can you create an object of an interface / abstract class? Explain.
  • Directly, no — you cannot do new MyInterface() or new MyAbstractClass(). Both are incomplete types; interfaces have no implementation (pre-Java 8) and abstract classes may have unimplemented (abstract) methods, so the JVM can't build a concrete instance.
  • Indirectly, yes, via:
    • Anonymous inner class: MyInterface obj = new MyInterface() { public void method() {...} }; — this actually creates a concrete subclass on the fly and instantiates that.
    • A concrete implementing/extending class: MyInterface obj = new MyImpl(); — reference type is the interface, but the object is of the concrete class.
    • Lambda expressions (for functional interfaces with a single abstract method) — syntactic sugar over an anonymous implementation.
Key line to say: "The interface/abstract class reference variable can point to an object, but the object itself must belong to a concrete class that provides implementations for all abstract methods."
2.3 Why is String immutable in Java?

Give 3–4 reasons, don't just say "security":

  • String pool / interning: literals are cached in the String Constant Pool, so immutability lets multiple references safely share the same object.
  • Security: strings back class names, file paths, network connections, DB URLs, credentials. A mutable string could change after validation but before use (classic TOCTOU issue).
  • Thread safety: immutable objects are inherently thread-safe — no synchronization needed when shared across threads.
  • Hashcode caching: since the value never changes, String caches its hashCode() after first computation, making it efficient as a HashMap/HashSet key.
  • Enforcement: the internal char[]/byte[] (Java 9+ uses compact byte[]) is private final, and the class is final so no subclass can override behavior.
2.4 Purpose of LinkedHashMap in Java? Have you used it in a framework?

LinkedHashMap extends HashMap but maintains a doubly linked list across entries, preserving insertion order (or access order with the accessOrder=true constructor — useful for an LRU cache).

vs HashMap (no order guarantee) and TreeMap (sorted by key, O(log n)) — LinkedHashMap gives predictable iteration at near-HashMap performance.

Framework angle: useful for building ordered JSON request bodies in REST Assured where field order matters for a legacy API, storing Excel/CSV row data in original column order, or an LRU-style cache of WebDriver elements / API responses during a run.
2.5 What is invocationCount used for in TestNG?

A @Test annotation attribute that runs the same test method multiple times.

java@Test(invocationCount = 5)
public void loginTest() { ... }

Common uses: load/stability testing of a single flow (run a flaky-prone login test 10 times to confirm consistency), or repeated runs with randomized data.

Related attributes: threadPoolSize (parallel invocations), invocationTimeOut (max time per invocation), successPercentage (pass overall if this % of invocations succeed — useful for tests with acceptable flakiness thresholds).

2.6 How would you wait for visibility of an element in Selenium?

Explicit wait (preferred, most interview-correct answer):

javaWebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(10));
WebElement element = wait.until(
    ExpectedConditions.visibilityOfElementLocated(By.id("submitBtn")));

visibilityOfElementLocated waits until the element is present and displayed (width/height > 0, not display:none), polling every 500ms by default (FluentWait under the hood).

Other conditions: visibilityOf(WebElement) (already have the reference), elementToBeClickable (visible + enabled), presenceOfElementLocated (in DOM only).

Avoid Thread.sleep(): it's a hard wait — wastes time on fast loads and still fails on slow ones. Mixing implicit + explicit waits is also an anti-pattern (inconsistent wait times) — mentioning this shows framework maturity.
2.7 How would you use AutoIT to upload a file?

Selenium's sendKeys() works for most native <input type="file"> uploads without AutoIT — say this first. AutoIT is a fallback for native OS dialog boxes Selenium can't touch.

Workflow:

  1. Write an AutoIT script (.au3) that identifies the "Choose File" dialog, sets the file path, and clicks "Open": 
    autoitControlFocus("Open", "", "Edit1")
ControlSetText("Open", "", "Edit1", "C:\Users\test\file.pdf")
ControlClick("Open", "", "Button1")
  2. Compile into an .exe via Aut2Exe.
  3. From the Selenium Java test, invoke it: Runtime.getRuntime().exec("path/to/script.exe").
Caveat: AutoIT is Windows-only and not CI/CD-friendly (headless Linux Docker agents can't run it) — mostly legacy/last-resort. Modern frameworks use sendKeys() directly, or Robot class / JavaScriptExecutor tricks.
2.8 What is ElementClickInterceptedException? How to resolve it?

Thrown when Selenium tries to click an element but another element overlaps it at the click coordinates (sticky header, spinner, modal, ad banner).

Resolutions, in order of preference:

  1. Wait for the overlay to disappear (invisibilityOfElementLocated).
  2. Scroll into view: ((JavascriptExecutor) driver).executeScript("arguments[0].scrollIntoView(true);", element);
  3. JS click as fallback: ((JavascriptExecutor) driver).executeScript("arguments[0].click();", element); — bypasses the mouse-event overlay check, use sparingly (can mask real UI bugs).
  4. Use the Actions class to move-then-click.
  5. Dismiss cookie banners / chat widgets / promo pop-ups explicitly at test start.
2.9 What challenges have you faced while working with your framework?

Frame using real DBS/GMF experience — 2–3 concrete challenges, not generic ones:

  • Dynamic/flaky elements in the DBS Playwright-Java framework — attributes changing between dev vs UAT, solved with resilient locators (normalize-space, data-testid) instead of brittle absolute XPaths.
  • Parallel execution + thread safety — shared WebDriver instances caused test pollution when scaling; resolved with ThreadLocal<WebDriver> per thread.
  • Environment-specific data dependencies — GMF's Oracle DB-backed email campaign flows needed careful test data seeding/cleanup to avoid cross-test pollution; talk about idempotent setup/teardown.
  • CI/CD flakiness at scale — Jenkins Remote Build API polling for DB status at DBS; async status updates not ready when checked, solved with backoff polling instead of fixed sleeps.
2.10 What is normalize-space() in XPath? What is its use?

Strips leading/trailing whitespace and collapses internal whitespace/newlines/tabs into a single space.

Syntax: normalize-space(string) — with no argument, applies to the context node's text.

Why it matters: real HTML text often has inconsistent whitespace from source formatting (<span> Submit \n</span>), which breaks exact-match XPath like //span[text()='Submit']. Use //span[normalize-space(text())='Submit'] instead.

Commonly combined with contains(): //button[contains(normalize-space(text()), 'Save')].

3.1 Singleton Design Pattern in Java — advantages?

Ensures a class has exactly one instance and provides a global point of access to it.

javapublic class DriverManager {
    private static volatile DriverManager instance;
    private DriverManager() {}
    public static DriverManager getInstance() {
        if (instance == null) {
            synchronized (DriverManager.class) {
                if (instance == null) {
                    instance = new DriverManager();
                }
            }
        }
        return instance;
    }
}

This is double-checked locking — volatile prevents instruction reordering so another thread never sees a half-constructed object.

  • Controlled single access point (e.g. a shared config/properties reader).
  • Saves memory/resources — avoids repeated expensive object creation.
  • Useful for a shared ExtentReports instance, ConfigReader, or logger.
Caveat (shows depth): Singleton + Selenium WebDriver is an anti-pattern in parallel execution — one global driver breaks test isolation. That's exactly why ThreadLocal<WebDriver> is used instead of a plain singleton for the driver itself.
3.2 How do you disable images in Selenium?

Chrome:

javaMap<String, Object> prefs = new HashMap<>();
prefs.put("profile.managed_default_content_settings.images", 2); // 2 = block
ChromeOptions options = new ChromeOptions();
options.setExperimentalOption("prefs", prefs);
WebDriver driver = new ChromeDriver(options);

Firefox:

javaFirefoxProfile profile = new FirefoxProfile();
profile.setPreference("permissions.default.image", 2);
FirefoxOptions options = new FirefoxOptions();
options.setProfile(profile);
WebDriver driver = new FirefoxDriver(options);

Purpose: speeds up page load in CI pipelines since images aren't rendered — useful when tests don't need to visually verify images.

3.3 Difference between Action vs Actions in Selenium

Actions (plural) is the builder class used directly in test code — chain low-level interactions then .build() and .perform().

javaActions actions = new Actions(driver);
actions.moveToElement(element).click().build().perform();

Action (singular) is the interface/type returned by .build() — the composed, ready-to-execute sequence. You rarely touch it directly.

Interview phrasing: "Actions is the builder I use to chain gestures; Action is the resulting object that represents that chained sequence, executed via .perform()."
3.4 How do you deal with elements that change attributes dynamically at runtime?

Avoid brittle absolute/attribute-dependent locators. Strategies, roughly in order of robustness:

  1. Relative/contains-based XPath on structurally stable attributes: //div[contains(@id,'row_')].
  2. Prefer stable attributes like data-testid, name, or aria-label — push for these in code review if missing.
  3. XPath axes (parent/sibling/ancestor) to locate relative to a stable nearby anchor.
  4. normalize-space() + contains() for whitespace-tolerant text matches.
  5. For randomly-suffixed IDs, use CSS attribute selectors ([id^='btn_'], [id*='dynamic']).
  6. Last resort: coordinate with dev team to add automation-friendly hooks — resilient locators are a collaboration problem as much as a technical one.
3.5 Purpose of using ThreadLocal class in Selenium

Gives each thread its own isolated copy of the WebDriver instance when running tests in parallel (TestNG parallel="methods"/"classes").

Without it, a shared WebDriver gets corrupted across threads — one thread navigates away while another is mid-assertion, causing StaleElementReferenceException or wrong-page failures.

javapublic class DriverManager {
    private static ThreadLocal<WebDriver> driver = new ThreadLocal<>();
    public static WebDriver getDriver() { return driver.get(); }
    public static void setDriver(WebDriver d) { driver.set(d); }
    public static void unload() { driver.remove(); }
}
Always call .remove() after teardown — CI thread pools reuse threads across runs, and stale ThreadLocal references leak memory.

3.7 How do you write a test case in Postman to validate the status code?

In the Tests tab (JavaScript, using the pm API):

javascriptpm.test("Status code is 200", function () {
    pm.response.to.have.status(200);
});

// Alternative / more flexible:
pm.test("Status code is 200", function () {
    pm.expect(pm.response.code).to.eql(200);
});

// Validate against a list of acceptable codes:
pm.test("Status code is either 200 or 201", function () {
    pm.expect(pm.response.code).to.be.oneOf([200, 201]);
});

These run automatically after the request executes; results appear in Test Results, and the same scripts run via Collection Runner, Newman (CLI), or in a CI pipeline.

3.8 How would you perform data-driven testing in Postman?

Collection Runner + external data file (CSV/JSON):

  1. Parameterize request body/URL with variables: {{username}}, {{password}}.
  2. Prepare a CSV/JSON file with columns/keys matching variable names, one row per iteration.
  3. Open Collection Runner, select the collection, upload the data file — Postman runs it once per row.

Via Newman (CI-friendly):

bashnewman run collection.json -d data.csv -e environment.json --reporters cli,html

3.9 Difference between HEAD and OPTIONS API methods

HEAD: identical to GET but returns only headers, no body. Used to check resource existence, metadata (Content-Length, Last-Modified), or cache validity without downloading the payload.

OPTIONS: discovers what HTTP methods a resource supports. Server responds with an Allow header (e.g. Allow: GET, POST, PUT). Central to browser CORS preflight requests before cross-origin POST/PUT with custom headers.

One-liner: "HEAD tells you about a specific resource (metadata, no body); OPTIONS tells you what you're allowed to do with it (supported methods), and it's the backbone of CORS preflight checks."
3.10 JMeter basics — Thread Group, Listeners

Thread Group: the starting point of any test plan — defines the virtual users simulating concurrent load.

  • Number of Threads (users): concurrent virtual users to simulate.
  • Ramp-up period: time over which JMeter starts all threads (e.g., 100 threads / 50s ramp-up = 2 threads/sec, avoiding an unrealistic instant spike).
  • Loop Count: repetitions per thread, or "Infinite" for duration-based tests.
  • Also worth naming: Stepping Thread Group (gradual staged increase) and Ultimate Thread Group (custom load patterns via plugins).

Listeners collect and display run results: View Results Tree (per-request detail, memory-heavy — debugging only), Summary Report (avg/min/max, throughput, error %), Aggregate Report, Response Time Graph.

Practical tip: disable heavy listeners like View Results Tree during real load runs — they skew results at higher thread counts.
Bridge: tie this to your DBS 300 TPS JMeter sign-off — JVM heap tuning, and switching log level from DEBUG to ERROR as concrete tuning steps you personally owned.

B.1 What is the difference between TestNG and JUnit 5?
  • Parallel execution: TestNG has native, fine-grained parallel support (methods/classes/suites via testng.xml); JUnit 5 needs the junit-platform-properties parallel config and is comparatively newer at it.
  • Test dependencies: TestNG supports dependsOnMethods/dependsOnGroups natively; JUnit 5 has no built-in equivalent (by design — tests should be independent).
  • Grouping: TestNG groups (@Test(groups="smoke")) vs JUnit 5 tags (@Tag("smoke")) — functionally similar.
  • Data-driven testing: TestNG @DataProvider vs JUnit 5 @ParameterizedTest + @MethodSource/@CsvSource — JUnit 5's syntax is more declarative.
  • Ecosystem fit: TestNG is still dominant in enterprise Selenium/Java automation (your DBS/GMF stack); JUnit 5 is the default for Spring Boot unit/integration tests and increasingly common with Playwright-Java.
B.2 Explain the Karate DSL — how does it differ from REST Assured?

Karate is a BDD-style, Gherkin-based API testing framework where the test itself is written in a domain-specific language (.feature files) rather than plain Java code — no step-definition glue code is required, unlike Cucumber+Java.

gherkinScenario: Get user details
  Given url baseUrl + '/users/1'
  When method GET
  Then status 200
  And match response.name == 'John'
  • Built-in assertions and JSON/XML matching — no need for separate assertion libraries.
  • Native parallel execution via JUnit runners without extra config.
  • Can call Java code directly when logic gets complex, and supports UI automation too (Karate now wraps Playwright under the hood).
  • REST Assured, by contrast, is a pure Java library — more code, more flexibility for complex logic/assertions, and integrates naturally into an existing Java/TestNG codebase without introducing a DSL.
Interview angle: Karate lowers the barrier for non-Java testers to write API tests, while REST Assured suits teams that want full Java control and reuse of existing utility classes.
B.3 How do you validate a Kafka message in an automated test?

Typical pattern with a Kafka consumer in the test framework (or Karate's Kafka plugin):

  1. Spin up a test consumer subscribed to the target topic, with a unique group.id per test run to avoid offset collisions.
  2. Trigger the producing action (API call, UI action, or upstream event).
  3. Poll the topic with a bounded timeout (e.g., consumer.poll(Duration.ofSeconds(5))) rather than blocking indefinitely.
  4. Deserialize the message (JSON/Avro) and assert on key fields — schema, correlation ID, business payload values.
  5. Clean up: close the consumer, and if using a shared topic, filter by a correlation ID unique to the test to avoid picking up another test's message.
Common pitfall: polling with no timeout, or reusing consumer groups across parallel tests — causes flaky "message not found" failures. Always scope a unique group/correlation ID per test.
B.4 What is a Cucumber Background block used for?

Background defines steps that run before every scenario in a feature file — common setup (login, navigating to a page, seeding shared test data) that would otherwise be duplicated in every Scenario.

gherkinFeature: Loan application

  Background:
    Given the user is logged in as "testuser"
    And the dashboard is loaded

  Scenario: Submit a new loan application
    When the user submits a loan request
    Then the application status is "Pending"
Caveat: overusing Background for unrelated setup makes scenarios harder to read in isolation — keep it to truly shared preconditions, not a dumping ground for every step.
B.5 Explain optimistic vs pessimistic locking — how does this affect test data isolation?
  • Pessimistic locking: acquires a lock on a row/record before reading it (SELECT ... FOR UPDATE), blocking other transactions until release. Safer under high contention, but reduces concurrency and can cause deadlocks.
  • Optimistic locking: no lock is taken upfront; instead a version column (or timestamp) is checked at write time, and the write fails/retries if the version changed since read. Higher throughput, but requires retry logic.
SDET angle: in parallel test execution against a shared DB, optimistic locking failures show up as intermittent "stale data" test failures — a strong sign you need per-test data isolation (unique test records, transactional rollback per test, or a dedicated schema per parallel worker) rather than shared fixtures.
B.6 What is StaleElementReferenceException and how do you handle it?

Thrown when the previously located WebElement is no longer attached to the DOM — the page was reloaded, the element was re-rendered by JS (React/Angular re-render), or navigation occurred after the element was found.

  • Re-locate the element right before interacting with it rather than caching a reference across steps.
  • Wrap the interaction in a small retry loop that catches the exception and re-finds the element (common in a custom wait utility).
  • Use explicit waits with a condition that re-fetches the element, like ExpectedConditions.refreshed(ExpectedConditions.visibilityOfElementLocated(locator)).
  • Avoid storing WebElement references as class fields across test steps in frameworks with heavy client-side re-rendering — store the By locator instead and resolve it fresh each time.
B.7 Difference between @BeforeMethod, @BeforeClass, and @BeforeSuite in TestNG
AnnotationRunsTypical use
@BeforeMethodBefore every @Test methodFresh browser/driver instance, reset UI state per test
@BeforeClassOnce, before the first method in the classExpensive setup shared across a test class (e.g., login once, reuse session)
@BeforeSuiteOnce, before the entire suite (across all classes)Global setup — start Selenium Grid, load environment config, spin up test data seeds
Interview point: misusing @BeforeMethod for expensive setup (like spinning up a WebDriver Grid session) tanks execution time at scale — matching the right scope to the right lifecycle is a design decision, not just syntax.
B.8 What is a JWT, and how do you validate it in API tests?

A JSON Web Token is a compact, self-contained token — header.payload.signature, Base64URL-encoded — used for stateless authentication/authorization.

  • Structural validation: assert the token has 3 dot-separated segments and decodes to valid JSON.
  • Claims validation: decode the payload and assert on exp (not expired), iss (expected issuer), sub/custom claims matching the test user.
  • Signature validation: re-verify the signature using the known public key/secret (for HS256/RS256) to confirm the token wasn't tampered with — important for security-focused API tests.
  • Negative tests: expired token → 401; tampered payload → 401; missing token on a protected endpoint → 401/403.
Tooling: in Java, io.jsonwebtoken:jjwt or Auth0's java-jwt library decode/verify tokens directly inside REST Assured or Karate assertions.
B.9 Explain the difference between a Mock, a Stub, and a Spy
  • Stub: a fake object that returns pre-programmed responses — used to isolate the system under test from a dependency, with no assertions on how it was called.
  • Mock: a fake object that additionally verifies interactions — you assert it was called with specific arguments, a specific number of times (verify(mock).methodX(arg) in Mockito).
  • Spy: wraps a real object, delegating calls to it by default, but lets you selectively override or verify specific method calls — useful when you want real behavior mostly intact but need to intercept one method.
SDET framing: stubs answer "does my code handle this response correctly"; mocks answer "did my code call the dependency correctly"; spies answer "did this real object behave as expected while I tweak one part of it."
B.10 How do you handle flaky tests in a CI/CD pipeline?
  1. Quarantine, don't ignore: tag known-flaky tests (e.g., @Flaky) and run them in a separate non-blocking CI stage so they don't block deployments while still surfacing failures for investigation.
  2. Root-cause classify: timing/sync issues (fix with proper waits, not retries), test data collisions (fix with isolation), environment instability (fix at infra level), genuine app bugs (file a defect — don't just "fix" the test).
  3. Controlled retry: a bounded retry (e.g., TestNG IRetryAnalyzer, max 1–2 retries) as a safety net for genuinely environment-flaky tests — but track retry counts as a metric, not silently.
  4. Track flakiness as a metric over time (pass rate per test in Allure/reporting) so quarantined tests get real attention instead of living there forever.
Anti-pattern to call out: blanket retry-on-failure for the whole suite hides real regressions and erodes trust in the pipeline — this is a strong thing to say explicitly in an interview.
B.11 Difference between soft assert and hard assert
  • Hard assert (Assert.assertEquals in TestNG/JUnit): fails and immediately stops the test method on the first failed assertion — subsequent assertions in that method never run.
  • Soft assert (TestNG's SoftAssert): records failures but continues executing the rest of the test method; you must call assertAll() at the end to actually fail the test and report all accumulated failures together.
javaSoftAssert softAssert = new SoftAssert();
softAssert.assertEquals(actualTitle, expectedTitle);
softAssert.assertEquals(actualPrice, expectedPrice);
softAssert.assertAll(); // reports all failures at once
When to use which: soft asserts are useful for validating multiple independent fields on one page (form validation, dashboard checks) so you see all mismatches in one run instead of fixing them one at a time; hard asserts suit sequential flows where a later step is meaningless if an earlier one failed (e.g., can't verify order confirmation if login itself failed).
B.12 Page Object Model vs Page Factory — what's the actual difference?
  • Page Object Model (POM) is the design pattern itself: one class per page, encapsulating locators and actions, hiding implementation detail from test methods.
  • PageFactory is a Selenium utility class that implements POM using annotations (@FindBy) and lazy initialization via PageFactory.initElements(driver, this) — it's one way to build a POM, not a separate pattern.
javapublic class LoginPage {
    @FindBy(id = "username") WebElement usernameField;
    public LoginPage(WebDriver driver) {
        PageFactory.initElements(driver, this);
    }
}
Modern nuance: PageFactory's lazy proxy elements are a common source of StaleElementReferenceException in SPA-heavy apps with frequent re-renders — many modern frameworks (including your Playwright-based EventHub project) skip PageFactory and use plain locator methods or component objects instead, re-resolving elements fresh each call.
B.13 What is CORS, and how would you test it?

Cross-Origin Resource Sharing is a browser security mechanism that restricts web pages from making requests to a different origin (scheme + host + port) than the one that served the page, unless the server explicitly allows it via response headers (Access-Control-Allow-Origin, etc.).

  • API-level testing: send a request with an Origin header and assert the correct Access-Control-Allow-Origin value comes back (exact match, wildcard, or absence for disallowed origins).
  • Preflight testing: for non-simple requests (custom headers, PUT/DELETE), send an OPTIONS request and verify Access-Control-Allow-Methods/-Headers reflect what's actually permitted.
  • Negative case: request from a disallowed origin should either omit the CORS header (browser blocks it client-side) or be explicitly rejected server-side, depending on the implementation.
Note: CORS is enforced by the browser, not the server — a tool like Postman/REST Assured will still get the response body even without proper CORS headers, so CORS bugs often only surface in real browser/UI testing, not pure API testing.
B.14 Explain database indexing and how EXPLAIN helps in test/data validation

An index is a separate data structure (typically a B-tree) that lets the database locate rows without scanning the entire table — trades write speed and storage for read speed.

  • Without an index: a query does a full table scan — O(n), slow on large tables.
  • With an index on the queried column, lookup is closer to O(log n).
  • EXPLAIN (MySQL) / EXPLAIN ANALYZE (PostgreSQL) shows the query execution plan — whether it's using an index (type: ref/range in MySQL) or falling back to a full scan (type: ALL), estimated rows scanned, and join order.
SDET angle: when a data validation query in a test suite runs slow and starts causing timeouts under CI, running EXPLAIN on it is the first diagnostic step — often reveals a missing index on a column the test framework filters/joins on frequently (e.g., a correlation ID or test-run tag column).
B.15 What is idempotency in REST APIs, and why does it matter for testing?

An operation is idempotent if making the same request multiple times produces the same result/state as making it once (though the response itself may differ, e.g. a repeated timestamp).

  • Idempotent by spec: GET, PUT, DELETE, HEAD, OPTIONS.
  • Not idempotent: POST (typically creates a new resource each call) and PATCH (depends on implementation).
Testing implication: a critical test case for payment/loan-disbursement style APIs (relevant to your banking domain) is verifying that retrying a POST after a network timeout doesn't create a duplicate transaction — this is where idempotency keys come in: the client sends a unique key per logical operation, and the server deduplicates retries with the same key. Testing this means firing the same request twice with the same idempotency key and asserting only one resource/side-effect was created.
B.16 What is shift-left testing, and how have you applied it?

Shift-left means moving testing activities earlier in the SDLC — testing requirements, designs, and code as they're written rather than waiting for a dedicated QA phase after development.

  • Requirements phase: reviewing Gherkin/BDD scenarios with BAs/devs before coding starts, catching ambiguous acceptance criteria early.
  • Dev phase: API contract tests and unit tests run in the same PR pipeline as the code change, not a separate downstream QA cycle.
  • CI integration: smoke/regression suites triggered on every PR (not just nightly), so failures surface within minutes of a code change.
Bridge: your GitHub Actions pipelines with sharded execution and PR-triggered runs are a concrete shift-left example worth citing directly.
B.17 What is contract testing, and how does it differ from end-to-end testing?

Contract testing (e.g., Pact) verifies that a consumer and provider of an API agree on the shape of requests/responses — without spinning up the full integrated system. The consumer defines expectations ("contract"), and the provider is verified against that contract independently.

  • Faster and more stable than full E2E — no need to deploy every dependent service to run the test.
  • Catches breaking changes early — if a provider changes a response field, the contract verification fails in the provider's own CI, before it ever reaches a shared environment.
  • E2E testing, by contrast, exercises the real integrated system end-to-end and catches issues contract tests can't (like actual business logic across services), but is slower, flakier, and more expensive to maintain.
Interview framing: "Contract tests answer 'will this API change break my consumer,' fast and in isolation. E2E tests answer 'does the whole system actually work together,' slower but with full realism. Mature test strategies use both — a testing pyramid with contract tests near the base."
B.18 Horizontal vs vertical scaling — how does this apply to a Selenium Grid?
  • Vertical scaling: adding more resources (CPU/RAM) to a single node, or raising SE_NODE_MAX_SESSIONS to cram more browser sessions onto one Grid node.
  • Horizontal scaling: adding more nodes (machines/containers) to the Grid so sessions distribute across independent hosts.
Why horizontal is the stronger interview answer: raising max sessions per node beyond a small number causes resource contention — CPU/memory pressure across concurrently running browsers on the same host leads to slow, flaky tests even though "more sessions" are technically available. Adding a second node instead keeps each session's resource footprint isolated, which is more predictable at scale and matches how you scaled the Docker-based Selenium Grid on Oracle Cloud.
B.19 Playwright's auto-waiting vs Selenium's explicit waits — what's actually different?
  • Selenium: waits are opt-in and explicit — you choose a condition (visibilityOfElementLocated, elementToBeClickable) and wrap it around each interaction; nothing waits automatically.
  • Playwright: actionability checks are built into every action by default — before clicking, Playwright automatically waits for the element to be attached, visible, stable (not animating), enabled, and receiving pointer events, with no explicit wait code needed for the common case.
Trade-off to mention: Playwright's auto-waiting reduces boilerplate and a whole class of flaky "not clickable" failures, but it can mask a genuinely slow-loading app if you don't also assert on business-meaningful conditions (like data actually loading) — auto-wait only guarantees the element is interactable, not that the underlying data is correct or complete.
B.20 What is a race condition, and how would you design a test to catch one?

A race condition occurs when the correctness of a system depends on the relative timing of concurrent operations — two threads/processes/requests access or modify shared state in an order that isn't guaranteed, producing inconsistent results.

  • Concurrency testing approach: fire multiple identical requests simultaneously (e.g., two "redeem coupon" calls for a single-use coupon at the same instant) using parallel threads or an async HTTP client, then assert only one succeeded and the other correctly failed/rejected.
  • Database-level check: verify no duplicate/inconsistent row was created — e.g., a balance wasn't debited twice for one logical transaction.
  • Tooling: JMeter with synchronized timers (forces all threads to fire at once) is a practical way to simulate this at load, or a small custom test harness using CompletableFuture.allOf() in Java to fire concurrent calls precisely.
Why this matters for banking/FinTech: race conditions in payment/loan-disbursement flows are exactly the class of bug that causes double-charges — worth explicitly connecting this to your GM Financial / DBS domain experience if asked for a real example.
