TC-01 How would you design a scalable Selenium automation framework using Java and TestNG? Framework Design ›

A scalable framework needs to survive growth in test count, team size, and application complexity without becoming unmaintainable. Key design pillars:

Layered Architecture

src/main/java
 ├── config/          → environment configs, property loaders
 ├── driver/          → DriverFactory (thread-safe WebDriver management)
 ├── pages/            → Page Object classes
 ├── components/       → reusable UI components (e.g., header, modal)
 ├── utils/             → waits, screenshot, file readers, extent report utils
 ├── listeners/          → TestNG listeners (ITestListener, IRetryAnalyzer)
 └── api/                 → Rest Assured clients, DTOs

src/test/java
 ├── tests/               → actual TestNG test classes
 ├── dataproviders/        → @DataProvider classes
 └── testng.xml

Core design decisions: - ThreadLocal for driver instance management to support parallel execution safely. - Factory pattern for driver creation (DriverFactory.getDriver(String browser)), abstracting ChromeDriver, FirefoxDriver, RemoteWebDriver behind one interface. - Builder pattern for test data objects to avoid constructor telescoping. - Singleton config manager backed by .properties or YAML files, loaded once per JVM/thread. - POM + Component Object Model — for pages with repeated widgets (headers, footers, modals), extract components separately so page classes don't duplicate locators. - Fluent Interface on Page Objects returning this or the next page object, improving readability of test flows. - Externalized configuration — never hardcode URLs, credentials, timeouts; use environment-specific .properties files (qa.properties, uat.properties, staging.properties) selected via a Maven/System property. - Reporting abstraction — a wrapper around ExtentReports so test classes never call Extent APIs directly (keeps reporting swappable). - Listener-driven cross-cutting concerns — screenshot capture, retry logic, and logging handled via TestNG listeners rather than scattered in test methods. - CI/CD-first mindset — framework should run identically via mvn test, Jenkins, or GitHub Actions, driven entirely by parameters/environment variables (no local-machine dependencies like absolute paths).

Scalability checklist to mention in interview: - Modular Maven multi-module setup if the suite grows very large (separate modules for UI, API, common-utils). - Version-controlled test data (avoid environment-specific hardcoded data in test methods). - Tagging/grouping tests (@Test(groups = {"smoke","regression"})) so CI can run subsets. - Centralized exception handling and custom exceptions for clearer failure diagnosis.

TC-02 Explain the Page Object Model (POM) Framework Design ›

POM is a design pattern that creates an object repository for web UI elements, separating test logic from page structure/locators.

Structure:

public class LoginPage {
    private WebDriver driver;

    private By usernameField = By.id("username");
    private By passwordField = By.id("password");
    private By loginBtn = By.id("loginBtn");

    public LoginPage(WebDriver driver) {
        this.driver = driver;
    }

    public HomePage login(String user, String pass) {
        driver.findElement(usernameField).sendKeys(user);
        driver.findElement(passwordField).sendKeys(pass);
        driver.findElement(loginBtn).click();
        return new HomePage(driver);
    }
}

Benefits: - Maintainability — if a locator changes, you fix it in one place, not across dozens of test methods. - Reusability — page actions (login(), searchProduct()) can be reused across multiple test cases. - Readability — test methods read like business flows, not raw Selenium calls. - Separation of concerns — testers write assertions/flows; locators are isolated from test logic.

PageFactory variant:

public class LoginPage {
    @FindBy(id = "username") WebElement username;
    @FindBy(id = "password") WebElement password;
    @FindBy(id = "loginBtn") WebElement loginBtn;

    public LoginPage(WebDriver driver) {
        PageFactory.initElements(driver, this);
    }
}

PageFactory.initElements uses lazy proxy initialization — elements aren't located until interacted with, so @FindBy doesn't throw NoSuchElementException at object creation.

Edge case / gotcha to mention: PageFactory-annotated elements are cached by default (in older Selenium) which can cause StaleElementReferenceException on SPA pages with frequent DOM re-renders. Mitigation: use @CacheLookup carefully (only on static elements) or avoid it entirely on dynamic pages, and re-locate elements per interaction.

Best practice extension: combine POM with the Fluent Page Object style, and add a BasePage class holding common wait/utility methods so every page object inherits explicit-wait helpers instead of duplicating them.

TC-03 How do you manage test execution across different browsers and environments (QA, UAT, Staging)? Selenium Core ›

Cross-browser management:

public class DriverFactory {
    private static ThreadLocal<WebDriver> driver = new ThreadLocal<>();

    public static WebDriver getDriver() {
        return driver.get();
    }

    public static void initDriver(String browser) {
        WebDriver webDriver;
        switch (browser.toLowerCase()) {
            case "chrome":
                webDriver = new ChromeDriver(getChromeOptions());
                break;
            case "firefox":
                webDriver = new FirefoxDriver();
                break;
            case "edge":
                webDriver = new EdgeDriver();
                break;
            default:
                throw new IllegalArgumentException("Unsupported browser: " + browser);
        }
        driver.set(webDriver);
    }
}

Browser is passed as a Maven system property or TestNG parameter: mvn test -Dbrowser=chrome.

For Selenium Grid / cloud grids (BrowserStack, LambdaTest, Sauce Labs), use RemoteWebDriver with DesiredCapabilities/MutableCapabilities, so the same test suite runs on multiple OS/browser combinations without code change — only capability JSON differs.

Environment management: - Maintain config/qa.properties, config/uat.properties, config/staging.properties, each with base.url, db.connection, api.baseuri, etc. - A ConfigReader utility loads the right file based on a system property:

String env = System.getProperty("env", "qa");
Properties props = new Properties();
props.load(new FileInputStream("src/test/resources/config/" + env + ".properties"));
  • Run via: mvn test -Denv=uat -Dbrowser=firefox
  • In Jenkins/GitHub Actions, env and browser become pipeline parameters, so the same job definition can trigger runs against any environment without code changes.
  • Sensitive data (passwords, tokens) — never in properties files committed to git; pull from Jenkins credentials store or environment variables at runtime.

Edge case to mention: environment-specific test data (e.g., a customer ID that exists only in QA) should be abstracted through a TestDataProvider keyed by environment, not hardcoded in test methods, so the same test class works across environments.

TC-04 How do you run parallel tests in TestNG and avoid thread-safety issues? CI/CD & Parallel ›

Enabling parallelism via testng.xml:

<suite name="RegressionSuite" parallel="methods" thread-count="5">
  <test name="ChromeTests">
    <classes>
      <class name="tests.LoginTest"/>
      <class name="tests.CheckoutTest"/>
    </classes>
  </test>
</suite>

parallel can be methods, classes, tests, or instances depending on granularity needed. thread-count controls the thread pool size.

Thread-safety strategies: 1. ThreadLocal WebDriver — the single most important fix. Each thread gets its own driver instance; never use a static shared WebDriver field.

private static ThreadLocal<WebDriver> tlDriver = new ThreadLocal<>();
  1. Avoid static mutable state in Page Objects and utility classes — static counters, shared Maps used for test data, etc. cause race conditions.
  2. Thread-safe reporting — ExtentReports requires ExtentTest objects to also be stored in a ThreadLocal<ExtentTest> because multiple threads write to the report concurrently.
  3. Independent test data — each parallel test should generate/use its own data set (e.g., unique email via UUID or timestamp) to avoid data collisions in shared environments (DB constraint violations, duplicate records).
  4. Synchronized blocks only where unavoidable — e.g., writing to a shared log file — but keep critical sections minimal since they reduce parallel throughput.
  5. @BeforeMethod/@AfterMethod, not @BeforeClass, for driver init when running parallel="methods", since @BeforeClass runs once per class and won't isolate driver state at the method level if the class itself has multiple parallel method executions sharing fields.

Common flaky-parallel symptom to mention: if you see intermittent NoSuchSessionException or one test's actions bleeding into another's browser, it's almost always a non-ThreadLocal static driver reference — a classic interview trap question.

TC-05 How do you handle dynamic elements with changing IDs? Selenium Core ›

Dynamic IDs (e.g., id="btn_38271" that changes per session/build) break By.id() locators. Strategies, roughly in order of preference:

  1. Stable attributes — prefer name, data-testid, aria-label, or custom data-qa attributes if the dev team adds them (best long-term fix — advocate for this with developers).
  2. CSS Selector with partial/attribute match:
driver.findElement(By.cssSelector("[id^='btn_']"));   // starts-with
driver.findElement(By.cssSelector("[id*='submit']"));  // contains
  1. XPath with contains() / starts-with():
driver.findElement(By.xpath("//button[contains(@id,'submit')]"));
driver.findElement(By.xpath("//div[starts-with(@id,'row_')]//span[text()='Approve']"));
  1. Relative XPath from a stable ancestor/sibling when the dynamic element itself has nothing stable, but a nearby label does:
driver.findElement(By.xpath("//label[text()='Account Number']/following-sibling::input"));
  1. Text-based locators for elements with stable visible text:
By.xpath("//button[normalize-space(text())='Submit']");
  1. Custom wait + retry wrapper — if the ID changes on every page reload but follows a pattern, an explicit wait with a regex-tolerant locator handles it; if it changes within a single page session (React re-render), pair this with explicit waits for staleness before re-locating.

Edge case: if IDs are auto-generated GUIDs with zero pattern and no other stable attribute exists, the pragmatic answer is to escalate to developers to add data-testid — this is a legitimate interview answer that shows collaboration maturity, not just a technical workaround.

TC-06 Can you automate file upload/download in Selenium? What approach or tools do you use? Selenium Core ›

File Upload: - If the upload control is a plain <input type="file">, Selenium can interact with it directly (no native OS dialog appears because sendKeys sets the file path programmatically):

driver.findElement(By.id("fileUpload")).sendKeys("C:\\testdata\\sample.pdf");
  • If the upload triggers a native OS file dialog (rare with modern web apps but possible with older Flash/Java applets or certain custom widgets), Selenium cannot interact with OS-level dialogs. Options:
  • Robot class (Java AWT) to simulate keyboard/mouse at OS level — fragile, avoid if possible.
  • AutoIT scripts (Windows only) triggered via Runtime.exec().
  • Preferably, ask devs to expose a standard <input type="file"> for testability.

File Download: - Configure browser preferences to auto-download without a save dialog:

ChromeOptions options = new ChromeOptions();
Map<String, Object> prefs = new HashMap<>();
prefs.put("download.default_directory", "C:\\downloads");
prefs.put("download.prompt_for_download", false);
options.setExperimentalOption("prefs", prefs);
  • Verify download success by polling the download directory for the expected file (with a timeout loop) rather than a fixed Thread.sleep():
File dir = new File(downloadPath);
Awaitility.await().atMost(30, TimeUnit.SECONDS)
    .until(() -> dir.listFiles((d, name) -> name.endsWith(".pdf")).length > 0);
  • For content validation post-download: use Apache POI (Excel), PDFBox (PDF text extraction), or OpenCSV to assert file contents programmatically instead of just checking existence.

Edge case to mention: in headless CI environments, download behavior can differ (headless Chrome historically blocked downloads by default) — solved via Chrome DevTools Protocol (Page.setDownloadBehavior) command execution.

TC-07 How do you handle alerts, popups, and iframes? Selenium Core ›

JavaScript Alerts:

Alert alert = driver.switchTo().alert();
alert.accept();          // OK
alert.dismiss();         // Cancel
String text = alert.getText();
alert.sendKeys("input"); // for prompt() dialogs

Always wrap alert-switching in an explicit wait (ExpectedConditions.alertIsPresent()) since alerts can appear asynchronously.

Window/Browser popups (new tab/window):

String parentWindow = driver.getWindowHandle();
Set<String> allWindows = driver.getWindowHandles();
for (String handle : allWindows) {
    if (!handle.equals(parentWindow)) {
        driver.switchTo().window(handle);
        // interact with popup
        driver.close();
    }
}
driver.switchTo().window(parentWindow);

iFrames:

driver.switchTo().frame("frameId");      // by id/name
driver.switchTo().frame(2);               // by index
driver.switchTo().frame(driver.findElement(By.cssSelector("iframe.payment")));  // by WebElement
// ... interact ...
driver.switchTo().defaultContent();       // back to main page

Nested iframes: must switch into each level sequentially — defaultContent() then re-descend; Selenium has no "switch to parent frame directly by name" shortcut across multiple nesting levels except switchTo().parentFrame() which steps up exactly one level.

Edge case for BFSI apps (relevant to your domain): payment gateway integrations are frequently embedded in iframes from third-party PSPs. A common flaky-test cause is trying to locate elements inside the iframe before switching context — always assert driver.switchTo().frame(...) succeeded (wrap with ExpectedConditions.frameToBeAvailableAndSwitchToIt()) before interacting.

TC-08 How do you capture screenshots on test failures and attach them to Extent Reports? Reporting & Debug ›

TestNG Listener approach (preferred over doing it inline in every test):

public class TestListener implements ITestListener {

    @Override
    public void onTestFailure(ITestResult result) {
        WebDriver driver = DriverFactory.getDriver();
        String screenshotPath = captureScreenshot(driver, result.getMethod().getMethodName());
        ExtentReportManager.getTest().fail(result.getThrowable())
            .addScreenCaptureFromPath(screenshotPath);
    }

    private String captureScreenshot(WebDriver driver, String testName) {
        TakesScreenshot ts = (TakesScreenshot) driver;
        File source = ts.getScreenshotAs(OutputType.FILE);
        String path = "screenshots/" + testName + "_" + System.currentTimeMillis() + ".png";
        try {
            FileUtils.copyFile(source, new File(path));
        } catch (IOException e) {
            throw new RuntimeException("Screenshot capture failed", e);
        }
        return path;
    }
}

Register the listener either via @Listeners(TestListener.class) on the test class or in testng.xml:

<listeners>
    <listener class-name="listeners.TestListener"/>
</listeners>

Extent Report integration: - Maintain ThreadLocal<ExtentTest> so parallel execution logs to the correct report node per thread. - Attach screenshot as base64 (not just file path) if the report needs to be portable/self-contained for emailing:

String base64Screenshot = ts.getScreenshotAs(OutputType.BASE64);
test.fail("Test Failed").addScreenCaptureFromBase64String(base64Screenshot);

Best practice: capture screenshots not only on failure but optionally on key checkpoints for audit trails — common ask in BFSI projects for compliance evidence.

TC-09 How do you debug flaky or intermittent test failures? Reporting & Debug ›

Structured approach (this is a strong interview differentiator — show a process, not guesses):

  1. Reproduce and isolate — run the failing test alone, multiple times, in both headless and headed mode, to rule out environment/parallel-execution interference.
  2. Check for synchronization issues first — the majority of flakiness is Thread.sleep() misuse, missing explicit waits, or race conditions between AJAX calls and assertions. Replace static sleeps with WebDriverWait + ExpectedConditions.
  3. Review StaleElementReferenceException patterns — usually caused by DOM re-render after an action; fix by re-locating the element rather than caching a reference across page state changes.
  4. Check test independence — flaky tests are often not isolated: shared test data, leftover state from a previous test, or execution-order dependency. Ensure @BeforeMethod resets state and tests don't rely on execution order.
  5. Environment-level factors — network latency, third-party service timeouts (payment gateways, KYC APIs common in BFSI), or Grid node resource contention causing slow rendering.
  6. Add diagnostics — capture browser console logs (driver.manage().logs().get(LogType.BROWSER)), network HAR captures, and screenshots at the point of failure, not just final failure.
  7. Quarantine + retry analyzer as a stop-gap, not a fix — TestNG IRetryAnalyzer can retry a flaky test up to N times to unblock CI, but the underlying root cause still needs a ticket and fix; retries should never be used to mask a genuine bug.
public class RetryAnalyzer implements IRetryAnalyzer {
    private int count = 0;
    private static final int MAX_RETRY = 2;

    @Override
    public boolean retry(ITestResult result) {
        if (count < MAX_RETRY) {
            count++;
            return true;
        }
        return false;
    }
}
  1. Track flakiness metrics over time — tag/log tests that fail intermittently across builds (via CI dashboards) to prioritize fixing the worst offenders instead of firefighting individually.
TC-10 Have you worked with Rest Assured or Postman for API automation? API & DB ›

Rest Assured (Java) — typical pattern used in a framework:

given()
    .baseUri("https://api.example.com")
    .header("Authorization", "Bearer " + token)
    .contentType(ContentType.JSON)
    .body(requestPayload)
.when()
    .post("/v1/accounts")
.then()
    .statusCode(201)
    .body("accountId", notNullValue())
    .time(lessThan(2000L));

Framework-level API design: - A base RequestSpecBuilder / ResponseSpecBuilder shared across all API tests to avoid repeating base URI, headers, auth setup. - POJOs/DTOs for request and response bodies (serialized/deserialized via Jackson) instead of raw JSON strings — improves compile-time safety and readability. - Separate API client classes per resource (AccountApiClient, TransactionApiClient) mirroring the POM pattern used for UI — keeps endpoint logic out of test methods. - Chained UI+API tests — e.g., create test data via API for speed, then validate the resulting state in the UI (common BFSI pattern: create an account via API, verify balance display in UI).

Postman — used for exploratory/manual API validation and quick contract checks before automating, plus Postman Collections + Newman for lightweight CI smoke checks when a full Rest Assured suite isn't warranted (e.g., quick sanity check of a third-party mock service).

Edge case relevant to BFSI: validating idempotency keys, retry-safe POST behavior, and asserting on sensitive fields being masked/encrypted in API responses (e.g., account numbers, SSNs) — a good answer to mention given the domain.

TC-11 How do you validate a JSON response using Java? API & DB ›

Using Rest Assured's built-in JSON Path (most common in interviews):

Response response = given().get("/v1/accounts/123");

response.then().body("status", equalTo("ACTIVE"));
response.then().body("balance", greaterThan(0f));
response.then().body("transactions.size()", equalTo(5));
response.then().body("transactions[0].type", equalTo("CREDIT"));

Using Jackson to deserialize into a POJO and assert with normal Java/AssertJ:

ObjectMapper mapper = new ObjectMapper();
AccountResponse account = mapper.readValue(response.asString(), AccountResponse.class);

assertThat(account.getStatus()).isEqualTo("ACTIVE");
assertThat(account.getBalance()).isPositive();

Schema validation (structural correctness, not just value checks):

response.then().assertThat()
    .body(matchesJsonSchemaInClasspath("schemas/account-schema.json"));

This is important for contract testing — catches breaking changes in API structure even when specific field values happen to pass.

JsonPath library directly (without Rest Assured), when parsing raw JSON strings:

DocumentContext context = JsonPath.parse(jsonString);
String status = context.read("$.status");
List<String> types = context.read("$.transactions[*].type");

Edge case to mention: for BFSI APIs, also validate JSON key absence (e.g., ensure a masked PAN/account field doesn't leak full digits) using response.then().body("$", not(hasKey("fullAccountNumber"))) — going beyond happy-path validation shows security-conscious testing.

TC-12 Different waits in Selenium — when to use implicit, explicit, or fluent waits Selenium Core ›

Implicit Wait:

driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));

Applies globally to all findElement calls for the driver's lifetime — Selenium polls the DOM up to the timeout before throwing NoSuchElementException. Downside: it's a blunt instrument; can't customize per-element conditions, and mixing implicit + explicit waits causes unpredictable wait times (a well-known anti-pattern Selenium docs explicitly warn against).

Explicit Wait:

WebDriverWait wait = new WebDriverWait(driver, Duration.ofSeconds(15));
WebElement el = wait.until(ExpectedConditions.visibilityOfElementLocated(By.id("submitBtn")));

Waits for a specific condition (visibility, clickability, presence, staleness, alert presence, etc.) on a specific element — the recommended default for modern frameworks since it's targeted and doesn't block unrelated calls.

Fluent Wait:

Wait<WebDriver> fluentWait = new FluentWait<>(driver)
    .withTimeout(Duration.ofSeconds(30))
    .pollingEvery(Duration.ofMillis(500))
    .ignoring(NoSuchElementException.class);

WebElement el = fluentWait.until(d -> d.findElement(By.id("dynamicBtn")));

Like explicit wait but with configurable polling interval and ability to ignore specific exceptions during polling — useful when an element intermittently throws StaleElementReferenceException while it's still rendering, and you want to keep retrying instead of failing on the first exception.

Practical guidance to state in interview: - Never mix implicit and explicit waits in the same test — pick one strategy, generally explicit-only, as the framework standard. - Use fluent wait selectively for known-flaky dynamic components (e.g., elements affected by client-side re-renders), not as the default for every locator — it adds unnecessary complexity otherwise. - Avoid Thread.sleep() entirely except for rare, well-documented cases (e.g., waiting out a rate limiter) — it's a code smell in production frameworks.

TC-15 How to implement data-driven testing using Excel, CSV, or JSON Data-Driven ›

Excel via Apache POI, wired into a TestNG @DataProvider:

@DataProvider(name = "loginData")
public Object[][] getLoginData() throws IOException {
    List<Object[]> data = new ArrayList<>();
    FileInputStream fis = new FileInputStream("testdata/login.xlsx");
    Workbook wb = new XSSFWorkbook(fis);
    Sheet sheet = wb.getSheetAt(0);
    for (Row row : sheet) {
        if (row.getRowNum() == 0) continue; // skip header
        data.add(new Object[]{
            row.getCell(0).getStringCellValue(),
            row.getCell(1).getStringCellValue()
        });
    }
    wb.close();
    return data.toArray(new Object[0][]);
}

@Test(dataProvider = "loginData")
public void testLogin(String username, String password) {
    // test logic
}

CSV via OpenCSV:

@DataProvider(name = "csvData")
public Object[][] getCsvData() throws Exception {
    CSVReader reader = new CSVReader(new FileReader("testdata/users.csv"));
    List<String[]> rows = reader.readAll();
    rows.remove(0); // header
    return rows.toArray(new Object[0][]);
}

JSON via Jackson, mapped to POJOs (cleaner for structured/nested test data):

@DataProvider(name = "jsonData")
public Object[][] getJsonData() throws IOException {
    ObjectMapper mapper = new ObjectMapper();
    TestUser[] users = mapper.readValue(new File("testdata/users.json"), TestUser[].class);
    Object[][] data = new Object[users.length][1];
    for (int i = 0; i < users.length; i++) data[i][0] = users[i];
    return data;
}

Design considerations: - Keep a single TestDataReader utility interface abstracting the source (Excel/CSV/JSON/DB) so test classes don't care where data comes from — swappable via config. - For large data sets, consider lazy-loading or streaming rather than loading the entire file into memory upfront. - Separate environment-specific data (URLs, IDs) from business/test data (input combinations) — mixing them makes data files hard to maintain across environments. - For BFSI-specific data-driven scenarios (interest rate tiers, loan eligibility matrices), JSON/Excel-driven parameterization is especially valuable since business analysts can maintain data without touching code.

TC-16 Strategies to keep test scripts reusable and maintainable as the project grows Framework Design ›
  • Strict POM/Component adherence — no raw Selenium calls inside @Test methods; all element interaction goes through page/component classes.
  • BasePage/BaseTest classes — common setup/teardown, wait helpers, and logging centralized, inherited by all pages/tests.
  • Utility layer for cross-cutting concerns (screenshots, file I/O, date handling, string generation) — never duplicate logic across test classes.
  • Test grouping/tagging (@Test(groups = {"smoke","regression","sanity"})) so suites can be sliced by CI stage (fast smoke on every commit, full regression nightly).
  • Configuration externalization — zero hardcoded environment values, timeouts, or credentials in test code.
  • Consistent naming conventions — test<Feature><Scenario> method naming, <Page>Page class naming, so any team member can navigate the codebase intuitively.
  • Code reviews + static analysis — enforce via SonarQube/Checkstyle in CI to catch anti-patterns (hardcoded sleeps, duplicated locators) before merge.
  • Version control discipline — feature-branch workflow, PR review for framework/core changes since they impact the whole suite.
  • Documentation — a README covering framework setup, how to add a new page object, how to run locally vs CI, onboarding new team members faster.
  • Regular refactoring debt tracking — treat flaky tests and duplicated code as technical debt with visibility (e.g., a Jira backlog), not something perpetually deferred.
  • Dependency management — pin library versions in pom.xml, review/upgrade Selenium/TestNG versions deliberately rather than letting drift cause silent breakage.
TC-17 Java program: Reverse a string / check for a palindrome Coding ›

Reverse a String (multiple approaches — mention the manual one in an interview to show fundamentals, not just library shortcuts):

public class StringReverser {

    // Manual approach - O(n) time, O(n) space
    public static String reverse(String input) {
        char[] chars = input.toCharArray();
        int left = 0, right = chars.length - 1;
        while (left < right) {
            char temp = chars[left];
            chars[left] = chars[right];
            chars[right] = temp;
            left++;
            right--;
        }
        return new String(chars);
    }

    public static void main(String[] args) {
        System.out.println(reverse("automation")); // noitamotua
    }
}

Palindrome Check:

public class PalindromeChecker {

    public static boolean isPalindrome(String input) {
        String cleaned = input.toLowerCase().replaceAll("[^a-z0-9]", "");
        int left = 0, right = cleaned.length() - 1;
        while (left < right) {
            if (cleaned.charAt(left) != cleaned.charAt(right)) {
                return false;
            }
            left++;
            right--;
        }
        return true;
    }

    public static void main(String[] args) {
        System.out.println(isPalindrome("Madam"));          // true
        System.out.println(isPalindrome("A man a plan a canal Panama")); // true
        System.out.println(isPalindrome("selenium"));        // false
    }
}

Edge cases to call out in the interview: - Normalize case and strip non-alphanumeric characters if the requirement is "ignore punctuation/spaces/case" (as in the classic "A man, a plan, a canal: Panama" example). - Empty string and single-character strings are trivially palindromes — handle without special-casing by letting left < right naturally short-circuit. - Mention time/space complexity: O(n) time, O(1) extra space for the two-pointer approach (excluding the cleaned string copy) — shows awareness beyond just "made it work."

TC-21 How do you handle dynamic web tables in Selenium? Selenium Core › 
public String getCellValue(WebDriver driver, String rowIdentifierText, String columnHeader) {
    List<WebElement> headers = driver.findElements(By.cssSelector("table thead th"));
    int colIndex = -1;
    for (int i = 0; i < headers.size(); i++) {
        if (headers.get(i).getText().trim().equalsIgnoreCase(columnHeader)) {
            colIndex = i;
            break;
        }
    }
    if (colIndex == -1) throw new NoSuchElementException("Column not found: " + columnHeader);

    List<WebElement> rows = driver.findElements(By.cssSelector("table tbody tr"));
    for (WebElement row : rows) {
        if (row.getText().contains(rowIdentifierText)) {
            List<WebElement> cells = row.findElements(By.tagName("td"));
            return cells.get(colIndex).getText();
        }
    }
    throw new NoSuchElementException("Row not found: " + rowIdentifierText);
}

Design principles: - Never hardcode row/column indices when headers exist — resolve column index dynamically from header text so the method survives column reordering. - For paginated tables, wrap the row search in a loop that checks for a "Next" button and re-scans each page until found or pagination ends. - For virtualized/infinite-scroll tables (only rendering visible rows in the DOM — common in React grids like AG Grid), scroll incrementally and re-query after each scroll, since off-screen rows won't exist in the DOM at all. - For sorting/filtering validation (a frequent BFSI ask — e.g., transaction history sorted by date), extract the full column into a List<String>, convert to appropriate types (dates, currency), and assert against a sorted copy using Java's Comparator, rather than eyeballing a few rows.

TC-25 Soft Assert vs Hard Assert in TestNG — when do you use each? TestNG ›

Hard Assert (org.testng.Assert) — stops test execution immediately on first failure:

Assert.assertEquals(actualBalance, expectedBalance, "Balance mismatch");
// Any code after a failed assertion here never runs

Soft Assert (org.testng.asserts.SoftAssert) — collects all failures and reports them together at the end, without halting execution mid-test:

SoftAssert softAssert = new SoftAssert();
softAssert.assertEquals(actualName, expectedName, "Name mismatch");
softAssert.assertEquals(actualEmail, expectedEmail, "Email mismatch");
softAssert.assertEquals(actualStatus, expectedStatus, "Status mismatch");
softAssert.assertAll(); // must be called explicitly, or failures are silently swallowed

When to use which: - Hard assert for critical path checks where continuing is meaningless if one fails (e.g., login failed → no point checking dashboard elements). - Soft assert for validating multiple independent fields on a single page/response in one pass (e.g., verifying 10 fields on an account summary page) — gives a complete picture of what's broken in one run instead of a fix-rerun-fix cycle for each field individually.

Common mistake to flag: forgetting softAssert.assertAll() at the end of the test — the test will report as passed even with failed soft assertions if assertAll() is never invoked, since that's the method that actually triggers the failure.

TC-26 Explain TestNG annotation execution order and common annotations used in a framework. TestNG ›

Execution hierarchy (class-level, single test method):

@BeforeSuite → @BeforeTest → @BeforeClass → @BeforeMethod → @Test → @AfterMethod → @AfterClass → @AfterTest → @AfterSuite

Typical framework usage:

@BeforeSuite   // one-time: read global config, start Extent report
@BeforeTest    // per <test> tag in testng.xml: e.g., environment-specific setup
@BeforeClass   // per class: e.g., navigate to base URL for that page's tests
@BeforeMethod  // per test method: e.g., initialize WebDriver (critical for parallel execution)
@Test(priority = 1, groups = {"smoke"}, dependsOnMethods = {"testLogin"})
@AfterMethod   // per test method: quit driver, capture screenshot on failure
@AfterClass
@AfterTest
@AfterSuite    // one-time: flush/close Extent report

Key attributes worth mentioning: - priority — controls execution order within the same class (lower runs first); avoid over-relying on this for logical flow — tests should be independent where possible. - dependsOnMethods — skips a test (marked SKIP, not FAIL) if its dependency fails; useful for genuinely sequential flows (e.g., create account → verify account) but overuse creates fragile test chains. - alwaysRun = true on @AfterMethod ensures cleanup (like driver.quit()) runs even if the @Test or a @BeforeMethod failed — omitting this is a common cause of orphaned browser processes in CI. - enabled = false to temporarily disable a test without deleting it (paired with a tracking ticket, not a silent long-term skip).

TC-27 Difference between `@DataProvider` and `@Parameters` in TestNG — when do you use each? TestNG ›

@Parameters — values come from testng.xml, fixed per suite/test run, good for environment-level or small config values:

Rule of thumb to state in interview: @Parameters for static, XML-level configuration (browser, environment, base URL); @DataProvider for actual test data variation where you want the same test logic to run N times with different inputs — especially when that data is voluminous or externally sourced, which XML parameters can't reasonably handle.

TC-35 What are your exception handling best practices in test automation code? Framework Design ›
  • Never use empty catch blocks — silently swallowing an exception (catch (Exception e) {}) hides real failures and produces false-positive passes; at minimum log it, and usually re-throw or fail explicitly.
  • Catch specific exceptions, not generic Exception, wherever the failure mode is known (NoSuchElementException, TimeoutException, StaleElementReferenceException) — broad catches mask unrelated bugs (e.g., a NullPointerException from a framework bug getting silently treated the same as an expected locator miss).
  • Fail fast for setup/precondition failures — if @BeforeMethod driver initialization fails, the test should be marked as an error immediately, not proceed into a @Test method that will produce a confusing cascade of unrelated NullPointerExceptions.
  • Distinguish expected vs. unexpected exceptions — e.g., in negative test scenarios, catching and asserting on an expected validation error is legitimate test logic, not exception "handling" in the defensive-programming sense; keep these clearly separated in code (assertThrows style) rather than generic try-catch.
  • Always release resources in finally or @AfterMethod(alwaysRun = true) — driver quit, DB connection close, file handle close — regardless of whether the test passed or failed, to prevent resource leaks accumulating across a long CI run.
  • Don't use exceptions for normal control flow — e.g., don't rely on catching NoSuchElementException as the standard way to check "does this element exist"; use driver.findElements() (plural, returns empty list instead of throwing) for existence checks instead.
TC-36 How do you perform database testing / validation using JDBC in a Java automation framework? API & DB › 
public class DBUtils {
    private static Connection getConnection() throws SQLException {
        String url = ConfigReader.get("db.url");
        return DriverManager.getConnection(url, ConfigReader.get("db.user"), ConfigReader.get("db.password"));
    }

    public static Map<String, Object> getRowAsMap(String query) throws SQLException {
        try (Connection conn = getConnection();
             PreparedStatement stmt = conn.prepareStatement(query);
             ResultSet rs = stmt.executeQuery()) {

            Map<String, Object> result = new HashMap<>();
            if (rs.next()) {
                ResultSetMetaData meta = rs.getMetaData();
                for (int i = 1; i <= meta.getColumnCount(); i++) {
                    result.put(meta.getColumnName(i), rs.getObject(i));
                }
            }
            return result;
        }
    }
}

Usage in a test — validating that a UI/API action correctly persisted to the DB:

TC-37 How would you validate data reconciliation across UI, API, and DB layers for the same business entity? API & DB ›

This is a layered validation strategy, useful to describe as a structured approach:

  1. Trigger the action via UI or API (e.g., submit a fund transfer).
  2. Capture the resulting identifier (transaction ID, account reference) returned by the UI confirmation or API response.
  3. Query the DB using that identifier to fetch the authoritative persisted record.
  4. Query the API (a GET/read endpoint) for the same identifier to fetch what the API layer reports.
  5. Assert three-way consistency: UI-displayed value == API response value == DB persisted value, for every field that should match across layers (amount, status, timestamp, currency).
  6. Account for legitimate transformation differences — e.g., DB might store amount in minor units (cents/paise) while UI displays formatted currency; API might return ISO 8601 timestamps while UI shows localized date format. TC-39 What's contract testing, and are you familiar with tools like Pact? API & DB ›

Contract testing verifies that a consumer (e.g., UI/frontend or another microservice) and a provider (the API) agree on the shape and behavior of their interface, without requiring both to be deployed together for every test run — addressing a gap that end-to-end tests alone don't efficiently cover in a microservices architecture.

How Pact typically works: 1. Consumer team writes tests defining expected interactions ("when I POST this payload, I expect this response shape") — this generates a pact file (a JSON contract). 2. The pact file is published to a Pact Broker. 3. Provider team runs provider verification tests against that same pact file in their own CI pipeline, confirming their actual API still satisfies the contract. 4. Breaking changes are caught in the provider's CI before deployment, without needing a full end-to-end environment spun up.

Relevance to mention honestly: if your direct hands-on Pact experience is limited, it's fine to say you understand the concept and value (catching consumer-provider contract drift early, reducing dependency on slow/flaky full-stack E2E environments for every interface check) even without deep tool-specific experience — this is a common "awareness-level" question at senior interviews, and overclaiming specific tool depth is riskier than being precise about your actual exposure.

TC-41 Where does UI test automation fit in the test pyramid, and how do you decide what to automate at which layer? Strategy & BDD ›

Test Pyramid (bottom to top):

        /\
       /UI\          ← fewer, slower, higher-value end-to-end flows
      /----\
     / API  \        ← more numerous, faster, business-logic-focused
    /--------\
   /   Unit   \      ← most numerous, fastest, isolated logic
  /------------\

Practical decision framework: - Unit tests (owned mostly by developers) — individual method/class logic, no external dependencies, milliseconds per test. - API/service-level tests — business logic validation without UI rendering overhead; this is where the bulk of functional test coverage should live for a mature QA automation strategy, since they're faster and less brittle than UI tests while still exercising real integration points. - UI/E2E tests — reserved for critical user journeys that must be validated exactly as a real user experiences them (login, checkout/payment flow, core navigation) — kept deliberately small in number because they're the slowest and most maintenance-heavy layer (locator changes, timing issues, environment dependencies).

A common anti-pattern worth naming proactively: teams that push most validation into UI Selenium tests because "that's what QA knows how to write" end up with a slow, flaky, expensive-to-maintain suite (an "ice cream cone" shape — inverted pyramid) instead of a healthy pyramid. Advocating for pushing coverage down to the API/unit layer where possible — and reserving UI automation for genuine end-to-end confidence — is a senior-level answer interviewers are specifically listening for.

TC-42 What does "shift-left testing" mean, and how have you applied it? Strategy & BDD ›

Shift-left means moving testing activities earlier in the SDLC — engaging QA during requirements/design rather than only after development completes — to catch defects when they're cheapest to fix.

Practical applications: - Requirement review participation — QA reviewing user stories/acceptance criteria for testability and ambiguity before development starts, catching unclear requirements early rather than discovering gaps during test execution. - API contract review — reviewing API specs (OpenAPI/Swagger) before backend implementation, catching design issues (missing error codes, inconsistent field naming) before they're baked into code. - Test automation written alongside development, not after — API/component-level tests authored as features are built (sometimes even TDD-style for test utilities), rather than automation being a phase that starts only once a feature is "done." - Static analysis and unit test gates in CI — catching code-level issues on every commit rather than waiting for a QA regression cycle to surface them. - Early involvement in CI/CD pipeline design — ensuring automated tests are wired into the pipeline from day one of a project, not retrofitted after manual testing habits are already entrenched.

Honest, senior-level framing: shift-left is genuinely valuable but requires organizational buy-in (dev teams willing to involve QA early, product teams writing testable acceptance criteria) — it's worth acknowledging in an interview that it's as much a process/culture change as a technical practice, not something a QA engineer can single-handedly impose.

TC-43 What security testing awareness should a QA automation engineer have, even without being a dedicated security tester? Strategy & BDD ›

Not expected to be a penetration tester, but a competent SDET should be able to: - Recognize OWASP Top 10 categories relevant to functional testing — e.g., testing that error messages don't leak stack traces or internal system details (information disclosure), verifying input fields reject script injection attempts in basic XSS smoke checks, confirming authorization checks (a standard user can't access another user's account data by manipulating an ID in the URL/API — IDOR, a very common and QA-catchable class of bug). - Validate sensitive data handling — confirming PII/financial data (account numbers, SSNs) is masked in UI display, API responses, and logs — directly relevant to BFSI compliance. - Check basic auth/session behavior — session expiry after logout actually invalidates the session server-side (not just clearing client-side tokens), and that expired/invalid tokens are rejected by the API rather than silently accepted. - Verify HTTPS enforcement and that sensitive form submissions don't occur over plain HTTP. - Escalate, don't attempt, deep exploitation — the QA role's responsibility is typically to catch obvious security-relevant functional gaps during normal test design and flag anything requiring deeper investigation to a dedicated security/pentest team, not to perform actual penetration testing without proper scope/authorization.

TC-44 What's your awareness of performance testing, and when should a functional QA engineer flag performance concerns? Strategy & BDD ›

While performance testing is usually a specialized discipline (JMeter, Gatling, k6), a functional automation engineer should: - Notice and report abnormal response times encountered incidentally during functional testing (e.g., an API that normally responds in 200ms suddenly taking 4 seconds) — this is often the earliest signal of a performance regression, well before dedicated load testing catches it. - Assert on reasonable response-time thresholds in API tests as a lightweight guardrail, not a substitute for real load testing:

  • Know when to escalate — a functional automation suite is not a substitute for dedicated load testing before a major release, especially for BFSI systems with peak-load events (e.g., month-end processing, salary-day transaction spikes) — flagging "this needs a proper load test" is itself valuable QA judgment.

TC-45 How do you handle CAPTCHA or OTP verification in automated tests? Strategy & BDD ›

CAPTCHA is deliberately designed to block automation, so the correct approach is almost never to "solve" it programmatically: - Ask for a test-environment bypass — most real-world QA/UAT environments disable CAPTCHA entirely or accept a fixed test token, configured by developers specifically to keep the flow automatable; this is the standard, correct solution and worth stating confidently as the primary answer. - Environment-specific feature flags — some apps expose a backend flag (captcha.enabled=false in QA config) precisely for this purpose.

For OTP (one-time passwords): - Test accounts configured with a fixed/predictable OTP in non-production environments (a common pattern — e.g., QA environments accepting "123456" universally for whitelisted test phone numbers). - API-based OTP retrieval — if the OTP is emailed, an automated mailbox check (via IMAP libraries like JavaMail, or a test email service API like Mailosaur/Mailtrap) can programmatically fetch and extract the OTP from the received email/SMS in near real time. - Direct DB/backend lookup — in some QA setups, the OTP value is queryable directly from a DB table or a test-only API endpoint exposed specifically for automation.

What to explicitly avoid: attempting actual CAPTCHA-solving (OCR-based image recognition, third-party CAPTCHA-solving services) — this is fragile, ethically questionable in a production context, and virtually never the right engineering answer; a senior candidate should recognize and state that clearly rather than describing a workaround that sounds impressive but is the wrong approach.

TC-46 How do you manage test data creation and cleanup to avoid polluting shared environments? Strategy & BDD ›
  • Programmatic setup via API/DB, not UI, for test preconditions — creating prerequisite data (e.g., an existing account) through a fast API call or direct DB insert rather than walking through UI screens, both for speed and to avoid coupling unrelated tests to UI stability.
  • Unique, generated identifiers per test run — using UUID, timestamps, or a dedicated test-data namespace/prefix (e.g., AUTO_TEST_<timestamp>_user@test.com) so parallel runs and repeated executions never collide on unique constraints (duplicate email, duplicate account number).
  • Explicit teardown in @AfterMethod/@AfterClass — deleting created records via API/DB after the test completes, wrapped in alwaysRun = true so cleanup happens even on test failure; an orphaned record from a failed test is a common cause of "works alone, fails in the full suite" flakiness.
  • Scheduled cleanup jobs as a safety net — a nightly job purging any leftover AUTO_TEST_*-prefixed data older than N days, catching cases where in-test cleanup itself failed (e.g., the test crashed before reaching @AfterMethod).
  • Isolated test data pools for scenarios that can't be created on the fly — e.g., an account in a specific aged/legacy state that's expensive to simulate freshly; maintain a reserved pool with a check-out/check-in mechanism to prevent two parallel tests from grabbing the same reserved record.
  • Never run destructive/creation-heavy automated tests against a genuinely shared UAT environment used by manual testers or business stakeholders concurrently without clear data namespacing — a frequent real-world friction point worth mentioning as something you've navigated.

TC-48 How do you ensure the test automation framework itself is reliable — do you test your own framework code? Framework Design ›

This is a maturity signal worth addressing directly, since it's easy to treat framework code as exempt from the same rigor applied to application code:

  • Unit tests for framework utility classes — e.g., a ConfigReader that resolves environment-specific properties, a DateUtils helper for date comparisons, a custom JsonComparator — these carry real logic and deserve JUnit/TestNG unit tests independent of any Selenium/browser dependency, since bugs here silently corrupt every test that depends on them.

  • Version-pinned dependencies — avoiding silent framework breakage from an auto-upgraded Selenium/TestNG/library version; deliberate, tested upgrades rather than floating version ranges.
  • Monitoring flakiness at the framework level, not just per-test — if a specific wait utility or a specific base method correlates with flaky failures across many unrelated tests, that's a framework defect, not a "flaky test" to individually retry-analyze away.
